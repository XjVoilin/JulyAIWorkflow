# 流程设计依据

## 保留的通用机制

- 通过机器状态检测选择下一阶段，并设置文档审查、实现波次和最终验收门禁。
- 保存原始策划输入，根据产品复杂度选择完整或精简 GDD。
- 在 MDD 前进行跨章节一致性、范围完整性和技术可行性审查。
- MDD 同时产出模块、依赖、波次、接口审查、进度和资源清单。
- 一次实现一个有明确责任的模块，以编译、接口、测试和验收证据更新进度。
- 设计变更必须标记下游影响，重新打开失效阶段并按顺序复验。
- GDD、MDD、QA 和进度采用稳定模板，但模板不替代产品决策。
- Luban 源文件、元表和生成物的误操作属于真实风险，应在最接近操作入口的位置约束。

## 不进入通用规则的内容

- 某个产品自己的编号体系、业务目录和资源前缀。
- 某个宿主层提供的生命周期、公共窗口、结算流程或注册方式。
- 固定数量的 MDD 层级与模块命名。独立产品应按真实领域责任和依赖拆分。
- 把 Figma、关卡编辑器或某种资源导入器规定为所有产品的必经阶段。

这些内容只有在目标项目实际提供相应契约且需求确实使用时，才能进入该项目的 Project Profile。

## 模板与 July 的真实边界

`E:\Projects\Other\Template_2022.3` 当前是 Unity `2022.3.62f2` 的组合根：

- 以不可变包标签固定 July 包版本。
- 拥有 provider 选择、项目配置、生成表、场景、资源和构建编排。
- 内置 Luban、YooAsset、HybridCLR、UniTask 等固定工具。
- `LubanGenerator` 支持扁平和多模块数据目录，并提供 `JulyGF/配置表/生成全部`。
- 不包含任何具体业务产品的宿主工作流。

`E:\Projects\Other\July\JulyFramework` 是包仓库：

- 包 seam 按独立安装理由、第三方依赖、Editor 边界或复用价值划分。
- 具体游戏业务由目标项目拥有，但应在职责适合时使用 JulyArch 的 `Store`、`System`、`Procedure`、`View` 四个角色；简单且不需要这些角色语义的类无需强行套用。
- 是否修改 `JulyFramework` 包仓库取决于能力能否跨产品复用，而不是业务代码是否使用 JulyArch。项目专属规则和配置留在目标项目，可复用能力才进入公共包。
- Git 消费者必须显式列出依赖闭包，并固定每个包的不可变 tag。

因此本仓库生成独立 July 产品流程：目标项目使用 JulyArch 组织游戏业务，并自行声明项目专属的宿主能力；只有经过验证的跨产品能力才沉淀到 `JulyFramework`。
