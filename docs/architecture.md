# July AI Workflow 第一版设计

## 目标

第一版验证两个核心能力：

1. 从已有 `策划案.md` 生成 GDD、有成立依据的业务能力边界和分阶段 MDD；
2. 让用户逐份审查模块代码、View 和流程接线，而不是一次生成跨越所有责任的完整功能。

用户明确指定的 MDD 是本轮唯一工作接口。第一版不保存全局状态，不自动选择下一项。

## 设计与实现阶段

### 1. GDD 与架构基线

GDD 维护产品级事实和玩家可观察的完整功能流程。功能切片可以跨多个模块，但不直接成为代码实施边界。

`MDD/骨架.md` 只维护：

- 通过成立检查的业务能力列表、成立依据、所有权和依赖方向；
- 计划中的 UI View、2D View 和相邻流程；
- 框架能力审计、人工审查和阶段门禁。

骨架不是纵向切片实现任务，不生成产品代码。

### 2. 模块

首次设计生成时，插件先提出业务能力候选，再以状态所有权、生命周期、非平凡规则、提交一致性或多调用者复杂度判断是否创建 `MDD/Modules/`。模块不按 Store/System/View 技术层拆分，也不把领域名词、Luban 表、DTO、枚举或 Content、Application、Domain、Models 等容器自动当成模块。

模块是否成立先于 JulyArch 角色选择。没有 Store/System 的纯规则模块可以成立；只有配置和简单映射的名词目录不能成立。每份模块 MDD 都记录模块成立依据、核心不变量、第一个真实调用者、删除检验和计划角色。

用户手动指定一份模块 MDD 后，插件：

1. 检查 GDD 和上游依赖；
2. 读取当前项目、用户指定参考项目和固定版本 July 包；
3. 填写“业务需要 / 候选能力 / 匹配程度 / 决定 / 依据”；
4. 确定具体 Store、System、Procedure 或普通类型；允许明确没有 JulyArch 角色，不创建模块级 `Ixxx`；
5. 只实现该模块，不生成 View、Prefab、完整流程或测试代码；
6. 用编译、Unity Console、Luban 生成、编辑器路径等证据验证；
7. 更新为 `待人工审查`，等待用户确认。

### 3. View

只有依赖模块全部 `已确认` 后才生成 View MDD。

- UI 使用 `WindowData + Events + Window`；
- 2D 使用 `ViewData + Events + View`；
- Window/View 只渲染、播放表现和发布类型化意图；
- 刷新事件携带新的 Data，不让 View 回查 Store/System；
- 每个 View 按稳定视觉职责拆分，不用一个 Window 承担完整玩家流程；
- 实现前必须实际查看参考图、Prefab 和参考项目。

### 4. 流程接线

只有涉及的模块与 View 全部 `已确认` 后才生成流程 MDD。每份只负责一个相邻状态转换，例如“主界面 → 招牌选择”或“开市 → 波次反馈”。

流程接线只负责接收意图、调用已确认模块、映射 Data、导航和发布刷新。它不新增业务规则，不创建 ApplicationSystem 或大型协调器，并清除模块/View 中指向该流程的定向 TODO。

### 5. 工具链与发布

离线内容生产放在 `Tooling/`，平台构建和真机门禁放在 `Release/`。它们不伪装成运行时业务模块，也不进入模块/View/流程三阶段的所有权。

## 目录

```text
Design/Docs/
├── 策划案.md
├── GDD.md
└── MDD/
    ├── 骨架.md
    ├── Modules/M001_<模块>.md
    ├── Views/UI/U001_<视图>.md
    ├── Views/2D/V001_<视图>.md
    ├── Flows/I001_<起点到终点>.md
    ├── Tooling/T001_<工具>.md
    └── Release/R001_<发布验收>.md
```

View、流程、工具链和发布目录按需创建，不生成空占位文档。

## MDD 类型与状态

允许的类型：

```text
架构基线 / 模块 / UI视图 / 2D视图 / 流程接线 / 工具链 / 发布验收
```

状态：

```text
规划 → 可实现 → 待人工审查 → 已确认
```

- `规划`：技术方向和责任边界尚未完成工程校准；
- `可实现`：产品规则、依赖、框架能力和预计修改树已经明确；
- `待人工审查`：AI 已实现并记录可重复验证证据；
- `已确认`：用户明确确认当前结果。

AI 不得自行写入 `已确认`。用户要求调整已确认内容时，先退回 `可实现`，调整和验证后回到 `待人工审查`。

## 第一版验证边界

目标项目暂不生成单元测试、测试 asmdef、Mock、Fake 或 Fixture。每份 MDD 必须列出与风险相称的编译、编辑器、配置生成、Prefab/Inspector、手工路径或目标平台证据。插件仓库自身脚本仍需测试。

## 失败行为

- 找不到目标设计目录、策划案或用户指定 MDD 时报告失败并停止；
- MDD 路径必须位于当前工作区 `Design/Docs/MDD/` 或其子目录；
- 产品决定不足、依赖未确认或框架证据不足时停止，不创建猜测接口或假数据；
- July 能力匹配度低时实现产品行为，不强行使用；通用能力缺口需要修改框架时先取得用户授权；
- 验证失败时保持当前状态并记录证据，不伪造成功。

## 第一版明确不做

- 不创建中央状态文件或状态脚本；
- 不自动续跑、自动选择 MDD 或管理并行功能；
- 不自动创建 Unity 项目、设计目录或策划案；
- 不提前创建 View/流程占位文件；
- 不让 AI 代替用户确认；
- 不在目标项目生成测试代码。
