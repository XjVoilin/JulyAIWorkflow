# July 游戏研发流程

本 Skill 只在用户显式引用 `$july-game-pipeline` 时运行。第一版不维护中央状态，不自动选择下一份 MDD，也不自动把工作标记为用户已确认。

## 定位项目

使用当前 Codex 工作区作为唯一 Unity 项目根目录，并固定使用 `Design/Docs` 作为设计文档目录：

1. 必须存在 `Design/Docs/策划案.md`。
2. 不扫描其他目录或工作区外路径寻找替代文件。
3. 用户指定 MDD 时，将其解析为当前工作区内路径并验证它位于 `Design/Docs/MDD/` 或其子目录。
4. 设计目录、策划案或指定 MDD 缺失时，明确报告缺失路径并停止，不自动创建。

读取 [July 项目约定](references/july-project-profile.md) 并验证当前工程。前提不满足时，明确报告执行失败和缺失项，然后停止。

## 选择动作

### 生成或更新设计

用户明确要求根据策划案生成或更新 GDD、MDD 时执行。先读取 [第一版产物契约](references/artifact-contract.md)，然后：

1. 从策划案生成或更新 `Design/Docs/GDD.md`。GDD 按玩家行为描述完整功能和流程，不写技术目录或类名。
2. 生成或更新 `Design/Docs/MDD/骨架.md`，只记录模块图、依赖、计划中的 View/流程和阶段门禁。
3. 从业务能力候选出发，以状态所有权、生命周期、非平凡规则、提交一致性或可复用复杂度作为模块成立依据；通过模块成立检查后，生成 `Design/Docs/MDD/Modules/M<N>_<模块>.md`。
4. 领域名词、Luban 表、DTO、枚举和简单映射不自动成为模块；没有独立行为的配置事实归入第一个负责解释和消费它们的能力模块。
5. 不把 `Content`、`Application`、`Domain`、`Models` 等技术或宽泛总称自动当作模块，也不要求每个模块必须拥有 Store 或 System。
6. 不在首次设计生成时创建 View、流程接线、代码、Prefab、配置表或测试代码。
7. 工具链或发布验收确属 GDD 范围时，可分别生成 `Tooling/` 或 `Release/` MDD。
8. 所有新 MDD 使用 `状态：规划`；架构基线在完成本次文档修改后最多为 `待人工审查`。

已有 GDD 或 MDD 时先读取并保留仍然成立的事实。需要从旧的功能切片 MDD 迁移时，把产品行为留在 GDD，把技术实施责任迁入模块、View、流程、工具链或发布 MDD；不要让两套可执行 MDD 同时存在并产生歧义。

### 生成 View MDD

仅在用户明确要求进入 View 阶段时执行：

1. 读取 [View 工作流](references/view-workflow.md)。
2. 确认目标 View 所依赖的模块 MDD 全部为 `已确认`。
3. 实际查看用户指定的参考图、Prefab 和参考项目，不以文件名或文字描述代替视觉检查。
4. 区分 `UI视图` 与 `2D视图`，按稳定视觉职责拆分，避免一个 Window 承担完整玩家流程。
5. 只生成用户本次指定范围的 View MDD，不实现代码；新文件使用 `状态：规划`。

依赖模块未确认时停止并列出依赖，不提前创建占位 View MDD。

### 生成流程接线 MDD

仅在用户明确要求进入流程接线阶段时执行：

1. 读取 [流程接线工作流](references/flow-workflow.md)。
2. 确认涉及的模块和 View MDD 全部为 `已确认`。
3. 将完整玩家流程拆为相邻起点到终点的小段，每份只负责映射数据、传递意图、触发刷新和推进该段状态。
4. 不在流程 MDD 中新增业务规则、模块角色或新的大型协调层。
5. 只生成用户本次指定范围的流程 MDD；新文件使用 `状态：规划`。

### 按指定 MDD 执行

仅在用户手动指定一份 MDD 时执行。MDD 必须位于当前工作区 `Design/Docs/MDD/` 或其子目录，不要根据功能名猜一份文件代替用户选择。

先读取策划案、GDD、指定 MDD 和当前工程，再根据顶部 `类型` 路由：

- `架构基线`：只审查或更新文档，不创建产品代码、配置、Prefab 或测试。
- `模块`：读取 [模块工作流](references/module-workflow.md)。
- `UI视图` 或 `2D视图`：读取 [View 工作流](references/view-workflow.md)。
- `流程接线`：读取 [流程接线工作流](references/flow-workflow.md)。
- `工具链`：按 MDD 范围读取 [Luban 工作流](references/luban-workflow.md) 和相关项目工具事实。
- `发布验收`：按 MDD 范围检查构建、平台和发布证据，不把平台适配塞入业务模块。

所有需要创建或修改产品文件的类型都遵循：

1. 检查 MDD 对应的 GDD 行为是否足够明确；存在影响实现的产品问题时先询问用户。
2. 读取 [项目结构校准](references/project-structure-calibration.md)，完成框架能力审计和预计改动树；通过校准门前不创建业务文件。
3. 涉及配置表时，在确定工作簿名称、路径或创建文件前读取 [Luban 工作流](references/luban-workflow.md)。
4. 满足产物契约后，将 MDD 更新为 `状态：可实现`。
5. 只实现指定 MDD 的范围；生成或修改代码时读取 [代码质量规则](references/code-quality.md)。
6. 不生成单元测试、测试 asmdef、Mock、Fake 或 Fixture；使用 MDD 约定的编译、Unity Console、Luban 全量生成、Prefab/Inspector、编辑器手工路径或目标平台证据验证。
7. 把实际修改、设计差异、未清除的定向 TODO 和验证结果写回同一份 MDD。
8. 实现和验证通过后更新为 `状态：待人工审查`，等待用户审查。

只有用户明确确认该 MDD 后，才能把它更新为 `状态：已确认`。用户要求调整时继续修改同一 MDD，完成后仍回到 `待人工审查`。

验证失败时保留当前状态并记录失败证据，继续修复当前 MDD 范围内的问题，不报告伪造成功。

## 没有指定 MDD 时

如果 GDD 和 MDD 已经存在，而用户只说“继续制作”但没有指定 MDD，递归列出 `MDD/` 下可选文件、类型及状态，请用户选择。不要自动决定下一项。

## 第一版边界

- 不创建 `.july-ai-workflow.json` 或 `工作流状态.md`。
- 不维护全局阶段、自动续跑、自动依赖图或独立历史状态。
- 不创建独立 GDD 审查报告或验收报告；证据写回指定 MDD。
- 不自动创建 Unity 项目、设计目录或策划案。
- 不在信息不足时用推测补出可实现 MDD。
- 不为未被指定的 MDD 实现代码。
- 不把 AI 完成等同于用户确认。
