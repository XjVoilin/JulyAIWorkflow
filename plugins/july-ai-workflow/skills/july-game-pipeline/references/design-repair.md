# MDD 实施中的设计一致性修复

本流程只在执行一份明确指定的 MDD 时，发现设计链问题阻止正确实施后启用。它负责修复权威设计并恢复当前实施，不是独立命令，不授权新增产品功能或推进其他 MDD。

## 1. 先暂停代码修改

发现问题后，不继续猜测实现，不用默认值、兼容层或临时代码绕过设计。保留已经确认正确且不受问题影响的改动；如果现有改动依赖待修复契约，不把它们报告为完成。

读取目标 MDD、索引、来源模块设计、来源 GDD、相关代码和实际 Framework/Luban/UI 接口，确定问题最早出现在哪一层。不得因为实现困难就修改上游设计；只有当前设计确实缺失、冲突或违反已经确认的工程事实时才进入修复。

## 2. 确定权威修复层

### MDD 层

产品规则、模块职责、状态所有权和角色规划都明确，问题只属于具体类型、公开签名、文件路径、依赖分类、配置作者源或 Framework/Luban/UI 接口描述。

- 直接修正当前 MDD；
- 若公开契约同时被索引、M999 或其他 MDD 引用，同步修正这些引用；
- 对完整 MDD 集合重新执行契约、依赖和可执行顺序验证；
- 不询问用户，不修改 GDD 或模块设计，然后继续当前实施。

### 模块设计层

问题会改变模块职责、业务决策归属、权威状态、不变量、跨模块事务编排、依赖方向或 JulyArch 角色规划。

- 停止代码实施，给出推荐修复、原因、将修改的模块设计及受影响 MDD；
- 询问用户是否按该方案修复并继续，只问一次；
- 用户肯定确认后，读取 [module-design.md](module-design.md) 和 [mdd.md](mdd.md)，整体更新模块设计并全局归一化，再更新完整 MDD 集合；
- 用户否定或未明确确认时停止，不再修改设计或代码，也不撤销进入修复前已经存在的用户改动。

### GDD 层

问题会改变玩家可见规则、核心玩法、状态与进度、成功失败、消耗奖励、恢复行为或功能边界。

- 不自行决定产品语义；
- 一次只提出一个会阻止当前实施的产品问题，给出推荐答案，并明确说明确认后会更新 GDD、模块设计、受影响 MDD 并继续当前实施；
- 用户选择或确认答案后，该回答同时授权本次设计链修复，不再要求用户手动编辑文档或重新执行命令；
- 将用户确认的答案视为本次 GDD 修复的权威产品输入，不要求用户先回到策划案补写同一决定；
- 读取 [gdd.md](gdd.md)、[module-design.md](module-design.md) 和 [mdd.md](mdd.md)，先更新 GDD，再整体更新并全局归一化模块设计，最后更新完整 MDD 集合。
- 用户未回答、否定推荐或没有给出可确定产品语义的选择时停止，不继续修改设计或代码。

同一问题不得通过在较低层打补丁来规避更高层修复。无法唯一判断权威层时，说明两种判断会造成的具体差异并只问一个问题。

## 3. 修复与验证顺序

按照实际需要从最高受影响层向下执行：

```text
GDD
→ 模块设计全局归一化
→ 完整 MDD 集合与索引、M999
→ 当前工程契约
→ 原 MDD 实施
```

修复上下文继承当前 MDD 的来源链和本次用户确认：

- 从目标 MDD 记录的路径解析模块设计与 GDD，不要求用户再次 `@` 上游文件；
- 用户对模块修复方案或产品问题的肯定回答，同时满足本次修复涉及的已有目标更新确认，不在每一层重复询问；
- 加载 `gdd.md`、`module-design.md`、`mdd.md` 时，跳过只适用于独立“执行”入口的输入选择、默认目标和目标已存在询问，使用已经解析的准确文件；
- 各 reference 的内容边界、更新规则、全局检查和写后验证仍然全部适用。

- 每层都使用对应 reference 的更新规则与写后验证，不生成新的审查文档或流程状态；
- 只改变解决已确认问题所必需的内容，但模块设计和 MDD 必须进行完整集合检查，不能只验证当前文件；
- 保留仍有效的名称、Mxxx、Ixxx、产品规则和公开契约，不无依据重命名或删除；
- 修复后重新从磁盘读取全部受影响文档，确认来源路径、职责、状态所有权、角色、签名和依赖一致；
- 设计文档修复完成前不恢复代码实施。

## 4. 恢复或停止实施

修复并验证通过后，重新判断原目标 MDD：

- 原 MDD 身份、职责和必要前置依赖仍成立：重新读取最新 MDD，继续同一次实施，不要求用户重新执行命令；
- 原 MDD 被删除、合并、替换，或职责发生根本变化：完成设计修复后停止，说明新的实施目标，不把原 MDD 报告为已实施；
- 修复新增了尚未实施的必要前置 MDD：完成设计修复后停止，说明必须先执行的 MDD，不创建临时替代品；
- 修复后仍有新的独立产品问题：按 GDD 层规则一次只问一个问题，不把多项决策打包。

## 5. 完成报告

最终报告必须区分：

- 发现的问题及权威修复层；
- 用户确认的产品或模块决定；
- 实际修改并验证的 GDD、模块设计、MDD、索引或 M999；
- 是否恢复并完成原 MDD 实施；
- 若未继续，具体是目标失效还是缺少哪一份必要前置 MDD。

不得把仅完成设计修复描述为已经完成代码实施。
