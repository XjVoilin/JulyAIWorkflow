# 策划案到 GDD

本流程只生成、更新或重新生成 GDD，不生成 MDD，不读取技术工程，不修改代码和配置。

## 1. 确定输入与目标

优先使用用户 `@` 指定的策划案和 GDD。未指定时，只使用当前项目中名称明确且唯一的候选文件。

- 找不到策划案：报告未执行；
- 候选策划案不唯一：询问用户；
- 目标 GDD 已存在而用户只说“生成”：停止，不覆盖；
- 用户说“更新”：同时读取策划案和现有 GDD；
- 用户说“重新生成”：可以完整重写指定 GDD，但不修改其他设计文档。

未指定目标时，在策划案同目录使用 `GDD.md`。

## 2. 写入前澄清产品语义

完整阅读策划案，找出会改变核心玩法、状态、功能边界或玩家结果的缺失和冲突，例如：

- 核心循环如何开始、推进和结束；
- 成功、失败、消耗、奖励与恢复；
- 状态是否跨局或跨启动保留；
- 规则冲突时的优先级；
- 页面是入口、过程还是结果；
- 随机、撤销、重复操作和异常输入如何处理。

存在关键歧义时不要写文件。每次只问一个问题，说明影响并给出推荐答案；确认充分后再继续。普通命名、措辞和不影响产品行为的小细节可以合理处理。

## 3. GDD 内容边界

GDD 只描述产品要做什么，可以包含：

- 产品目标与核心体验；
- 核心玩法循环；
- 游戏规则与优先级；
- 状态、进度和内容解锁；
- 功能之间的关系；
- 页面、玩家输入和可见反馈；
- 配置数据需求；
- 成功、失败、边界和恢复行为；
- 供 MDD 拆分使用的功能清单。

GDD 不包含：

- Store、System、Procedure、Window、GameView 等技术角色；
- C# 类型、方法、字段、命名空间和文件路径；
- 具体 Luban 表、Bean 或字段设计；
- 图片生成、美术生产、Prefab 或 Inspector 方案。

不要逐段复述策划案，也不要用大量“待定”“可能”“建议”填充正式文档。

## 4. 最小覆盖结构

根据项目实际内容组织标题，至少检查：

```markdown
# <项目名称> GDD

## 产品目标
## 核心体验
## 核心玩法循环
## 游戏规则
## 状态与进度
## 功能说明
## 页面与玩家交互
## 配置数据需求
## 失败、边界与恢复行为
## 功能清单
```

这是最低覆盖清单，不是篇幅上限。复杂项目可以增加经济、养成、关卡、引导、随机、解锁等真实章节，并使用状态表、流程图、规则优先级表、输入结果表和页面流转表。不相关章节可以省略，不生成空章节。

第一版保持一份主 GDD，不自动拆成多份并列的权威 GDD。

## 5. 更新规则

更新已有 GDD 时：

- 保留与最新策划案不冲突的已确认产品规则；
- 策划案和现有 GDD 对同一规则冲突时先询问，不自行选择；
- 删除已经被最新确认明确否定的旧描述；
- 保证功能清单与正文一致；
- 不顺带生成或修改 MDD。

## 6. 写后验证闭环

写入 GDD 后，必须从磁盘重新读取实际文件，再对照策划案与本流程逐项确认：

- 核心玩法、状态和结果没有未确认的关键歧义；
- 功能清单覆盖正文中的真实产品功能；
- 更新时，策划案、保留规则、删除规则和功能清单彼此一致；
- 没有技术角色、代码签名和工程路径；
- 没有图片、Prefab 或美术生成内容；
- 只修改了本次指定的 GDD。

发现问题时，在 GDD 动作范围内修正并重新读取验证；发现必须由用户决定的产品语义时停止并询问，不把未验证产物报告为完成。全部通过后报告 GDD 路径和仍需用户决定的问题，然后停止。
