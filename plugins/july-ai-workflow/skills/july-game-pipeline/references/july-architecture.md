# JulyArch 角色与协作

本文件是插件唯一的 JulyArch 角色语义来源。这里只记录会改变设计决策的正向职责。

生成或实施 MDD 时，必须核对当前项目安装的 JulyFramework 源码、版本、基类和 API。若本参考与实际源码冲突，停止并报告插件需要更新，不自行兼容。

## 1. Store

Store 是可脱离单个 System 生命周期而独立共享、整体替换或持久化的权威领域状态所有者。并非所有运行时数据都必须进入 Store。

- 继承当前 Framework 的 Store 基类；
- 保存生命周期独立于单个 System，并且确实需要被多个长期能力独立使用、完整替换或持久化恢复的权威状态；
- 通过有业务语义的方法修改状态；修改路径本身保证不变量，不在每次受控修改后重新扫描和校验完整状态；
- 一致修改完成后再发布相应事件或标记 Dirty；
- `GetData()` 返回实时数据引用，可供读取、传输和持久化接入；调用方按只读约定使用，不为普通读取额外复制快照；
- `ReplaceData()` 用于存档恢复等完整数据替换，不代替普通业务修改；
- 其他模块可以直接读取 Store，并对同步且只涉及该 Store 的原子业务动作调用其公开语义方法；不要为限制这种访问额外增加只做同名转发的 System。

WindowData、View、Procedure 或同一 System 的内部类型需要读取状态，不单独构成“独立共享”。状态是权威状态、可变状态或需要被界面展示，也不自动成为 Store。

只有 Store 所拥有状态的变化必须经过该 Store 的语义方法。若状态只服务于一项长期能力，随该能力创建和销毁，不需要脱离该能力独立共享、替换或持久化，优先由 System 或其内部普通类型直接管理。把这份状态移入 System 后若不会丢失独立生命周期、替换边界或持久化边界，就不创建 Store。

## 2. System

System 是由 ArchContext 管理或定位的长期业务能力所有者，负责该能力的行为、生命周期和能力运行态。

- 模块存在不代表必须创建 System；只有能力确实需要 JulyArch 定位、初始化/关闭、持续推进或隐藏跨状态协作时才使用 System；
- 在需要隐藏业务决策、生命周期或协作步骤时提供稳定业务入口；System 不是所有 Store 读写的统一门面；
- 一个 System 只代表一项长期业务能力；可以有多个公开方法，但这些方法必须服务于该能力拥有的业务决策和一致性目标；
- 可以直接管理仅属于该能力的运行时数据，例如当前战斗中的关卡、怪物、生命值、冷却和效果；数据可变不等于必须放入 Store；
- 其他模块需要读取这类运行态时，优先提供实时状态的只读约定或针对真实业务问题的查询；不要先完整复制为中间读取类型，再由 WindowData 或调用方复制第二次；
- 可以读取 System、Store、View、配置和事件能力；
- 可以直接完成属于自身职责的业务动作；
- 跨多个状态所有者的业务事务由拥有该事务决策的 System 统一编排；
- 需要持续玩法推进时，由拥有整体会话生命周期的 System 承担唯一 Framework 原始时间入口。它把 `deltaTime` 转换为确定性的业务推进信号；单局编排者规定同一业务步内的跨模块顺序，各普通运行对象仍拥有自身速度、倒计时、队列、节奏和到期机制。不要把“唯一 Update”解释为“System 或总编排者拥有全部时间细节”；
- 业务动作确实需要等待、跨帧、取消或嵌套流程时，由 System 创建并运行 Procedure；
- Store 恢复后若还需要补充默认状态、接入配置或订阅生命周期事件，可以保留承担这些工作的 System；不要因此增加 Store 查询和写入转发；
- 可以被多份 MDD 按同一长期业务能力的明确范围逐步扩展；新增公开入口不能引入独立业务问题、不变量、生命周期或失败语义；
- 删除 System 后若调用方只需直接执行原本被转发的一次 Store 调用，说明该 System 过浅，应在设计阶段移除或收回真实职责；
- 实施时保持 MDD 已确定且符合本文件的角色。

## 3. Procedure

Procedure 是一次性的异步、跨帧或可取消流程协调对象。

- 每次调用创建新实例；
- 必须具有真实的等待、取消、跨帧生命周期或嵌套流程价值，而不只是形式上返回 `Task`；
- 协调一次由 MDD 明确定义的流程，并只保存该次执行的临时流程态；
- 可以读取 Store/System/View，并通过相应状态所有者的语义能力提交结果；
- 由 System 创建和运行；
- Window 和产品 GameView 不直接构造或运行 Procedure；
- 只同步执行一个或少量调用的操作直接放入 System、Store 或普通类型，不创建 Procedure；
- 实施时保持 MDD 已确定且符合上述成立条件的角色和调用关系。

根据动作性质选择调用方向，不使用单一固定链路：

```text
查询展示数据：WindowData → Store / System
单 Store 同步原子动作：Window / 其他模块 → Store 语义方法
长期能力动作：Window / 其他模块 → System
异步或可取消流程：Window / 其他模块 → System → Procedure → System / Store
```

System、Procedure 或普通运行对象之间要求严格顺序的核心事务使用显式调用。Event 只在状态已经完整提交后广播事实，适合多个互相独立的观察者；不得用订阅顺序表达移动、收集、落箱、胜负等事务优先级。

## 4. 普通类型

普通 C# 类型承担不需要 JulyArch 生命周期或运行时定位的真实职责，例如：

- 确定性规则和算法；
- System 内部能力运行态及其数据结构；
- 随一次会话生灭、拥有自身状态与推进机制的领域运行对象；
- 值对象与 GDD 定义的真实业务计算产物；
- 不变量；
- 纯数据转换。

角色选择依据职责。不要为了未来可能需要创建没有当前 MDD 职责的接口、包装和扩展点。

普通运行对象可以接收由 System 产生的确定性 Tick，但不接收 Unity 原始 `deltaTime`，也不自行注册独立 Update。它应自行解释并保存本领域的速度、时长和间隔，维护本领域的计数器和到期队列，并返回编排者真正需要的业务事实。编排者只决定调用顺序、跨所有者事务和结果处理，不代替运行对象维护这些机制。

System、Store、Procedure 和普通类型不是模块的固定槽位，也没有数量目标。先判断状态生命周期和动作性质，再选择满足成立条件的角色；不能从“这是一个模块”反推必须存在某种 JulyArch 角色。

## 5. UIView / Window

Window 是由 UISystem 管理生命周期的页面。

- 负责页面打开、关闭、页面级协调和渲染；
- 使用对应 WindowData 作为唯一显示输入；
- 根据动作性质，将玩家业务意图交给 System，或对同步且只涉及单个 Store 的原子动作调用 Store 语义方法；
- 管理页面级纯表现状态；
- 不直接从 Store/System 读取并组装显示内容；
- 不直接修改 Store Data 的字段或集合；
- 不直接构造或运行产品 Procedure。

## 6. GameView

GameView 是场景对象或独立 UI 子组件，不限于世界/场景表现。

它可以负责：

- 独立显示区域；
- 重复交互项；
- 拖拽和指针交互；
- 动画区域；
- 临时选中和其他纯表现状态。

复杂 Window 是否拆分 GameView 由真实 UI 职责决定，不使用序列化字段数量、代码行数等机械阈值。UI 子 GameView 的显示输入来自 WindowData 中对应数据，不绕过 Data 直接读取 Store 来渲染。

## 7. WindowData

每个 Window 都有对应 WindowData，用于正常运行和 GM 显示测试。

WindowData：

- 正常构造时通过当前 July 查询能力从 Store/System 取得首屏展示数据；
- 可以根据页面实际复杂度提供一个 `Refresh()` 或多个局部刷新方法；
- 展示字段可由 GM 创建和覆盖；
- 不修改 Store；
- 不执行业务动作；
- 不负责导航；
- 不创建或运行 Procedure。

WindowData 有且只有两种来源路径：调用方注入的实例直接成为本次显示输入，不得再被 Window 或 WindowData 的运行态查询覆盖；未注入时，Window 才创建默认实例，并在唯一映射位置从 Store 或 System 填充。正常入口要么注入已经填充的 Data，要么不注入，不能注入空默认实例后依赖隐藏的 `Refresh()` 完成首屏。Window 始终只根据最终 Data 渲染。

业务事件不强制为空，可以携带表示业务事实所需的最小稳定数据；不要把 WindowData 放进业务事件。刷新可以简单全量，也可以按 MDD 的真实需要局部更新。

## 8. Luban

Luban 保存策划配置事实。具体表、Bean、枚举和生成方式以当前项目实际作者源为准。

- 不用运行时 Store 重复保存静态配置事实；
- 不手写与生成类型语义相同的镜像类型；
- 不直接编辑生成产物；
- 新增业务作者源 Excel 文件使用 `<中文业务名>_<英文标识>.xlsx`。中文部分表达策划可读名称；英文部分使用稳定表意标识，并沿用当前工程已有的大小写、前缀和单词分隔约定；
- `__tables__.xlsx`、`__beans__.xlsx`、`__enums__.xlsx` 等 Luban 控制文件不适用业务作者源命名规则。更新已有作者源时沿用现有文件名，不因本规则自动重命名；
- 运行时变化由其生命周期所属的 System 或 Store 拥有；
- 第一版不创建项目业务 `ConfigSystem`、`ContentSystem` 或其他配置聚合入口。实际承担配置读取的业务代码通过框架 `IConfigSystem` 获取所需的表；不因读取配置额外创建 System；
- 已进入 Luban 的数值、名单、顺序、配额、文案和当前内容不在 C# 中以字面量重复表达或逐项核对；
- 默认信任 Luban 已生成配置，不在运行时预先巡检表是否存在、记录数量、引用完整性、字段范围或内容分布；
- 需要的配置在真实业务代码中直接读取和使用。不要为了更早报错或提供更友好的错误文本而改用 `TryGet...`、增加空值分支或包装自然异常；
- 只有 GDD 明确把配置缺失或非法定义为需要处理的业务状态，或者缺少校验会让错误继续运行并污染权威状态时，才在实际消费位置增加最小校验。

## 9. 业务状态与表现状态

- Store 保存需要独立共享、替换或持久化的业务状态；System 保存随长期能力生命周期存在的能力运行态；
- 拖拽影子、按钮按压、动画进度、逐项播放位置等属于 Window/GameView；
- 业务结果先完整提交，再由 View 根据 WindowData 播放表现；
- 普通动画结束不反向决定业务结果是否成立；
- 只有 GDD 明确赋予业务意义的确认、交互或等待状态，才能进入 Store、System 或 Procedure；具体角色由状态生命周期决定。

## 10. 角色稳定规则

- 模块设计在模块稳定后确定角色规划，MDD 将规划细化为具体类型、公开签名和实施范围；
- 实施 MDD 时忠实落地，不擅自删除、合并、替换或绕过角色；
- 实施 MDD 时发现模块职责、状态所有权或角色规划不合理，进入 `design-repair.md` 的模块设计层修复；只涉及具体类型、签名或实施范围时进入 MDD 层修复。设计修复完成前不绕过现有角色；
- 当前 MDD 之外的功能不得进入任何角色，即使它已经出现在 GDD 或其他 MDD 中。

## 11. 项目代码形态

- 项目业务 System 直接使用具体类型，不为其配套创建 `IXXSystem` 接口。当前 Framework API 强制要求实现的框架接口不属于项目级配套接口。
- 项目业务代码不创建静态工具类、静态管理器或静态业务入口。静态类只允许承载纯常量，例如统一的 `UIWindowID`，或满足 C#、Unity、当前 Framework 与生成器的硬性要求。
- 普通可失败操作在调用方只需区分接受或拒绝时返回 `bool`。调用方需要区分多个合法业务结果、继续不同业务路径时，使用能通过构造排除非法组合的语义结果类型；不创建只包装 `Success`、错误文本或技术异常的通用 `Result`。
- 日志位于真正负责观察或处理失败的位置。领域运行对象不需要为每个正常拒绝自行记录日志；内部违约通过异常或断言暴露，必要上下文由异常本身或外层统一诊断入口提供。
- GDD 定义的真实业务计算产物可以使用独立数据类型，例如一次营业结算、推进事实或阶段转换结果；它不是通用成功包装。
- 内部不变量违约优先在真实使用位置自然失败。只有不校验会继续运行并污染状态时才增加必要的异常或断言；不用 `bool`、默认值或日志把违约伪装成可恢复的业务失败。
- 不为了解耦、防御未来变化或方便读取而创建读取快照。是否属于快照按行为判断，不按名称判断：任何只为普通读取而复制全部或大部分可变业务状态的 `Snapshot`、`ViewState`、`ReadModel`、`DTO` 或同类结构都属于读取快照。模块直接使用已有 Store Data、System 实时状态的只读约定、真实业务值对象或配置类型；WindowData 直接完成最终显示转换，不在权威状态与 WindowData 之间增加整份读取副本。
- `WindowData` 是 Window 的显式显示输入和 GM 测试入口，不属于领域快照；存档边界，以及 GDD/MDD 明确要求的回放、跨帧冻结或提交一致性数据，可以使用独立结构。
- 普通运行对象优先允许通过真实构造入口和业务接口直接验证。不要为了测试把它们提升为 System、添加项目级接口、暴露内部集合写入口或复制快照。

## 12. 校验与失败

通用的边界验证、内部信任、快速失败、资源保护和重复判定规则统一遵循 [code-quality.md](code-quality.md)。本文件只决定失败判定应由哪个 JulyArch 角色承担：跨多个状态所有者的普通失败由拥有事务决策的 System 判定；只涉及单个 Store 的原子业务失败由该 Store 判定；紧随其后的提交不重复返回同一失败。

## 13. 项目模块与代码目录

模块是业务组织单位。一个模块拥有一项长期业务能力，以及为维持该能力一致性而必须共同管理的业务决策、规则、不变量、状态和有界流程。先根据完整 GDD、当前工程和已有 MDD 确定模块，再决定 JulyArch 角色和文件路径；System、Store、Procedure、普通类型、共享数据、MDD 拆分、命名空间和 asmdef 都不直接决定模块边界，`Modules` 下也不要求为模块创建独立 asmdef。

共同变化是判断归组的证据，不是模块定义。候选模块必须同时满足：

1. 它对所含业务决策具有唯一所有权，并能用一句话说明负责的长期业务能力及明确不负责的相邻职责；
2. 这些决策必须共同维持一致性，调用方不需要了解内部数据、配置解释和严格执行步骤；
3. 它能通过稳定而集中的接口隐藏当前实质复杂度，或者当前项目范围内已确认扩展将带来的具体规则、状态、结果或流程。

已确认扩展必须来自当前 GDD、已有模块设计或现有代码；下游 MDD、模块设计之外的零散设想和“以后可能扩展”都不能反向制造模块职责，也不为未来预建空 System、Store、Procedure、接口或包装。

判断一个候选是否包含多个决策中心时，检查其中各部分是否回答不同业务问题、维护不同不变量、拥有不同状态生命周期或失败语义，或者会被调用方独立使用。满足其中任一项时重新评估拆分；把它们提取成普通类型不会改变仍由原 System 公开并编排这些行为的模块职责。

- Store 唯一拥有其共享领域状态的表示、原子语义修改和不变量；System 唯一拥有其能力运行态和生命周期。其他模块可以读取 Store，并通过其语义方法请求同步原子变化；使用同一 Store 不代表业务决策属于 Store 所在模块；
- 一个跨模块业务事务必须有唯一编排者。若调用方必须协调多个模块的执行顺序、提交和失败处理，应把该知识收回拥有事务决策的模块；
- 公共机制模块只拥有机制、协议和聚合规则。依赖具体业务状态的判断仍由相应业务模块拥有，并在集成位置注册或连接，避免公共机制成为业务收纳模块；
- 拆分不得破坏必须完整提交的状态变化、形成循环依赖或暴露内部知识；出现任一情况时重新调整接缝；
- 大模块通过接口而不是代码量判断。实现复杂但接口集中、调用原因一致的深模块不拆；公开能力形成多组互不相关的调用原因时应重新检查；
- 小模块通过删除检查。删除后规则、不变量或流程知识会散落则保留；只需搬回少量转发且没有已确认扩展则合并；
- 只有多个方案的决策所有权和一致性边界同样正确时，才选择模块数量更少、接口更深的方案；不得为了减少数量合并独立业务决策；
- 共享 Store、相同数据、业务动词、调用方数量、所在 MDD、文件和代码规模都不能单独决定合并或拆分；
- 模块名使用稳定、具体的业务概念，不使用覆盖大部分产品职责的产品名，也不使用 `Game`、`Core`、`Common`、`Business`、`Content`、`Config` 或 JulyArch 角色作为业务收纳目录；
- System 和 Store 没有固定数量限制。每个角色都必须独立满足本文件的成立条件；同一模块出现多个 System 或 Store 时，重新检查是否存在不同长期能力、生命周期、替换边界或持久化边界，但不因数量本身拆分模块、合并无关状态或删除合理角色；
- 一个模块可以由多份 MDD 按同一长期业务能力逐步扩展；新增公开 System 能力时必须说明它为什么仍属于该能力。MDD 拆分不决定模块边界。

产品运行时代码放入 `Assets/Game/Scripts/Runtime/Modules/<模块名>/`。Store、System、Procedure 和普通业务类型是模块内部角色，不据此创建顶层 `Systems`、`Stores`、`Procedures` 或同义目录。

`Views`、`Generated`、`Shared` 等模板已有专用目录继续承担原有职责；Window、WindowData、GameView 和生成代码不因本规则迁入 `Modules`。MDD 为本次创建或修改的主要产品类型写明准确文件路径。旧 MDD 未写路径时，实施阶段按上述规则选择模块，不退回按角色分目录。
