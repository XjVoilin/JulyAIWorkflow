# 项目结构与框架能力校准

划分模块、选择角色以及创建、移动或命名任何产品文件之前完成本校准。目标是让模块设计从目标项目、用户指定参考项目和语义匹配的 July 能力中自然产生，不从空模板推导通用架构。

## 证据优先级

按以下顺序决定目录、文件粒度、命名空间、框架角色和组合方式：

1. 用户对当前实现的明确要求；
2. 用户指定的参考项目或路径；
3. 当前项目中职责相近且已经确认的模块；
4. 同一宿主体系、相近固定版本的成熟项目；
5. 当前项目固定版本 July 包的公开类型、测试、示例和模板代码；
6. 通用架构经验。

低优先级证据不得覆盖高优先级证据。当前项目接近空模板时，不得把“没有先例”解释为可以自动引入 DDD、Clean Architecture、项目名总目录或其他通用分层。

用户已经给出可读取的参考路径时直接检查。只有证据缺失、冲突且会实质改变结果时才询问。

对于当前工作流已知的 July 产品参考，如果 `E:\Projects\Kunpo\GooseMarket\Assets\Game\Scripts` 可读取且用户没有指定更高优先级参考，在空项目或缺少同类先例时用它校准模块粒度、角色组合和一文件一主要职责；该路径不可读取不构成项目失败。不得照搬其源码根目录、模块内 View、平台特例或具体跨模块耦合。

模块设计阶段至少选择若干不同形态的代表模块进行检查，例如 Store-only、System-only、Procedure-only、混合角色或 provider/普通类型模块。记录从中采用的模块尺度、角色组合和文件粒度，也记录不照搬的 View 归属、跨模块耦合、平台特例和源码根目录。参考证据及路径写入 `骨架.md`，供后续新任务复用。

## 创建文件前的检查

至少检查并写回指定 MDD：

- 业务源码实际根目录、程序集边界和 root namespace；
- 现有模块的目录深度、命名方式和一个文件承载的主要职责；
- System、Store、Procedure、View 和普通类型的真实注册或使用方式；
- UI 是否通过 July UI provider、配置表、资源地址和 Prefab 加载；
- 配置、存档、场景、事件和启动组合的标准接入路径；
- 目标 MDD 预计新增或修改的目录树、具体角色及已知依赖；
- 相关角色是否已经由 July 或当前项目提供。

若当前项目没有某类范例，检查用户指定参考项目和固定版本包；不要凭记忆补 API、Host、Factory 或兼容层。

## 框架能力审计

对 MDD 中每项技术需要记录：

| 业务需要 | 候选框架能力 | 匹配程度 | 决定 | 依据 |
| --- | --- | --- | --- | --- |
| 具体需要 | 具体类型/包/组合 | 高 / 中 / 低 | 复用 / 复用底层能力 / 产品实现 | 源码、示例或项目先例 |

匹配程度含义：

- **高**：语义、生命周期、错误合同和组合方式都匹配，直接走框架标准路径；
- **中**：只有某个底层能力匹配，例如持久化传输、事件总线或资源加载，只复用这一部分；
- **低**：强行复用会扭曲业务所有权、产生额外适配层或隐藏错误，由产品代码实现；
- **未确认**：证据不足，不得进入 `可实现` 或创建文件。

“框架已经提供”不是使用理由；“匹配度不高”也不是复制框架通用职责的理由。先找最窄的可复用能力，找不到高或中匹配时再实现产品行为。

## JulyArch 角色

按实际责任选择具体角色：

- 长期能力和初始化生命周期可以使用 System；
- 领域状态及受控变更可以使用 Store；
- 有明确开始、提交和结果的单次用例可以使用 Procedure；
- 绑定 Unity 对象和交互生命周期的表现使用 View；
- 无对应生命周期语义的确定性规则和值类型保持普通 C# 类型。

这些是候选，不是配额。每个模块可以只使用其中一部分，也可以全部保持普通类型。

禁止：

- 为模块额外创建 `Ixxx` 对外接口；
- 新增只转发调用的 `ApplicationSystem`、Manager、Facade 或总协调层；
- 因 MDD 写了“编排”就默认创建长期对象；
- 为了让代码“看起来用了 July”而让不匹配的业务继承框架角色；
- 用运行时 UI Factory 或动态 RootView 绕过项目既有 July UI 配置与 Prefab 路径。

若确有跨产品复用价值并需要修改 July Framework，先报告能力缺口并取得用户授权；单个产品 MDD 不自动扩大到包修改。

## 结构约束

- 当前 `Template_2022.3` 工程已经以 `Assets/Game/Scripts/Runtime/` 声明产品运行时代码根目录时，模块直接放在 `Runtime/Modules/<业务模块>/`，View 后续放在 `Runtime/Views/`；
- 不用项目名在既有业务源码根目录下额外包一层，除非高优先级证据要求；
- 不新增 `Application`、`Domain`、`Models` 等通用分层目录，除非项目已有一致约定；
- 不把 `Content`、`Common`、`Core` 等宽泛总称自动建成业务模块；
- 按稳定、可独立命名和维护的项目能力组织模块；状态、不变量和生命周期用于模块内部设计，不是所有模块统一成立的门槛；
- 保持项目已有文件粒度；项目采用一文件一个主要框架角色时必须遵守；
- 紧密相关的数据定义可以按项目惯例放在同一数据文件，多个 System、Store 或 View 不塞进一个文件；
- 不复制 July 已提供且匹配的生命周期、事件、持久化、资源或 UI 加载机制；
- 不创建单元测试、测试 asmdef、Mock、Fake 或 Fixture。

## 校准门

以下内容写入指定 MDD 后，才可以更新为 `状态：可实现` 并创建产品文件：

1. 使用了哪些证据及其优先级；
2. 框架能力审计表及每项决定；
3. 最终业务源码根目录和预计修改目录树；
4. 每个主要对象为何是具体 System、Store、Procedure、View 或普通类型；
5. UI、配置、存档、事件和启动组合如何复用现有能力；
6. 存在会实质改变结果的竞争方案时，记录未采用的替代结构及原因；
7. 与本 MDD 类型一致的验证方式。

实现中发现依据错误时，停止扩展错误结构，更新同一 MDD 后再继续；不要在旧结构上增加兼容层。

## 完成前审计

在进入 `待人工审查` 前检查：

- 产品文件是否全部位于校准后的根目录和模块边界；
- 是否残留试错目录、空目录、无用 `.meta` 或工具副产物；
- 是否出现无依据的项目名总目录、Application/Domain/Models、Content 总模块、ApplicationSystem、Manager、Facade、UIFactory 或 RootView；
- 是否出现模块级 `Ixxx` 接口、一个文件多个主要角色或被强行套用的 July 角色；
- UI、配置、存档、事件、资源和启动是否走已记录的标准路径；
- 是否误生成测试代码；
- 是否只保留具有明确后续归属的定向 TODO，且 TODO 不在当前可执行路径上；
- 编译、Unity Console、配置生成、Prefab/Inspector、手工路径或平台证据是否已经写回 MDD。

发现偏差时修正并重新验证，不以“能编译”代替结构和行为审计。
