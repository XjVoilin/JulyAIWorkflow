# 项目结构校准

按 MDD 实现时，在创建、移动或命名任何业务文件之前完成本校准。目标是复用目标产品真实的主机约定和已安装 July 能力，而不是把通用架构偏好写进一个缺少业务范例的模板工程。

## 证据优先级

按以下顺序决定目录、文件粒度、命名空间、框架角色和组合方式：

1. 用户对当前实现的明确要求；
2. 用户指定的参考项目或路径；
3. 当前项目中职责相近的已完成模块；
4. 同一工作区内、使用相同模板和 July 版本族的成熟项目；
5. 当前项目实际固定版本的 July 包公开类型、测试、示例和模板代码；
6. 通用架构经验。

低优先级证据不得覆盖高优先级证据。当前项目接近空模板时，不得把“没有先例”解释为可以自动引入 DDD、Clean Architecture 或其他通用分层；应继续检查用户指定的参考项目和相同宿主体系的成熟项目。

用户已经给出可读取的参考路径时直接检查，不重复询问。只有证据缺失、相互冲突且会实质改变结果时才向用户确认。

## 创建文件前的检查

至少检查并记录以下事实：

- 业务源码实际根目录、程序集边界和 root namespace；
- 现有功能模块的目录深度、命名方式和一个文件承载的主要职责；
- 注册入口如何分别注册 System、Store及其他长期对象；
- 一个代表性的 System、Store、Procedure和 View 如何使用 JulyArch；
- UI是否通过已安装的 July UI provider、配置表、资源地址和 prefab加载；
- 配置、存档、场景和启动组合已有的标准接入路径；
- 目标 MDD预计新增或修改的目录树、主要角色及其依赖方向。

若当前项目没有某类范例，检查相同宿主体系的参考项目和固定版本包；不要凭记忆补 API或主机层辅助类。

## 角色与框架复用校准

按责任选择 JulyArch角色：

- 长期能力和初始化生命周期使用 System；
- 领域状态及受控变更使用 Store；
- 有明确开始、提交和结果的单次用例使用 Procedure；
- 绑定 Unity对象和交互生命周期的表现使用 View；
- 无上述生命周期语义的确定性规则和值类型保持普通 C#类型。

不要新增只转发调用、没有独立生命周期或稳定职责的 `ApplicationSystem`、Manager或Facade。不要因为 MDD写了“用例编排”就默认创建长期外观对象；先判断一个业务 System配合若干有界 Procedure是否已经完整表达责任。

已安装能力存在时，产品代码必须走其标准组合路径。例如项目已经使用 July UI provider、窗口配置和 prefab资源加载时，不得为了省略制作接线而另建运行时 UI Factory或动态 RootView。只有产品行为或已有主机约定确实要求动态构建时才采用该方案，并在 MDD记录依据。

## 结构约束

- 不用项目名在既有业务源码根目录下额外包一层，除非当前项目已有一致约定或程序集隔离要求；
- 不新增 `Application`、`Domain`、`Models`等通用分层目录，除非高优先级项目证据明确采用它们；
- 不把一个业务总称自动当作必须存在的顶层聚合目录；按参考项目的功能模块边界组织；
- 保持项目已有文件粒度。项目采用“一文件一个主要 System、Store、Procedure或 View”时必须遵守；紧密相关的聚合数据类型可以按项目惯例放在同一数据文件中；
- 不复制 July 已提供的生命周期、事件、持久化、资源或 UI加载机制。

这些约束防止无证据的新增结构，不把任何单一产品的目录树提升为通用 July标准。

## 结构校准门

将以下内容写入指定 MDD的实现校准部分后，才可以更新为 `状态：可实现`并创建业务文件：

1. 采用了哪些项目证据及其优先级；
2. 最终业务源码根目录和预计修改目录树；
3. 每个主要对象为何是 System、Store、Procedure、View或普通类；
4. UI、配置、存档和启动组合如何复用现有 July能力；
5. 明确不采用的替代结构及原因，尤其是原 MDD中未经验证的目录和类名。

实现过程中若发现校准依据错误，先停止扩展错误结构，重新检查证据并更新同一 MDD；不要在旧结构上继续兼容或再包一层。

## 完成前结构审计

编译和功能测试之外，还要对照 MDD记录的目录树执行结构审计：

- 业务文件是否全部位于校准后的源码根目录和模块边界；
- 是否残留试错产生的项目名目录、业务总包、空目录或 `.meta`；
- 是否出现无依据的 Application/Domain/Models、ApplicationSystem、Manager、Facade、运行时 UIFactory或RootView；
- 每个主要框架角色是否按项目文件粒度独立且由标准注册入口可达；
- UI、配置、存档和资源是否确实通过已记录的 July/Luban路径工作。

发现偏差时删除错误结构并重新运行 Unity编译及相关测试；不要只让类型编译通过就报告完成。
