# 模块工作流

只用于 `类型：模块` 的 MDD。目标是先建立可人工审查的业务模块和真实角色，不提前完成 View 或玩家流程。

## 1. 校准模块边界

从 GDD 提取业务事实，再问：哪组状态、不变量和行为必须由同一个所有者维护？模块以这个所有权命名。

一个合适的模块：

- 有一个清楚的业务名称；
- 拥有一组共同变化的状态或配置解释；
- 能说明自己保证的核心不变量；
- 对下游提供有意义的具体能力，而不是数据袋或转发层；
- 大小适合用户逐份审查。

继续拆分的信号：

- 名称只能叫 Content、Common、Core、Application、Domain 或 Models；
- 同时管理多个可独立变化的聚合，例如题目、会话、结算、收藏和存档；
- 责任描述需要大量“以及”，且各项没有共同不变量；
- 修改其中一项经常不需要理解其余部分。

不要按 Store/System/Procedure 分模块，也不要把一个共同不变量机械拆成贫血小类。

## 2. 明确所有权和依赖

MDD 至少写清：

- 模块拥有的事实、派生结果和不变量；
- 不拥有的 View、跨模块流程、存档或配置职责；
- 上游模块和所需具体能力；
- 下游第一个计划使用者；
- 哪些依赖已确认，哪些仍阻止实现。

不创建模块级 `Ixxx` 接口。使用上游已经确认的具体角色或普通类型；只有固定版本框架本身要求的接口才按标准组合方式使用。

## 3. 检查框架能力

读取 [项目结构与框架能力校准](project-structure-calibration.md)，逐项填写：

| 业务需要 | 候选框架能力 | 匹配程度 | 决定 | 依据 |
| --- | --- | --- | --- | --- |

先查看当前项目和用户指定参考项目，再查看固定版本包源码、测试和示例。高匹配直接复用，中匹配只复用底层能力，低匹配在产品模块实现。证据未确认时停止，不凭包名或记忆创建类型。

框架角色必须有真实责任：

- Store 拥有需要观察和受控变更的领域状态；
- System 拥有长期能力或初始化生命周期；
- Procedure 表达有明确开始、提交和结果的一次用例；
- 普通类型承载不需要框架生命周期的规则和值。

不为了角色齐全而同时创建 Store、System 和 Procedure，不创建 ApplicationSystem、Manager 或 Facade 转发层。

## 4. 实现范围

模块实现应完成本模块当前声明的行为，而不是只生成空角色。允许：

- 模块自己的具体框架角色和普通类型；
- 与模块语义直接相关的 Luban 作者输入与 schema；
- 必需的标准注册接线；
- 模块边界的配置、文件或存档校验。

禁止：

- UIWindow、2D View、Prefab 和美术资源接线；
- 把多个模块串成完整玩家流程；
- 未在当前 MDD 中拥有的业务规则；
- 单元测试、测试 asmdef、Mock、Fake 和 Fixture；
- 只为未来可能使用而创建的空角色、接口或扩展点。

下游尚未接入时，只在未来确实需要调用或发布事件的位置留下定向 TODO：

```csharp
// TODO(FLOW:I003): 招牌确认流程在这里提交营业夜初始化结果。
```

TODO 必须指向计划的流程 MDD，不得掩盖当前模块未实现的行为，也不得出现在当前可执行路径。

## 5. 验证与交付

根据改动选择可观察证据：

- 产品程序集编译通过且 Unity Console 无新增错误；
- 涉及 Luban 时全量生成成功，并检查代表性作者输入和派生产物；
- 注册入口能发现具体框架角色；
- 通过编辑器或现有调试入口重复验证关键状态和不变量；
- 结构审计没有无依据目录、接口、角色、View、Prefab 或测试文件。

把实际目录树、框架能力决定、差异、验证结果和保留 TODO 写回 MDD。通过后将状态更新为 `待人工审查`，等待用户查看模块代码；不得自行写为 `已确认`。
