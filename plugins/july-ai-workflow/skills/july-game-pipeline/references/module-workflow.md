# 模块工作流

只用于 `类型：模块` 的 MDD。目标是先建立可人工审查的业务模块和真实角色，不提前完成 View 或玩家流程。

## 1. 先判断候选是否值得成为模块

从 GDD 提取业务能力、状态变化和规则决策，不要先把每个领域名词变成目录。一个候选至少满足一项才生成模块 MDD：

- 拥有需要受控变化的状态和共同不变量；
- 拥有明确初始化、更新或关闭生命周期；
- 以小而稳定的使用合同隐藏非平凡规则；
- 承担不可拆分的一致性或提交边界；
- 为多个真实调用者集中原本会重复的复杂度。

执行删除检验：假设删掉候选，如果复杂度会重新散落到多个调用者，它在提供价值；如果只是把 DTO、枚举、配置行或简单映射移动到唯一消费者旁边，它不是独立模块。

没有 Store 或 System 不是失败。棋盘规则、确定性分配、评分计算等纯规则能力可以全部使用普通 C#；前提是调用者通过较小的使用合同获得显著能力，而不是学习几乎等同于实现的表面。

以下候选通常合并到第一个解释和消费它们的能力模块：

- 单个领域名词及其数据定义；
- Luban 表、DTO、枚举和值对象的集合；
- 没有受控变化和不变量的数据袋；
- 没有确定调用者的未来扩展点。

作者生产本身具有独立生成、审计或发布门禁时，使用 `工具链` MDD，不把生产工具伪装成运行时业务模块。

## 2. 校准已经成立的模块边界

一个合适的模块：

- 有清楚的业务能力名称，而不只是实体名称；
- 围绕共同状态、不变量、生命周期、规则或提交边界；
- 对下游提供有意义的具体能力，而不是数据袋或转发层；
- 大小适合用户逐份审查。

继续拆分的信号：

- 名称只能叫 Content、Common、Core、Application、Domain 或 Models；
- 同时管理多个可以独立变化的聚合；
- 责任描述需要大量“以及”，且各项没有共同不变量；
- 修改其中一项经常不需要理解其余部分。

需要合并的信号：

- 只有配置、类型声明和简单映射；
- 只有一个调用者，且调用者仍需理解全部实现细节；
- 模块的公开操作与内部步骤数量接近，只增加转发；
- 无法说明删除后复杂度会扩散到哪里。

不要按 Store/System/Procedure 分模块，也不要把一个共同不变量机械拆成贫血小类。

## 3. 明确成立依据、所有权和依赖

MDD 至少写清：

- 模块成立依据及隐藏的复杂度；
- 删除检验结论；
- 模块拥有的事实、派生结果和不变量；
- 不拥有的 View、跨模块流程、存档或配置职责；
- 上游模块和所需具体能力；
- 下游第一个真实调用者；
- 计划使用的 JulyArch 角色，或明确说明“无 JulyArch 角色”；
- 哪些依赖已确认，哪些仍阻止实现。

不创建模块级 `Ixxx` 接口。使用上游已经确认的具体角色或普通类型；只有固定版本框架本身要求的接口才按标准组合方式使用。

## 4. 在边界成立后检查框架能力

读取 [项目结构与框架能力校准](project-structure-calibration.md)，逐项填写：

| 业务需要 | 候选框架能力 | 匹配程度 | 决定 | 依据 |
| --- | --- | --- | --- | --- |

先查看当前项目和用户指定参考项目，再查看固定版本包源码、测试和示例。高匹配直接复用，中匹配只复用底层能力，低匹配在产品模块实现。证据未确认时停止，不凭包名或记忆创建类型。

JulyArch 角色用于落实已经成立的模块，不用于证明模块存在。角色必须有真实责任：

- Store 拥有需要观察和受控变更的领域状态；
- System 拥有长期能力或初始化生命周期；
- Procedure 表达有明确开始、提交和结果的一次用例；
- 普通类型承载不需要框架生命周期的规则和值。

一个模块可以有多个角色、一个角色或完全没有 JulyArch 角色。不为了角色齐全而同时创建 Store、System 和 Procedure，不创建 ApplicationSystem、Manager 或 Facade 转发层。

## 5. 实现范围

模块实现应完成本模块当前声明的行为，而不是只生成空角色。允许：

- 模块自己的具体框架角色和普通类型；
- 与模块语义直接相关的 Luban 作者输入与 schema；
- 必需的标准注册接线；
- 模块边界的配置、文件或存档校验。

禁止：

- UIWindow、2D View、Prefab 和美术资源接线；
- 把多个模块串成完整玩家流程；
- 未在当前 MDD 中拥有的业务规则；
- 单元测试、测试 asmdef、Mock、Fake 和 Fixture；
- 只为未来可能使用而创建的空角色、接口或扩展点。

下游尚未接入时，只在未来确实需要调用或发布事件的位置留下定向 TODO：

```csharp
// TODO(FLOW:I003): 招牌确认流程在这里提交营业夜初始化结果。
```

TODO 必须指向计划的流程 MDD，不得掩盖当前模块未实现的行为，也不得出现在当前可执行路径。

## 6. 验证与交付

根据改动选择可观察证据：

- 产品程序集编译通过且 Unity Console 无新增错误；
- 涉及 Luban 时全量生成成功，并检查代表性作者输入和派生产物；
- 注册入口能发现具体框架角色；
- 通过编辑器或现有调试入口重复验证关键状态和不变量；
- 结构审计没有无依据目录、接口、角色、View、Prefab 或测试文件。

若模块没有 JulyArch 角色，跳过注册检查，改为验证其真实调用者可以通过计划使用合同获得结果。若实现后发现模块只剩配置或简单类型，停止交付并合并到实际消费者，而不是保留空目录。

把实际目录树、框架能力决定、差异、验证结果和保留 TODO 写回 MDD。通过后将状态更新为 `待人工审查`，等待用户查看模块代码；不得自行写为 `已确认`。
