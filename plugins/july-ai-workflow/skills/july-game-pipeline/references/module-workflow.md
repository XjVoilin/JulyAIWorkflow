# 模块工作流

只用于项目能力发现、`类型：模块` 的 MDD 设计与指定模块实现。目标是先建立全部可人工审查的项目能力和真实实现产物，不提前设计 View 或具体串联方式。

## 1. 先取得模块形态证据

在确定项目能力清单前读取 [项目结构与框架能力校准](project-structure-calibration.md)，实际检查：

1. 用户指定参考项目中的顶层模块名称、模块粒度和代表性角色组合；
2. 当前项目已经成立的源码根目录、文件粒度、命名空间和注册方式；
3. 当前固定版本 July 中 Store、System、Procedure、View 与 provider 等真实语义。

把参考路径、检查过的代表模块和结论写入 `骨架.md`。参考项目用于校准模块尺度和角色形态，不直接复制它的模块名称、View 归属、跨模块耦合、平台特例或源码根目录。新 Codex 任务必须能从 `骨架.md` 恢复这些证据，不依赖旧对话记忆。

## 2. 从完整项目流程发现能力

首次生成模块设计时，遍历 GDD 中全部主要流程，但只把流程当作能力覆盖输入：

1. 标记每段流程实际依赖的项目能力。
2. 合并在不同流程中重复出现的同一能力。
3. 补齐只出现在恢复、长期进度、平台入口、工具或发布路径中的能力。
4. 检查每项 GDD 责任是否都有归属。

不要在这里生成全局状态图、View 清单、事件图、方法调用顺序或统一协调层。

## 3. 识别项目能力

一个合适的模块名称应能完成句子：“这个项目有一项 <能力>”。团队会独立查找、讨论和修改它，并能说明它负责什么、不负责什么。

常见而自然的角色形态包括：

```text
持有一类业务状态      → Store + Data + Events
提供长期项目能力      → System
完成一次有界业务操作  → Procedure
管理状态并应用到框架  → Store + System
提供多种内部实现      → System + strategies/checkers/routes
确定性规则或值语义    → 普通类型
共享且稳定的静态业务语义 → Luban 类型化配置
```

这些只是可能形态，不是模板配额。模块可以只有一个角色，也可以包含多个角色和内部类型。

判断项目能力时优先看：

- 名称是否来自项目业务语言；
- 是否具有稳定、可独立理解的责任；
- 是否会被独立定位和维护；
- 是否在项目流程中承担真实作用；
- 是否至少有一组能够实现当前责任的真实产品代码或配置产物。

状态、不变量、生命周期、规则复杂度和提交一致性是辅助证据。它们帮助设计模块内部、选择角色和发现过大模块，但不要求所有模块都同时具备。

## 4. 拆分与归并

相邻能力即使经常在同一玩家流程中出现，只要能够独立命名、配置、修改或复用，就应分别建立模块。不要把完整流程打包成一个大模块。

继续拆分的信号：

- 名称包含多个可独立成立的业务能力；
- 需要通过大量“以及”才能描述职责；
- 内部角色分别服务不同项目概念；
- 修改其中一部分通常不需要理解其他部分；
- 为了容纳所有内容只能使用 Content、Core、Common 等宽泛名称。

需要归并到现有模块的内容：

- 模块专用 Data、Events、状态、规则、Checker、Resolver、Route 或 Helper；
- 只有表结构、值对象、枚举、资源地址和简单映射，且不满足产物契约中配置型能力的独立业务所有权；
- 玩家流程中没有独立项目含义的普通步骤；
- 仅为未来可能复用而存在的抽象或空角色。

不要按 Store、System、Procedure 分模块。同一项目能力需要的不同 July 角色属于同一模块。

## 5. 编写模块总览与 MDD

`骨架.md` 记录项目能力覆盖表：

| 项目能力 | 模块 | 负责内容 | 角色候选 | 相关 GDD 流程 |
| --- | --- | --- | --- | --- |

该表只验证能力覆盖和归属，不描述调用顺序。

覆盖表之前记录模块形态证据：当前项目与参考项目路径、实际查看的代表模块、采用的模块粒度/角色形态，以及明确不照搬的内容。没有这些证据时不能定稿模块清单。

每份模块 MDD 写清：

- 项目能力说明；
- 职责范围和明确排除；
- 相关项目流程；
- 模块自己的状态、数据、规则或生命周期；
- 计划 Store、System、Procedure、普通类型或配置型实现，以及选择原因；
- 支持该模块边界和角色选择的项目/参考/July 证据；
- 专属于该能力的内部 Data、Events、状态或策略；
- 所需 July、配置、存档、资源和平台能力；
- 待后续实现或联通事项；
- 预计修改树和验证方式。

不要求“第一个真实调用者”“删除检验”或对外 `Ixxx`。只有模块内部已经存在多个真实实现时，才按项目先例使用接口，例如 Checker、Resolver 或可替换生命周期。

## 6. 校准 July 与项目结构

模块划分前已完成第一轮形态校准；实现前再次读取 [项目结构与框架能力校准](project-structure-calibration.md)，用目标模块的具体职责和预计修改树完成第二轮能力审计。证据优先级为：

1. 用户明确要求；
2. 用户指定参考项目；
3. 当前项目已确认模块；
4. 相同宿主与 July 版本的成熟项目；
5. 固定版本 July 包源码和示例；
6. 通用经验。

为每项真实技术需要记录：

| 业务需要 | 候选框架能力 | 匹配程度 | 决定 | 依据 |
| --- | --- | --- | --- | --- |

角色选择：

- Store：持有并受控修改模块状态；
- System：提供长期能力或初始化/更新/关闭生命周期；
- Procedure：完成一次有清楚开始、执行和结果的业务操作，也可以在后期协调其他模块；
- 普通类型：承载无需 July 生命周期的规则和值。

不创建只转发调用的 ApplicationSystem、Manager、Facade，也不为了“使用 July”或满足模块门禁强行增加角色。

在新增普通产品类型前做必要性审查：如果删除该类型并让消费者直接使用 Luban 生成 Bean、`Tb*`、枚举或已有框架类型，不会损失独立行为、不变量、状态、生命周期或清楚的错误合同，就不创建。字段转发、查表转发、重命名属性和重复扫描配置完整性都不构成独立行为。该审查只判断产品类型是否必要，不作为项目能力能否成为模块的单一门槛。

## 7. 实现指定模块

模块阶段的目标是让该项目能力及已确认角色到位，而不是提前完成所有未来页面和流程行为。

允许实现：

- 已有明确理由的 Store、System、Procedure 和普通类型；
- 满足产物契约且当前责任只需要作者数据的配置型实现，不要求同时创建产品包装代码；
- 模块自身能够确定的状态、生命周期、规则和事件；
- 专属于模块语义且当前行为确实需要的 Luban 输入；
- 必需的标准注册、持久化和框架接入；
- 模块输入边界的必要校验。

暂不实现：

- 只有具体 View 或玩家功能联通后才能确定的方法、事件和映射；
- 未来展示所需的 Snapshot、Preview、Result 或资源字段集合；
- 多模块完整玩家流程；
- 没有当前责任依据的扩展点和兼容层。
- 只有未来消费者取得棋盘、顾客、流程状态或其他动态事实后才能成立的计算；不要为了把计算提前放入当前模块而把尚未拥有的事实压缩成布尔参数或占位输入。

不要用空方法、默认值、伪造成功或静默跳过表示“以后再做”。尚无代码接入位置的事项写入 MDD；只有位置已经明确时才在代码中留下可搜索、可清除的定向 TODO。

跨模块调用不是结构缺陷，但模块阶段不为未来流程提前设计调用。后期某项玩家功能由该能力发起时，可以在其 System 或 Procedure 中自然调用其他模块。

## 8. 验证与交付

根据实际改动选择证据：

- 产品程序集编译通过且 Unity Console 无新增错误；
- 角色通过目标项目标准方式注册和初始化；
- 涉及 Luban 时全量生成成功，并检查源工作簿与代表性派生产物；
- 当前已实现的状态、规则或生命周期可通过现有编辑器入口重复观察；
- 目录中没有无依据的层级、角色、接口、View、Prefab、测试或工具副产物。

如果一个模块实现后只剩配置数据，按产物契约重新判断它是否具有独立业务所有权；满足条件时记录配置型产物与消费者，不满足时归入实际解释和使用它的能力。空目录或无必要的包装代码不能作为模块产物。把实际角色文件或配置作者源、注册/配置改动、当前责任、实际差异、验证结果和待联通事项简洁写回 MDD；这些证据不完整时不能进入 `待人工审查`。

用户对模块划分或计划角色的认可只表示可以继续实现，不把 MDD 直接改为 `已确认`。通过实现验证后更新为 `待人工审查`；只有用户审查实际模块产物后才能进入 `已确认`。View 阶段同时检查状态与上述实现证据。
