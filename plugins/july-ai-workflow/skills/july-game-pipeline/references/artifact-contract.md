# 产物契约

## 输入与 GDD

`Design/Docs/策划案.md` 是用户提供的产品输入。插件不得自动创建设计目录或策划案，也不得用推测补齐缺失内容。

`Design/Docs/GDD.md` 是产品设计事实来源，至少明确：

- 产品定位、玩家目标和核心循环；
- 项目概念、规则、内容和长期状态；
- 玩家可感知的主要功能及完整项目流程；
- 每项功能的触发、结果、反馈和业务允许的分支；
- 当前范围、排除项和未决问题。

GDD 不写类名、技术目录或 July 调用方式。完整流程用于发现项目能力和检查覆盖，不直接成为模块或代码边界。

## MDD 目录与类型

所有 MDD 位于 `Design/Docs/MDD/` 或其子目录：

```text
MDD/
├── 骨架.md
├── Modules/M001_<模块>.md
├── Views/UI/U001_<视图>.md
├── Views/2D/V001_<视图>.md
├── Integrations/I001_<玩家功能>.md
├── Tooling/T001_<工具>.md
└── Release/R001_<发布验收>.md
```

允许的 `类型`：

- `架构基线`
- `模块`
- `UI视图`
- `2D视图`
- `玩家功能联通`
- `工具链`
- `发布验收`

目录按需创建。首次设计只创建架构基线、全部模块 MDD，以及 GDD 明确要求的工具链或发布验收 MDD；不提前创建 View 或玩家功能联通 MDD。

## MDD 公共信息

每份 MDD 顶部包含：

```text
类型：<允许的类型>
状态：规划
对应 GDD：<章节或功能名>
```

正文只记录当前类型真正需要的事实，通常包括：

- 目标、范围和排除项；
- 当前产物负责的项目能力或视觉职责；
- 计划角色、内部组成和依赖；
- 相关配置、资源、存档、场景或框架能力；
- 预计修改范围；
- 未决问题、待后续实现或联通事项；
- 与当前阶段相称的验证方式。

实现后可以在底部追加简洁的实际差异和验证结果，但不要把详细命令输出、临时诊断日志或重复设计说明堆入稳定正文。

## 架构基线

`骨架.md` 是随阶段演进的项目总览，不是可执行代码 MDD。

首次设计阶段只记录：

- 从完整项目流程中识别出的项目能力；
- 模块划分前实际查看的当前项目、用户指定参考项目和固定版本 July 证据；
- 从参考证据采用的模块粒度、文件粒度和角色形态，以及明确不照搬的 View 归属、耦合或产品特例；
- 项目能力到模块的覆盖关系；
- 模块名称、职责、角色候选和明确排除；
- 模块阶段顺序、状态和人工审查门禁；
- 工具链、发布或框架缺口等独立事项。

此时不规划具体 View、事件、模块调用或玩家功能联通。

全部模块确认并进入 View 阶段后，才补充完整 View 清单及 UI/2D 分类。玩家功能联通项在全部 View 确认后按用户要求登记，不预建统一运行时协调架构。

## 模块划分

模块代表项目中一项稳定、可独立命名、定位和维护的能力。它可以由一个或多个 Store、System、Procedure、普通类型及内部 Data、Events、状态、策略或适配器组成。

模块候选通常具备以下特征：

- 团队会独立谈论、查找和修改这项能力；
- 它在项目一个或多个流程中承担清楚而稳定的责任；
- 它可以与相邻能力分别理解，而不是只表示某个技术层；
- 至少存在一个有明确理由的 July 角色或普通实现；
- 模块名称使用项目业务语言，而不是宽泛容器。

状态所有权、不变量、生命周期、规则复杂度和一致性边界用于设计模块内部及判断模块是否过大，但不是所有模块必须满足的统一成立门槛。模块可以只有 Store、只有 System、只有 Procedure，也可以完全由普通类型实现。

以下内容通常不单独成为模块：

- 只有 Luban 表、DTO、枚举、值对象或资源路径；
- 只按文件类型聚合的 Data、Events、Models、Rules 或 Providers；
- `Content`、`Common`、`Core`、`Application`、`Domain` 等技术或宽泛总称；
- 仅表示玩家流程中一个没有独立项目含义的普通步骤；
- 只为未来可能复用而创建的空扩展点。

这些内容归入负责解释和使用它们的项目能力。只有作者生产本身有独立生成、审计或发布职责时，才使用 `工具链` MDD。

相邻但可独立命名和维护的能力应拆开，即使它们经常出现在同一流程中。反之，同一能力所需的 Store、System、Procedure、状态和内部策略不按技术角色拆成多个模块。

每份模块 MDD 至少记录：

- `项目能力说明`；
- `职责范围` 与 `明确排除`；
- `相关项目流程`，仅用于覆盖说明，不设计调用顺序；
- `计划角色与内部组成`；
- 模块划分与角色选择所依据的当前项目、参考项目和 July 证据；
- 配置、持久化、资源和框架依赖；
- `待后续实现或联通事项`。

不强制记录“第一个真实调用者”“删除检验”或模块级 C# 接口。

## 模块实现范围

模块阶段先建立全部识别出的项目能力及其真实角色，便于用户逐份审查。实现指定模块时：

- 完成已经能够由模块自身确定的状态、生命周期、规则和标准注册；
- 允许暂不提供只有 View 或具体玩家功能联通才能确定的方法、事件和映射；
- 不创建返回默认结果的空方法、伪造成功或当前可执行路径上的未实现分支；
- 不为未来展示提前创建 Snapshot、Preview、Result 或资源字段集合；
- 待联通事项优先记录在 MDD，代码中只有存在明确接入位置时才保留定向 TODO。

模块实现不创建 View、Prefab、完整玩家功能串联或目标项目测试代码。

模块 MDD 的 `已确认` 专指用户已经审查并接受模块实现，不是只接受模块设计文字。生成模块 MDD 后保持 `规划`；完成工程校准后可进入 `可实现`；只有计划角色代码、必要的注册/配置改动、当前范围行为和验证证据都已到位，才进入 `待人工审查`。没有运行时代码的能力必须在 MDD 中明确说明其真实产物和验证证据，不能用“文档模块”绕过门禁。

## View 与联通阶段

只有 `MDD/Modules/` 下全部模块 MDD 都是 `已确认`，且每份都记录实际角色产物和验证证据后，才能生成 View 设计。

View 阶段先形成完整 View 清单，再按 UI 与 2D 的视觉职责生成 MDD。View 只负责展示、表现和玩家意图，不复制业务规则。

只有 `骨架.md` 完整 View 清单中的所有 View MDD 都已实现并确认后，才能生成玩家功能联通 MDD。联通优先由发起该项目能力的 System、Procedure、Store 操作或普通类型承担，不默认建立独立运行时协调层。若联通暴露新的模块责任或角色，先退回对应模块 MDD 调整。

## 状态

状态流固定为：

```text
规划 → 可实现 → 待人工审查 → 已确认
```

- `规划`：设计责任和预计角色尚未完成工程校准。
- `可实现`：当前范围、参考证据、角色、修改树和验证方式已经明确。
- `待人工审查`：AI 已完成该 MDD 的实际产物并记录可重复验证证据；设计草案或待实现计划不能进入此状态。
- `已确认`：用户明确接受该 MDD 的实际产物；AI 不得自行写入，也不得用用户对设计方案的认可替代实现确认。

后期联通发现已确认模块或 View 需要调整时，先将相应 MDD 退回 `可实现`，修改和验证后重新进入 `待人工审查`。

## 当前测试边界

目标项目暂不生成单元测试、测试 asmdef、Mock、Fake 或 Fixture。验证使用编译、Unity Console、Luban 全量生成、Prefab/Inspector、编辑器手工路径或目标平台证据。插件仓库自身脚本的测试要求不受此限制。
