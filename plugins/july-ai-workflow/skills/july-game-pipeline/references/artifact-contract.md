# 第一版产物契约

## 输入

`Design/Docs/策划案.md` 是用户提供的产品输入。插件不得自动创建设计目录或策划案，也不得用推测内容补齐缺失文件。

## GDD

`Design/Docs/GDD.md` 是产品设计事实来源，至少明确：

- 产品定位、玩家目标和核心循环；
- 全局概念、规则和长期状态；
- 玩家可感知的完整功能与起点到终点流程；
- 每个功能的触发、状态变化、反馈和验收场景；
- 本轮范围、排除项和未决问题。

GDD 不写类名、技术目录或 July 调用方式。功能切片可以用于描述产品行为，但不直接决定 MDD 和代码的拆分方式。

## MDD 目录与类型

所有 MDD 位于 `Design/Docs/MDD/` 或其子目录：

```text
MDD/
├── 骨架.md
├── Modules/
│   ├── M001_<模块>.md
│   └── ...
├── Views/
│   ├── UI/
│   │   └── U001_<视图>.md
│   └── 2D/
│       └── V001_<视图>.md
├── Flows/
│   └── I001_<起点到终点>.md
├── Tooling/
│   └── T001_<工具>.md
└── Release/
    └── R001_<发布验收>.md
```

允许的 `类型`：

- `架构基线`
- `模块`
- `UI视图`
- `2D视图`
- `流程接线`
- `工具链`
- `发布验收`

目录按需创建。首次生成设计时只创建架构基线、模块，以及 GDD 明确需要的工具链/发布验收 MDD；不得提前创建空的 View 或流程 MDD。

## MDD 公共信息

每份 MDD 顶部必须包含：

```text
类型：<允许的类型>
状态：规划
对应 GDD：<章节或功能名>
```

正文始终维护：

- 目标、范围和排除项；
- 唯一职责、状态、数据和所有权；
- 上游依赖、下游使用者和依赖状态；
- 框架能力审计与角色决定；
- Luban、资源、存档或场景中与本类型真正相关的变化；
- 预计修改范围；
- 风险、未决问题和可执行验证；
- 实际修改、差异、定向 TODO 和验证证据。

结构以清楚表达事实为准，不为不涉及的主题创建空章节。

## 架构基线

`骨架.md` 只负责：

- 通过成立检查的业务能力列表、每个模块的成立依据、所有权及依赖方向；
- 计划中的 UI View、2D View 和相邻流程接线；
- MDD 类型、状态、人工审查和阶段门禁；
- 框架能力审计、TODO 和验证原则。

骨架不是可执行代码 MDD。它不得承诺具体类名，不生成空模块角色，不实现 View、Prefab、配置表、测试或玩家流程。

## 模块拆分

模块按有意义的业务能力拆分，不按完整玩家流程、技术层或领域名词表拆分。模块是否成立先于 JulyArch 角色选择；Store、System、Procedure 的数量不是模块成立条件。

候选至少满足一项：

- 拥有需要受控变化的状态和不变量；
- 拥有明确初始化、更新或关闭生命周期；
- 在小而稳定的使用合同后隐藏非平凡确定性规则；
- 承担不可拆分的一致性或提交边界；
- 将多个真实调用者原本需要重复理解的复杂度集中在一处。

每份模块 MDD 必须记录：

- `模块成立依据`：满足上述哪项，以及隐藏了什么复杂度；
- `核心不变量`：没有则说明为何仍是有深度的能力；
- `第一个真实调用者`：尚无调用者的未来扩展不单独建模块；
- `删除检验`：删除后复杂度会扩散到哪里，而不只是文件移动；
- `计划角色`：具体 Store/System/Procedure/普通类型，允许明确写“无 JulyArch 角色”。

没有 Store 或 System 不构成缺陷。纯棋盘规则、分配器、评分器等只要能以小使用合同隐藏足够复杂度，就可以是普通 C# 的独立模块。

反之，以下内容通常不是独立模块：

- 只有 Luban 表、DTO、枚举、值对象或简单字段映射；
- 只保存数据但没有受控状态变化、生命周期或不变量；
- 删除后只是把类型移动到唯一消费者旁边；
- 没有确定的第一个调用者，只为未来可能复用而存在。

这些内容归入第一个负责解释和消费它们的能力模块；只有作者生产本身具有独立流程和门禁时，才成为 `工具链` MDD。

以下是需要继续拆分或改名的信号：

- 名称是 `Content`、`Common`、`Core`、`Application`、`Domain`、`Models` 等宽泛或技术性总称；
- 同时拥有多个可以独立变化、独立审查的业务事实；
- 需要跨越配置、会话、结算、收藏、存档等多个所有权才能解释其职责；
- 只能通过罗列大量互不相关角色说明模块内容。

不要为了追求小文件把一个共同不变量拆成一组贫血类。模块要小到可人工审查，也要深到隐藏自身复杂度。

模块 MDD 只规划模块角色和行为；不创建 View、Prefab、完整玩家流程或测试代码。下游触发尚未接线时可以记录定向 TODO，但当前模块的行为不能留成空实现。

## View 与流程延迟生成

View MDD 只有在依赖模块全部为 `已确认` 后生成。它必须先区分 UI 和 2D，再按稳定视觉职责拆分。

流程接线 MDD 只有在涉及的模块与 View 全部为 `已确认` 后生成。每份只负责一个相邻起点到终点，不新增业务规则。

## 状态

状态流固定为：

```text
规划 → 可实现 → 待人工审查 → 已确认
```

### 规划

描述预计责任和边界，不承诺未经工程验证的类、文件、接口或框架调用。

### 可实现

只有满足以下条件后才能进入：

- GDD 规则足以实现；
- 上游依赖达到本类型要求的状态；
- 已检查当前代码、用户指定参考项目和固定版本 July 包；
- 已完成框架能力审计，记录业务需要、候选能力、匹配程度、决定和证据；
- 已确定业务源码根目录、模块边界、文件粒度和命名空间；
- 已明确具体 July 角色或选择普通 C# 类型的原因；
- 已明确 Luban、资源、存档、场景和启动组合变化；
- 已列出预计修改树和验证方法；
- 没有影响实现的未决问题。

### 待人工审查

AI 已完成约定范围并执行可用验证。在同一份 MDD 记录：

- 实际修改内容；
- 与原设计的差异及原因；
- 编译、编辑器、配置生成、Prefab/Inspector、手工路径或平台验证结果；
- 尚待流程接线的定向 TODO；
- 未完成项或已知限制。

验证失败不得进入该状态。

### 已确认

只有用户明确确认当前 MDD 后才能进入。AI 不得根据编译成功、自动验证成功或自己的审查结论自行写入 `已确认`。

用户要求调整已经确认的 MDD 时，开始修改前把状态退回 `可实现`；修改和验证后回到 `待人工审查`。

## 当前版本的测试边界

目标项目暂不生成单元测试、测试 asmdef、Mock、Fake 或 Fixture。验证方式必须在 MDD 中具体列出，且与风险相称。插件自身脚本的测试要求不受此限制。
