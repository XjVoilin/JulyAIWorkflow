# GDD 到模块设计

本流程只生成或更新一份项目级模块设计，不生成 MDD，不实施代码。

开始前必须已经读取 `july-architecture.md`。

## 1. 确定输入与目标

使用用户 `@` 指定的 GDD。目标模块设计由统一入口按默认位置确定。

- 找不到 GDD：报告未执行；
- 目标模块设计不存在：创建模块设计；
- 目标模块设计已存在但用户尚未确认更新：停止，不覆盖；
- 用户已对统一入口的本次询问作出肯定确认：同时读取最新 GDD、现有模块设计和当前相关代码并整体更新。

未指定目标时，在 GDD 同目录使用 `模块设计.md`。模块设计开头必须使用相对于自身位置可解析的路径记录唯一来源 GDD；不复制完整 GDD。

## 2. 检查当前工程事实

直接检查当前项目实际存在的：

- 已有产品模块、System、Store、Procedure、普通类型及注册关系；
- 权威状态、能力运行态、持久化边界和原子修改入口；
- 当前业务配置、已有公开能力和跨模块调用；
- 当前 JulyFramework 的角色、生命周期和定位方式。

沿代表性调用链记录输入、决策、状态修改、结果消费和生命周期结束。分别标明直接代码事实、现有需求下的问题、依赖未来场景的推断；目录名、已有接口和现有文档不能代替这些证据。

不读取其他产品项目，不把其他产品的模块结构作为依据，不要求项目提供额外说明 Markdown。模块设计只记录会影响业务职责与协作的工程事实，不写详细方法签名、文件实施清单或 UI 组件方案。

现有 System、Store、Procedure 和普通类型只是需要迁移或复用的工程事实，不是角色正确的证明。先根据 GDD、状态生命周期和 `july-architecture.md` 得出目标角色，再与现有代码比较；现有角色不满足成立条件时，在目标模块设计中明确收回其职责或迁移其状态，不因代码已经存在而保留。

现有代码若让编排者持有其他状态所有者的队列、计数器、游标、随机、配置换算、速度、时长或到期规则，应记录为需要迁移的职责冲突，不能把这种实现形态直接归一化为目标设计。工程事实说明“现在是什么”，目标设计仍必须独立回答“这些状态与机制应该由谁拥有”。

## 3. 先解决产品语义缺口

如果 GDD 缺少会改变业务决策、状态、不变量、事务结果或功能边界的产品语义，报告一个具体缺口并停止。建议用户先更新 GDD；当前动作不修改 GDD，也不生成部分模块设计。

普通模块命名和不改变长期职责的内部组织自行决定。只有选择会产生不同业务决策所有权、状态所有权或公共协作方向时才询问用户，每次只问一个问题并给出推荐。

## 4. 提取业务决策

从完整 GDD 和当前工程提取：

- 玩家或系统需要作出的业务判断；
- 必须持续成立的不变量；
- 权威状态及其生命周期、共享范围、替换和持久化需要；
- 必须完整提交的状态变化；
- 具有开始、结束和失败结果，并且确实需要等待、跨帧、取消或嵌套的流程；
- 需要跨模块协作的业务事务；
- 当前项目已经确认的具体扩展。

GDD 的章节、功能清单、页面、业务动词和数据对象都不是模块。先得到业务决策清单，再判断哪些决策必须由同一个长期业务能力共同维持一致性。

## 5. 建立候选模块并全局归一化

候选模块至少记录：

- 一项长期业务能力；
- 拥有的业务决策、规则和不变量；
- 明确不负责的相邻职责；
- 权威状态、能力运行态、各自生命周期、推进机制和原子变化；
- 面向其他模块的稳定语义接口；
- 跨模块事务的唯一编排者及依赖方向；
- 已确认扩展的具体内容与来源。

项目存在跨帧推进、等待、队列、节奏、随机或恢复机制时，建立状态与推进机制归属：每项业务演进都记录权威状态所有者、推进机制所有者、输入信号、对外业务事实和跨模块编排者。推进机制包括解释本领域速度、时长和间隔，以及维护相关队列、计数器、游标、随机状态、恢复算法和到期规则。除非 GDD 明确要求一个跨状态所有者事务，这些机制与其推动的权威状态必须由同一模块拥有。

对当前功能或已确认变化，用一个具体修改场景检查候选划分：主要需要阅读哪些实现和协作契约，是否被迫理解无关功能。以缩小理解范围作为职责划分的证据，不要求所有修改只涉及一个文件，也不以类数量或 View 厚薄决定边界。

在有真实选择的接缝上比较至少两个可行方案，记录推荐理由、代价、适用条件和会使该选择失效的反例；不为每个普通私有方法制造方案比较。区分职责分配与代码形态：方法、普通类、有限接口是否成立，要看它隐藏了哪些知识及有效期。

共同变化只是归组证据，不是单独结论；共享 Store、相同数据、业务动词、调用方数量、MDD、文件和代码规模也不单独决定模块边界。

全部候选建立后必须一起检查并调整：

- 同一决策、权威状态或不变量只能有一个归属模块；
- 一个候选若服务多项独立的对外业务承诺，或其部分状态确实需要独立生命周期、替换和共享，则重新评估拆分；同一业务承诺下的内部能力可以分别维护自己的算法与不变量，不因它们有不同名称或局部规则就提升为平级模块；
- 一个业务事务若要求调用方了解多个模块的严格执行顺序，则确定唯一编排模块并隐藏内部步骤；
- 编排模块只拥有跨状态所有者的阶段、顺序、提交和结果处理；领域状态的队列、计数器、游标、随机、速度换算和到期规则仍归该状态所有者。若改变某领域规则还必须修改总编排者中的机制细节，重新调整接缝；
- 对每项领域推进执行变化局部性检查：只改变该领域的速度、时长、间隔、随机、队列或恢复规则时，应主要修改状态所有者及其验证；若总编排者也必须修改机制字段、换算或分支，说明知识已经泄漏；
- 拆分若破坏原子提交、形成循环依赖或暴露内部数据、配置解释和执行步骤，则重新调整接缝；
- 公共机制模块只拥有机制、协议和聚合规则；依赖具体业务状态的判断由对应业务模块拥有，再由集成位置注册或连接；
- 大候选通过接口检查：实现复杂但接口集中、调用原因一致的深模块不拆；公开能力形成多组互不相关的调用原因时重新评估；
- 小候选通过删除检查：删除后规则、不变量或流程知识会散落则保留；只剩少量转发且没有已确认扩展则合并；
- 只有决策所有权和一致性边界同样正确时，才选择模块数量更少、接口更深的方案。

全部候选共同通过检查后才能成为最终模块设计。

## 6. 分配 JulyArch 角色

模块稳定后再规划 JulyArch 角色：

- System、Store、Procedure 和普通类型不是模块的固定槽位，不设数量目标；先判断状态生命周期和动作性质，再决定是否需要角色；
- 只有能力需要 JulyArch 定位、初始化/关闭、Framework 原始时间入口或隐藏跨状态协作时才规划 System。为每个 System 说明删除后会向调用方泄漏的生命周期、顺序或业务知识；模块存在本身不是成立依据；
- 只有状态需要脱离单个 System 生命周期，被多个长期能力独立使用、完整替换或持久化恢复时才规划 Store。为每个 Store 说明独立生命周期、替换或持久化依据；被 WindowData、View、Procedure 或同一能力内部类型读取不算独立共享；
- Procedure 只用于确实需要等待、跨帧、取消或嵌套的一次性流程，并由 System 创建和运行；纯同步操作不设计 Procedure；
- 普通类型隐藏同一模块内部的规则、算法、值对象和 System 内部运行态结构；它可以是随会话生灭并拥有自身推进机制的有状态运行对象。一个 System 接收原始时间，不构成把所有队列和计时细节收进 System 或总编排者的理由；不把只为普通读取而完整复制 Store/System 状态的类型误写为“只读业务数据”。无论命名为 `Snapshot`、`ViewState`、`ReadModel` 还是其他名称，都按实际复制行为判定；
- System 不作为 Store 的统一门面；只做 Store 查询或写入转发且不隐藏业务决策、生命周期或协作步骤时，不创建或保留该 System 接口；
- 同一模块出现多个 System 或 Store 时，检查是否真的存在不同长期能力、生命周期、替换边界或持久化边界；不因数量本身拆分模块、合并状态或删除角色；
- 不为当前没有的职责预建空角色、接口或扩展点。

需要 System 的模块，默认由它直接持有局部能力、安排跨能力顺序并管理生命周期；算法与完整局部操作保留在能力内部。另设总运行入口或工厂必须说明真实的独立宿主、复用或创建复杂度，不为保持 System 薄而增加层级。

模块设计只记录角色规划、职责和成立依据，不预写准确 C# 签名、私有实现、完整文件列表或 MDD 实施切片。

## 7. 模块设计结构

根据项目复杂度增减说明，但至少覆盖：

```markdown
# <项目名称> 模块设计

- 文档类型：模块设计
- 来源 GDD：`<相对于本文件的准确路径>`

## 业务决策归属
| 业务决策、状态或不变量 | GDD 来源 | 归属模块 |
|---|---|---|

## 模块总览
| 模块 | 长期业务能力 | 权威状态与生命周期 | 稳定接口 | 依赖 |
|---|---|---|---|---|

## <模块名>

### 负责
### 明确不负责
### 权威状态与不变量
### 稳定语义接口
### 跨模块协作与事务编排
### JulyArch 角色规划与成立依据
### 已确认扩展
### 选择理由、适用条件与反例

## 状态与推进机制归属
| 业务演进 | 权威状态所有者 | 推进机制所有者 | 输入信号 | 输出业务事实 | 跨模块编排者 |
|---|---|---|---|---|---|

## 全局依赖与集成关系
```

没有权威状态、跨模块事务或已确认扩展时明确写“无”。稳定语义接口描述其他模块需要知道的业务能力、顺序约束和失败语义，不写具体 C# 签名。项目不存在跨帧推进、等待、队列、节奏、随机或恢复机制时，可以省略“状态与推进机制归属”。

## 8. 更新规则

更新已有模块设计时：

- 以最新 GDD 的产品规则为准；
- 保留职责未变化的稳定模块名和语义；
- 根据最新角色成立条件重新判断现有 System、Store 和 Procedure，不把现有类型或注册关系当成必须保留的目标设计；
- 对全部模块重新执行全局归一化，不只修改新功能附近的模块；
- GDD 新增决策时为其确定唯一归属；
- GDD 删除或改变规则时同步清理失效的职责、依赖和角色规划；
- 不修改 GDD、MDD 或代码。

如果最新 GDD 会使模块设计产生必须由用户决定的职责冲突，停止并询问，不把局部更新报告为完成。

## 9. 写后验证闭环

写入模块设计后，必须从磁盘重新读取实际文件，并对照完整 GDD、当前工程和 `july-architecture.md` 验证：

- 来源 GDD 路径准确、唯一并可从模块设计位置解析；
- 文档类型明确为模块设计；
- GDD 中每项真实业务决策、权威状态和不变量都有唯一归属模块；
- 每个模块都能说明一项长期业务能力、稳定接口和明确不负责的相邻职责；
- 没有包含多个独立决策中心的宽泛模块，没有纯转发模块或按 JulyArch 角色划分的模块；
- 现有代码中的职责冲突被识别为迁移问题，没有因为既有编排者已经持有领域机制而把错误所有权写入目标设计；
- 小模块具有当前实质复杂度或有明确来源的已确认扩展；
- 每个跨模块业务事务都有唯一编排者，依赖无循环，拆分没有破坏原子提交或暴露内部知识；
- 存在跨帧推进、等待、队列、节奏、随机或恢复机制时，每项业务演进的权威状态、推进机制、输入信号、输出事实和跨模块编排者均已明确；状态与推进机制由同一模块拥有，除非 GDD 明确要求跨状态所有者事务并已说明唯一编排者；
- 对需要严格时序的同一业务运行单元，时间或行动入口与优先级明确，不依赖多个 System 的注册顺序；不强制无关能力共享时钟，也不把固定 Tick 设为所有项目的要求；
- 编排者没有替其他状态所有者保存或解释队列、计数器、游标、随机、速度、时长、间隔、配置换算、恢复算法和到期规则；改变单一领域机制时不需要同步修改总编排者的机制细节；
- 普通运行对象能够通过真实构造入口和稳定业务接口独立验证其主要状态转换；没有为了测试提升为 System、增加项目级接口、暴露内部集合写入口或复制状态快照；
- 公共机制没有收纳依赖具体业务状态的判断；
- 角色在模块稳定后分配，没有从模块数量或既有类型反推 System、Store 或 Procedure；
- 每个 Store 都写明脱离单个 System 的独立共享、整体替换或持久化依据；WindowData、View、Procedure 或同一能力内部读取没有被误判成独立共享；
- 每个 System 都写明必须由 JulyArch 定位、管理生命周期、持续推进或隐藏的跨状态协作；通过删除检查确认它不是 Store 读写转发；
- 每个 Procedure 都写明真实等待、跨帧、取消或嵌套流程依据，没有包装纯同步调用；
- 关键边界有代码或需求证据、选择理由与失效条件；已区分跨项目约定、项目业务规则和可能复用的公共机制，没有把现有项目类型树直接当作通用模板；
- System 与局部能力的持有关系及完整操作清楚，没有职责重叠的总编排层，也没有把创建、准备和最终发布拆成需要调用方猜测的顺序；
- 没有在 Store/System 权威状态与 WindowData 之间规划只为读取而完整复制状态的中间层；真实业务结果、跨帧冻结数据和 WindowData 已与读取快照明确区分；
- 每项普通失败只有一个判定责任位置；上游同步预检后紧随其后的原子提交没有重复返回同类业务失败；
- 多个 System 或 Store 只触发职责与生命周期复查，不因数量本身改变模块或角色；
- 模块设计没有复制完整 GDD，没有写 MDD 实施切片、准确代码签名或无依据的未来抽象；
- 只修改了目标模块设计。

发现问题时，在模块设计动作范围内修正并重新读取验证。需要改变产品语义时停止并建议更新 GDD。全部通过后报告模块设计路径、来源 GDD 和验证结果，然后停止，不生成 MDD。
