# GDD 到模块设计

本流程只生成或更新一份项目级模块设计，不生成 MDD，不实施代码。

开始前必须已经读取 `july-architecture.md`。

## 1. 确定输入与目标

优先使用用户 `@` 指定的 GDD。未指定时，只使用当前项目中名称明确且唯一的 GDD。

- 找不到 GDD：报告未执行；
- 候选不唯一：询问用户；
- 目标模块设计已存在而用户只说“生成”：停止，不覆盖；
- 用户说“更新”：同时读取最新 GDD、现有模块设计和当前相关代码；
- 用户说“重新生成模块设计”：报告第一版不支持，建议改为更新模块设计。

未指定目标时，在 GDD 同目录使用 `模块设计.md`。模块设计开头必须使用相对于自身位置可解析的路径记录唯一来源 GDD；不复制完整 GDD。

## 2. 检查当前工程事实

直接检查当前项目实际存在的：

- 已有产品模块、System、Store、Procedure、普通类型及注册关系；
- 权威状态、持久化边界和原子修改入口；
- 当前业务配置、已有公开能力和跨模块调用；
- 当前 JulyFramework 的角色、生命周期和定位方式。

不读取其他产品项目，不把其他产品的模块结构作为依据，不要求项目提供额外说明 Markdown。模块设计只记录会影响业务职责与协作的工程事实，不写详细方法签名、文件实施清单或 UI 组件方案。

## 3. 先解决产品语义缺口

如果 GDD 缺少会改变业务决策、状态、不变量、事务结果或功能边界的产品语义，报告一个具体缺口并停止。建议用户先更新 GDD；当前动作不修改 GDD，也不生成部分模块设计。

普通模块命名和不改变长期职责的内部组织自行决定。只有选择会产生不同业务决策所有权、状态所有权或公共协作方向时才询问用户，每次只问一个问题并给出推荐。

## 4. 提取业务决策

从完整 GDD 和当前工程提取：

- 玩家或系统需要作出的业务判断；
- 必须持续成立的不变量；
- 权威状态及其生命周期；
- 必须完整提交的状态变化；
- 具有开始、结束和失败结果的有界流程；
- 需要跨模块协作的业务事务；
- 当前项目已经确认的具体扩展。

GDD 的章节、功能清单、页面、业务动词和数据对象都不是模块。先得到业务决策清单，再判断哪些决策必须由同一个长期业务能力共同维持一致性。

## 5. 建立候选模块并全局归一化

候选模块至少记录：

- 一项长期业务能力；
- 拥有的业务决策、规则和不变量；
- 明确不负责的相邻职责；
- 权威状态、生命周期和原子变化；
- 面向其他模块的稳定语义接口；
- 跨模块事务的唯一编排者及依赖方向；
- 已确认扩展的具体内容与来源。

共同变化只是归组证据，不是单独结论；共享 Store、相同数据、业务动词、调用方数量、MDD、文件和代码规模也不单独决定模块边界。

全部候选建立后必须一起检查并调整：

- 同一决策、权威状态或不变量只能有一个归属模块；
- 一个候选若包含回答不同业务问题、维护不同不变量、拥有不同生命周期、失败语义或独立调用场景的决策中心，则重新评估拆分；
- 一个业务事务若要求调用方了解多个模块的严格执行顺序，则确定唯一编排模块并隐藏内部步骤；
- 拆分若破坏原子提交、形成循环依赖或暴露内部数据、配置解释和执行步骤，则重新调整接缝；
- 公共机制模块只拥有机制、协议和聚合规则；依赖具体业务状态的判断由对应业务模块拥有，再由集成位置注册或连接；
- 大候选通过接口检查：实现复杂但接口集中、调用原因一致的深模块不拆；公开能力形成多组互不相关的调用原因时重新评估；
- 小候选通过删除检查：删除后规则、不变量或流程知识会散落则保留；只剩少量转发且没有已确认扩展则合并；
- 只有决策所有权和一致性边界同样正确时，才选择模块数量更少、接口更深的方案。

全部候选共同通过检查后才能成为最终模块设计。

## 6. 分配 JulyArch 角色

模块稳定后再规划 JulyArch 角色：

- 每个模块最多一个项目业务 System、最多一个项目业务 Store，也可以没有其中任一角色；
- System 代表模块的一项长期业务能力；
- Store 拥有运行时权威状态和语义修改；
- Procedure 只用于一次性的有界流程，并由 System 创建和运行；
- 普通类型只隐藏同一模块内部的规则、算法和值对象；
- 不为满足角色数量限制合并无关能力或状态；
- 不为当前没有的职责预建空角色、接口或扩展点。

模块设计只记录角色规划和职责，不预写准确 C# 签名、私有实现、完整文件列表或 MDD 实施切片。

## 7. 模块设计结构

根据项目复杂度增减说明，但至少覆盖：

```markdown
# <项目名称> 模块设计

- 来源 GDD：`<相对于本文件的准确路径>`

## 业务决策归属
| 业务决策、状态或不变量 | GDD 来源 | 归属模块 |
|---|---|---|

## 模块总览
| 模块 | 长期业务能力 | 权威状态 | 稳定接口 | 依赖 |
|---|---|---|---|---|

## <模块名>

### 负责
### 明确不负责
### 权威状态与不变量
### 稳定语义接口
### 跨模块协作与事务编排
### JulyArch 角色规划
### 已确认扩展

## 全局依赖与集成关系
```

没有权威状态、跨模块事务或已确认扩展时明确写“无”。稳定语义接口描述其他模块需要知道的业务能力、顺序约束和失败语义，不写具体 C# 签名。

## 8. 更新规则

更新已有模块设计时：

- 以最新 GDD 的产品规则为准；
- 保留职责未变化的稳定模块名和语义；
- 对全部模块重新执行全局归一化，不只修改新功能附近的模块；
- GDD 新增决策时为其确定唯一归属；
- GDD 删除或改变规则时同步清理失效的职责、依赖和角色规划；
- 不修改 GDD、MDD 或代码。

如果最新 GDD 会使模块设计产生必须由用户决定的职责冲突，停止并询问，不把局部更新报告为完成。

## 9. 写后验证闭环

写入模块设计后，必须从磁盘重新读取实际文件，并对照完整 GDD、当前工程和 `july-architecture.md` 验证：

- 来源 GDD 路径准确、唯一并可从模块设计位置解析；
- GDD 中每项真实业务决策、权威状态和不变量都有唯一归属模块；
- 每个模块都能说明一项长期业务能力、稳定接口和明确不负责的相邻职责；
- 没有包含多个独立决策中心的宽泛模块，没有纯转发模块或按 JulyArch 角色划分的模块；
- 小模块具有当前实质复杂度或有明确来源的已确认扩展；
- 每个跨模块业务事务都有唯一编排者，依赖无循环，拆分没有破坏原子提交或暴露内部知识；
- 公共机制没有收纳依赖具体业务状态的判断；
- 每个模块最多一个项目业务 System、最多一个项目业务 Store，角色在模块稳定后分配；
- 模块设计没有复制完整 GDD，没有写 MDD 实施切片、准确代码签名或无依据的未来抽象；
- 只修改了目标模块设计。

发现问题时，在模块设计动作范围内修正并重新读取验证。需要改变产品语义时停止并建议更新 GDD。全部通过后报告模块设计路径、来源 GDD 和验证结果，然后停止，不生成 MDD。
