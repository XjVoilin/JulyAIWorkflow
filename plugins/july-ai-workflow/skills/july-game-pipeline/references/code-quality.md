# 代码质量与实现结构

本规范定义协作契约与实现质量规则。模块设计按需使用协作形式、有效期和时间规则；具体签名、契约闭包与实施验证留到 MDD 和实施阶段。模块边界、业务决策所有权与已确认扩展由 `module-design.md` 决定，JulyArch 角色由 `july-architecture.md` 决定；本文件不重新分配它们。

质量优先级固定为：产品行为正确，状态所有权与数据一致性，职责与控制流清晰，可解释和可验证，已确认变化的局部性。不得为假想变化牺牲前四项。

设计总纲：让正确行为容易实现，让错误行为难以表达；让业务决策、状态所有权和变化集中在唯一责任位置；让主控制流可以用业务语言直接阅读，让实际结果能够通过真实业务接口、自动化验证或必要诊断信息解释和复现。该总纲不自动授权读取快照、事件、接口、日志、状态类型或其他抽象；测试也必须复用生产接口，不得反向污染生产设计。具体实现仍受 GDD、模块设计、当前 MDD 和本文件后续规则约束。

## 长期设计偏好

以下是默认决策原则，不替代产品行为、数据一致性和当前任务的明确要求：

- 以修改时的理解成本衡量职责划分：修改一个已有功能，应主要阅读该功能实现和少量明确协作契约；跨功能修改允许涉及多个所有者，不为追求单文件修改重复规则或合并不同职责。
- 将一个功能的规则、参数解释和局部状态集中维护；配置事实仍保留在 Luban 作者源。跨功能共享的规则由唯一所有者维护，不散落在调用方。
- 不以类多、View 薄、统一后缀或层数衡量设计。名称表达实际职责；只有降低理解成本或封装真实规则的拆分才有价值。
- 同步方式按当前正确性需求和成本选择。每帧拉取可以是合理实现，不为消除 Update 自动改成事件；缓存、版本号和调度机制需要明确需求或性能证据，不复制完整权威状态来制造分层。
- 对用户提出的方案独立判断，说明实际收益、代价和适用条件；不把偏好当作预定结论，也不借审视设计扩大当前修改范围。

## 1. 可读性与直接性

- 代码使用 GDD、模块设计和 MDD 已建立的业务语言；名称表达业务事实、决策或动作，不使用 `Manager`、`Helper`、`Processor`、`HandleData` 等无法说明职责的泛化名称。
- 方法主线保持同一抽象层级。协调方法表达业务步骤，具体算法和转换留在拥有该知识的普通类型或私有方法中；不把资源操作、业务解释和表现提交混在同一段控制流里。
- 分支必须对应业务情况、真实边界失败、资源一致性或内部不变量违约。不要把理论上的 `null`、重复、顺序错误或未来兼容写成普通分支。
- 注释解释约束来源、非显然原因和取舍，不复述代码。能够用准确名称表达的内容不增加注释。
- 不以行数、字段数或方法数机械拆分类和方法。只在出现可独立命名的知识、决策、算法或生命周期时拆分。
- 不用布尔参数切换互不相同的行为；调用方有不同业务意图时使用不同语义入口，纯内部且含义明显的局部开关除外。
- 拥有运行状态的类型应从自身状态决定当前行为；不让调用方重复传入阶段、模式、保护状态等本可由被调用方判断的控制参数。

## 2. 决策局部性

- 一项业务决策、配置解释、不变量或普通失败只能有一个责任位置。下游直接依赖已经建立的结果，不重复判断同一事实。
- 调用方表达业务意图，不编排被调用模块内部必须按顺序执行的步骤。若多个调用方需要知道相同步骤、配置含义或失败处理，把这些知识收回拥有该决策的模块。
- 配置在唯一消费位置解释为业务含义。不要让调用方共同理解 Luban 字段组合，也不要在多个位置把同一枚举、掩码或数值重新映射为业务规则。
- 对象创建时已经确定、并在该对象生命周期内保持不变的配置，由状态所有者在创建边界解释和保存；后续业务方法只接收本次调用的新意图或新事实，不让调用方反复传入所有者自己的规则参数。
- 配置解释与运行机制可以通过同一能力类型的创建方法和运行方法区分。只有单一创建用途的工厂、临时参数袋、同形配置副本或单字段结果包装，没有独立约束与消费者时合并；创建成功应满足可用契约，不把必须紧接执行的初始化步骤外借给调用方。多种创建来源或独立分发需求成立时再提取创建适配。
- 修改公开能力、状态入口、事件或配置解释时，检查本次改动及其受影响锥：全部直接调用方、状态修改入口、事件发布与订阅位置、作者源和唯一消费位置。不要扩大到无关模块。

## 3. 状态所有者与编排者

- 职责单一按“同一业务变化原因和一致性目标”判断，不按类的方法数、字段数或文件长度判断。一个类型可以拥有多种操作，但它们必须共同维护同一组状态、规则和不变量。
- 状态所有者同时拥有该状态的表示、修改入口、不变量和推进机制。属于某领域的队列、计数器、游标、随机状态、节奏和恢复算法不能因为总编排者拥有 Update 入口而上移。
- 编排者只拥有跨状态所有者的业务政策：阶段准入、调用顺序、事务提交、结果路由、胜负和取消边界。它可以调用领域运行对象并消费完整业务事实，但不重新解释其配置、维护其内部计时队列或执行其算法步骤。
- 调整某项领域规则时，如果必须同步修改编排者中的计数、队列、配置换算或分支，说明领域机制已经泄漏；应把机制收回状态所有者，再由编排者使用更小的语义入口。
- 一个局部业务事务可以有自己的编排者。例如批量处理能力可以拥有领取、处理及完成顺序，来源对象维护被领取对象的身份和有效性；总入口只决定何时开始及如何处理完成事实。消费者不读取来源内部集合来替它维护状态关系，局部流程也不因此把自身队列上移到总入口。
- 普通运行对象可以是有状态的深模块。只有需要 JulyArch 定位、框架生命周期或独立更新入口时才提升为 System；提取普通类型不等于增加业务模块或 JulyArch 角色。

## 4. 深模块与内部类型

- 接口是调用方正确使用模块必须知道的全部信息，包括签名、不变量、顺序、失败和性能约束，不等同于 C# `interface`。优先让少量稳定语义入口隐藏完整实现，使调用方获得高杠杆、维护者获得局部性。
- 类型不能只做同名转发、字段搬运或把内部步骤重新暴露给调用方。删除检查关注隐藏的知识是否重新泄漏：即使只有一个调用方，只要类型集中拥有规则、算法、局部状态或实例生命周期，并减少调用方必须理解的细节，也可以保留；应评价完整职责，不因某个业务入口委托内部算法就判定整个类型无价值。
- MDD 锁定职责、公开契约、JulyArch 角色、状态和主要文件，不锁定私有方法、辅助字段及内部实现分解。
- 实施阶段可以在目标 MDD 已授权的模块和职责范围内创建普通类型及对应文件，用于集中已授权的规则、算法、转换或局部运行态；文件放在该模块现有目录或 MDD 主要类型的相邻业务目录，不得借此新增业务职责、跨 MDD 契约、JulyArch 角色或跨模块依赖。
- 每个新增内部类型都执行删除检查：删除后若规则、算法或状态管理会泄漏到调用方、混入无关职责或散落到多个位置，则保留；若只是搬回少量转发或字段且不增加理解成本，则删除或合并。调用方数量不是成立条件。
- 访问级别只服从 C#、Unity、Framework、序列化、程序集边界和项目既有约定；同一程序集内不把 `private`、`internal` 或 `public` 的选择当作解耦手段或质量评分。不要为了制造只读隔离而新增接口、门面、包装或逐项转发层。接口质量按调用方必须知道的业务规则、内部步骤和状态修改责任衡量：可以直接持有职责合理的具体运行对象，但不能被迫编排其内部算法、重复解释规则或修改不属于自己的状态。
- 对每个跨 MDD 契约执行契约闭包：从构造函数、方法、属性和事件载荷出发，递归展开其中每个项目自定义类型，直到基础类型、生成类型、Framework 类型或已经核实且签名不变的现有类型。闭包内写清构造方式、可读成员、可变性和合法状态组合；只有可见性会影响 Framework、Unity、序列化或程序集边界时才把它作为契约要求。不能用“包含”“至少包含”“等”“保持现有语义”让实施者猜测类型形状。辅助实现结构不进入契约闭包。
- 每个结果或事件类型都必须有当前范围内的真实消费者，并说明其需要的事实与消费时机。可以查询当前值不等于可以删除变更通知：刷新触发、逐次过程或某次操作的固定结果都有独立语义。只重复当前可查询状态、没有独立通知或结果语义，或者无人消费的载荷与包装才删除；拉取与事件按正确性和成本选择。
- 使用 `Kind` 或枚举区分结果形态时，构造契约必须排除无效字段组合；不要用一组可空值、默认值或互斥字段组成无法证明合法的字段袋。
- 接缝放在真实协作知识处，而不是每个类之间。内部确定性算法优先使用具体类型；当消费者确实只应掌握有限操作、需要隔离外部依赖或已有多种实现时，可以建立小接口。单一实现不自动否定有限能力契约，第二个实现也不自动证明需要抽象；接口必须隐藏状态表示、操作协议或实际变化，而非复制整个类的成员。
- 不因“可测试”“解耦”或“以后可能替换”扩大生产接口。可测试性来自真实业务接口、显式依赖、确定性输入和可观察结果，而不是测试专用门面、读取快照或逐类接口。

### 协作形式与有效期

| 需要协作的知识 | 默认形式 | 应明确的契约与反例 |
|---|---|---|
| 同进程的确定业务行为 | 直接调用具体入口 | 明确先后与失败；不用事件订阅顺序完成必需步骤 |
| 本次计算完成后的事实 | 值或语义结果 | 足以驱动消费者，不让消费者按来源类型补推规则；不是整份运行态副本 |
| 仅本次操作需要的实时信息 | 参数或查询委托 | 在操作中按需调用，不默认存为字段；复杂交互协议不塞进一组无语义委托 |
| 多个相关操作或持续有效的使用权 | 有限能力接口，必要时返回操作对象 | 谁持有身份与状态、是否固定选择、何时耗尽或失效；不暴露来源的全部集合和修改步骤 |
| 用户或系统的请求 | 命令语义的方法 | 需要排队、回放或传输时再将命令建模为数据，不默认引入命令总线 |
| 已提交且需被观察的事实 | 返回事实或提交后事件 | 不参与本次提交成败；最终状态无法还原且必须保留的过程才需要缓冲 |

这些形式可以组合。依赖的传入时点按有效期选择：稳定且与能力同生灭的依赖可在创建时保存；当次输入和临时查询在操作时提供。业务计划须说明能否跨状态变化继续使用；跨异步等待、并发修改或动态规则时，不能沿用仅在同步调用期间成立的有效性假设。

## 5. 已确认扩展

- 只为 GDD、模块设计或当前代码明确记录的变化设计局部性。MDD 应说明当前切片需要保持的已确认变化，但不为模糊未来预建接口、空角色、注册表或兼容分支。
- 区分参数变化、既有契约内的新行为和突破契约的新语义：分别通过配置、新实现、修改模型及消费者完成。内容、资源与验证随之改变可以合理；若多个消费者需要重新推导同一规则，才是知识泄漏，不能仅按改动文件数判断。
- 同一种功能的参数解释、定义构建与执行规则优先集中维护。不同阶段不自动要求独立模块；公共流程负责输入归集、通用结构和跨规则约束，不复制每种规则的专有判断。
- 多处按同一业务类型分派已经形成同步维护时，可使用局部、显式的单一登记点，将类型绑定到相应处理器。只有少量封闭分支时保留 switch；不默认采用反射、自动发现或统一生命周期接口。
- 扩展点写清接纳的新行为范围。状态变化、规则组合、冲突优先级或计划失效超出当前契约时，允许修改公共模型；不能承诺所有新行为永远只新增一个类。静态规则处理器若共享，运行状态必须保留在实际所有者中。

## 6. 时间推进与事件进度

- 需要严格同刻优先级的业务运行单元，使用一个明确的时间与推进入口；不要让同一事务的业务优先级依赖多个 `IUpdatableSystem` 的注册顺序。回合制可以直接按行动推进，互不相关的长期能力不必共享一个全项目时钟。
- 固定 Tick、物理步、业务时长或外部完成信号由产品语义选择。采用固定 Tick 时，内部能力可以接收“推进一个 Tick”，并完整拥有自己的速度换算、队列和到期规则；需要其他时间事实时明确单位、来源、暂停与消费语义，不把“查询所有模块下一事件后切片”默认设计成通用调度协议。
- 唯一时间入口不等于唯一时间机制所有者。System 可以同时负责 Framework 时间适配和跨能力优先级，各能力保留自己的推进机制；职责区分不要求再创建总运行对象。时间方案按产品选择，不把固定频率或 Tick 提升为所有项目的骨架要求。
- 生命周期内不变的速度、时长和间隔在创建边界由真正消费它的状态所有者解释并保存。编排者不替其他模块把配置换算为距离、Tick 或到期队列。
- 每次推进必须完整处理该业务步内的状态变化和待提交事实，不能用任意最大迭代次数、静默丢弃事件或跨模块时间协商掩盖漏事件与不推进。若一个领域步需要在跨模块事务后继续，接口应表达业务上的暂停与继续事实，不能泄漏通用剩余时间调度器。
- 同一业务时刻存在多个事实时，由拥有业务优先级的唯一编排者规定稳定顺序。单次推进返回一个事实还是一批事实都可以，但返回结构必须完整表达约定的同时语义；不要用互斥枚举假装表达实际可能同时发生、且没有规定拆分顺序的多个结果。
- 期限、持续时间或时间戳有真实消费者时可以成为业务输入；不能为形式统一禁止有意义的时间参数，也不能把宿主帧时长无差别透传给每个能力。表现动画、异步等待和资源超时由各自责任位置管理。
- 每个持久阶段都必须改变准入、推进、失败或可观察结果，并有明确进入与结束事实。若一个阶段只在同一同步调用栈内被设置后立刻离开、没有消费者能观察且没有独立待处理事实，用一次结果或阶段转换表达，不保存没有生命周期的瞬时状态。

### 表现更新与业务时间

- 权威运行态决定业务事实，表现层拥有实例、当前位置和动画进度等局部状态；除非产品契约明确要求，动画完成回调不决定业务完成。
- 实例生灭与跨归属交接集中管理，各种表现的参数、规则和动画状态归对应功能。View 可以保留生命周期和帧顺序编排，不要求额外总 Presenter，也不强制每个私有步骤成为独立类型。
- 对象对齐与动画推进是不同职责，但不强制拆成两套接口或缓存目标。运行态不变时动画仍可推进；重复读取同一状态不重建实例或重置进度。
- 使用当前状态自我对齐时，明确首次建立、归属迁移和清理的行为。若业务要求展示渲染帧之间的每次短暂事实，再设计必要的表现事件；不能假设最终状态可以还原完整过程。

## 7. 校验、失败与资源保护

默认采用“边界验证、内部信任、违约快速失败”。每项校验必须能够说明具体故障来源、不校验的业务后果和触发后的规定行为。

只在以下情况增加保护：

- 用户输入、网络、文件、存档、设备数据或第三方接口等不可信边界；
- GDD 允许的普通业务失败，并且调用方需要依据结果继续；
- 非法值不会自然失败而会继续产生错误结果或污染权威状态；
- 资源释放、取消、幂等性或原子提交确实要求保护。

配置经过生成不等于业务语义一定合法。对会在自然失败前继续污染运行态的非法枚举、非有限时长、重复顺序、缺失引用或跨表关系，在最接近运行态建立的唯一责任位置验证；已有表查询或类型约束会在任何状态修改前明确失败时，不重复扫描或预校验。MDD 不使用“自然失败”概括未经当前真实代码确认的行为。

为某个位置分配校验责任前，必须确认该位置通过现有或本次明确设计的依赖能够取得全部必要事实，并写明具体来源。跨表、配置与地图、配置与资源等一致性校验只有在同一责任位置能访问两侧事实时才成立；事实不可达时，只能在既定职责和依赖方向内调整责任位置或传入最小业务事实，不让调用方先解释规则。若必须改变模块依赖或决策所有权，进入设计修复；不得写下无法实施的校验承诺。

模块内部已经由类型、构造流程、上游判定、Framework 生命周期或调用契约保证的条件不重复检查。内部违约应直接访问、断言、抛出有意义的异常或自然失败；不用 `TryXxx`、`false`、默认值、空集合、静默返回或日志后继续执行来伪装恢复。

不捕获异常只为替换错误文本，不在写入后扫描完整状态，不为普通读取复制快照，不用宽泛重试或兼容分支隐藏设计错误。资源保护和候选提交失败清理不属于过度防御，但必须只存在于拥有资源或事务的责任位置。

同步连续修改不自动具有异常回滚能力。若当前宿主会捕获异常后继续调用，而中断可能留下部分提交，生命周期拥有者应使受影响运行实例失效并保留原异常，阻止继续推进；不要在各内部方法重复捕获或默默恢复。是否保留旧状态、丢弃运行实例或执行补偿由明确的数据保护要求决定，不为所有项目机械增加 Faulted 状态或通用事务框架。

## 8. 行为可解释性与验证

- 主调用路径应能直接回答：接收了什么业务意图、由哪个状态所有者作出决定、产生了什么业务事实或状态变化，以及调用方依据什么结果继续。不要用泛化方法名、散落字段写入、隐藏回调或无所有者的异步任务掩盖这条因果链。
- GDD 或 MDD 已定义持久阶段时，进入和结束必须通过拥有该状态的唯一责任位置表达；转换代码应使用业务语言说明目标阶段与触发事实。不要为了形式统一强制创建状态类、状态机或 Procedure，也不要把只有一次同步调用栈的瞬时步骤保存为阶段。
- 已有日志、异常或项目诊断入口在报告真实边界失败、普通业务失败或内部违约时，应携带定位该事实所需的最小稳定上下文，例如业务标识、当前阶段、触发意图或失败资源；不转储整份运行态，不复制读取快照，不捕获异常只为改写文本。
- 只有 GDD、MDD、已知缺陷、历史事故或明确诊断需求证明运行轨迹必须跨调用保留时，才增加最小、有界且由状态所有者维护的诊断记录。诊断记录不成为第二份权威状态，不参与业务决策，不通过事件、公开接口或跨模块时间协议扩散；若需要改变公开契约、模块职责或 JulyArch 角色，进入设计修复。
- 可解释性优先来自准确业务名称、唯一决策位置、显式状态转换和稳定执行顺序。不得为了“方便排查”普遍增加日志、事件、Result、Snapshot、包装层或调用链透传字段。
- GDD 允许的业务拒绝若调用方只需知道接受或拒绝，可以使用 `bool`；调用方必须区分多个合法业务结果时，使用能排除非法组合的语义结果类型。不要用通用 `Result<T>`、错误文本或一组互斥可空字段代替业务建模，也不要强迫领域方法自行记录所有普通拒绝日志。
- 验证强度与改动风险匹配：优先覆盖核心规则、数据一致性和复杂状态转换，不为低风险改动机械增加测试，不以测试数量或覆盖率替代质量判断。用户对本次验证的明确限制优先，报告实际未验证部分，不把单次“不需要测试”固化为长期免验证规则。
- 测试与调用方穿过同一接口。优先验证状态转换、确定性、事务原子性、事件顺序和边界失败；不要断言私有方法、内部集合形状或纯实现步骤。
- 新增或修改确定性核心规则时，若项目已有测试基础设施，或者可以在不增加生产接缝的情况下建立测试，应创建或更新自动化测试。若无法自动化，MDD 必须写明可执行的替代验证入口和无法自动化的具体原因，不能只写“编译通过”。
- 测试代码可以构造普通运行对象及其真实依赖。不得为了测试把生产成员改成 `public`，也不得增加项目级接口、快照、Mock 专用入口或第二份权威状态；项目使用独立测试程序集时，可以按既有约定通过测试 asmdef 或 `InternalsVisibleTo` 访问原本就构成模块接口的 `internal` 业务入口，但不能借此测试私有实现步骤。

## 9. MDD 约束

MDD 只明确：职责边界、状态与机制所有权、编排责任、公开语义、跨 MDD 契约、GDD 定义的失败、不可信输入边界、资源一致性要求、验证路径和已确认变化。

MDD 不规定私有方法、辅助字段、内部集合实现、重复的不变量检查、没有恢复行为的异常包装，或只为看起来可扩展而存在的类型。验收标准验证可观察业务结果、公开契约、边界拒绝、确定性、事务顺序、资源行为、生成和编译，不把内部实现步骤写成固定答案。

## 10. 实施质量闭环

功能实现和首次编译完成后，重新读取磁盘上的实际 diff，并执行：

1. 沿主调用路径检查业务意图是否可以从名称与控制流直接读出；
2. 对每项业务判断、配置解释和失败判定确认唯一责任位置；
3. 对每个新增类型、结果、事件、跨 MDD 入口和间接层执行删除检查，完成契约闭包，并确认模块接口足够深、调用方只需知道完成自身职责所需的业务语义；不以访问级别替代边界判断；
4. 对每个业务模式布尔参数、重复传入的所有者配置、校验、`TryXxx`、`catch`、默认值、集合复制和生命周期守卫核对真实故障、事实可达性与处理依据；
5. 对当前功能或已确认变化选择一个具体修改场景，检查需要阅读的实现与契约：规则、参数解释和局部状态是否集中，是否必须理解无关功能，跨功能协作是否只有少量明确契约；不为假想变化创建扩展点；
6. 检查受影响锥，确认调用方没有获得新的内部知识或承担不属于自己的状态修改；特别检查编排者是否持有其他状态所有者的队列、计数器、配置换算或算法步骤；涉及时间或行动推进时确认需要严格顺序的运行单元有明确入口、推进机制仍在各自所有者、同时业务事实顺序唯一且每个持久阶段都有真实生命周期；
7. 对受影响的持久阶段与跨帧流程，确认业务意图、决策所有者、状态转换原因和结果消费可以沿主调用路径追溯；核对已有日志、异常与诊断入口是否只携带定位真实失败所需的最小上下文，且没有为诊断擅自增加测试接缝、读取快照、事件中转或第二份权威状态；
8. 按 MDD 验证路径创建或更新必要测试并执行；没有自动化入口时执行已声明的替代验证，记录实际覆盖与限制；
9. 删除不能证明必要的分支、包装、复制、接口、事件和中间类型，再次生成、编译并执行受影响验证入口。

如果质量问题只能通过改变公开契约、业务决策所有权、模块职责或 JulyArch 角色解决，停止代码修改并进入 `design-repair.md`。纯私有实现组织问题在当前实施范围内直接修正。

测试资产属于验证范围，不属于产品功能扩张。只创建覆盖当前 MDD 行为所必需的测试、Fixture 和测试 asmdef；不创建生产 Mock/Fake，不为测试便利改变生产设计，也不得把未执行的验证描述为通过。
