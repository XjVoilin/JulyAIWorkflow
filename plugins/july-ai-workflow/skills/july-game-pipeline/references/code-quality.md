# 代码质量与实现结构

本规范只约束 MDD 的代码契约和实施质量。模块边界、业务决策所有权与已确认扩展由 `module-design.md` 决定，JulyArch 角色由 `july-architecture.md` 决定；本文件不重新分配它们。

质量优先级固定为：产品行为正确，状态所有权与数据一致性，简单直接和可读，已确认变化的局部性。不得为假想变化牺牲前三项。

## 1. 可读性与直接性

- 代码使用 GDD、模块设计和 MDD 已建立的业务语言；名称表达业务事实、决策或动作，不使用 `Manager`、`Helper`、`Processor`、`HandleData` 等无法说明职责的泛化名称。
- 方法主线保持同一抽象层级。协调方法表达业务步骤，具体算法和转换留在拥有该知识的普通类型或私有方法中；不把资源操作、业务解释和表现提交混在同一段控制流里。
- 分支必须对应业务情况、真实边界失败、资源一致性或内部不变量违约。不要把理论上的 `null`、重复、顺序错误或未来兼容写成普通分支。
- 注释解释约束来源、非显然原因和取舍，不复述代码。能够用准确名称表达的内容不增加注释。
- 不以行数、字段数或方法数机械拆分类和方法。只在出现可独立命名的知识、决策、算法或生命周期时拆分。
- 不用布尔参数切换互不相同的行为；调用方有不同业务意图时使用不同语义入口，纯内部且含义明显的局部开关除外。
- 拥有运行状态的类型应从自身状态决定当前行为；不让调用方重复传入阶段、模式、保护状态等本可由被调用方判断的控制参数。

## 2. 决策局部性

- 一项业务决策、配置解释、不变量或普通失败只能有一个责任位置。下游直接依赖已经建立的结果，不重复判断同一事实。
- 调用方表达业务意图，不编排被调用模块内部必须按顺序执行的步骤。若多个调用方需要知道相同步骤、配置含义或失败处理，把这些知识收回拥有该决策的模块。
- 配置在唯一消费位置解释为业务含义。不要让调用方共同理解 Luban 字段组合，也不要在多个位置把同一枚举、掩码或数值重新映射为业务规则。
- 对象创建时已经确定、并在该对象生命周期内保持不变的配置，由状态所有者在创建边界解释和保存；后续业务方法只接收本次调用的新意图或新事实，不让调用方反复传入所有者自己的规则参数。
- 修改公开能力、状态入口、事件或配置解释时，检查本次改动及其受影响锥：全部直接调用方、状态修改入口、事件发布与订阅位置、作者源和唯一消费位置。不要扩大到无关模块。

## 3. 深实现与内部类型

- 优先让少量稳定语义入口隐藏完整行为。公开入口不能只是同名转发、字段搬运或把内部步骤重新暴露给调用方。
- MDD 锁定职责、公开契约、JulyArch 角色、状态和主要文件，不锁定私有方法、辅助字段及内部实现分解。
- 实施阶段可以在目标 MDD 已授权的模块和职责范围内创建普通类型及对应文件，用于集中已授权的规则、算法、转换或局部运行态；文件放在该模块现有目录或 MDD 主要类型的相邻业务目录，不得借此新增业务职责、跨 MDD 契约、JulyArch 角色或跨模块依赖。
- 每个新增内部类型都执行删除检查：删除后若规则、算法或步骤会散落到多个位置，则保留；若只需搬回少量转发、字段或一次调用，则删除或合并。
- 访问级别只服从 C#、Unity、Framework、序列化、程序集边界和项目既有约定；同一程序集内不把 `private`、`internal` 或 `public` 的选择当作解耦手段或质量评分。不要为了制造只读隔离而新增接口、门面、包装或逐项转发层。接口质量按调用方必须知道的业务规则、内部步骤和状态修改责任衡量：可以直接持有职责合理的具体运行对象，但不能被迫编排其内部算法、重复解释规则或修改不属于自己的状态。
- 对每个跨 MDD 契约执行契约闭包：从构造函数、方法、属性和事件载荷出发，递归展开其中每个项目自定义类型，直到基础类型、生成类型、Framework 类型或已经核实且签名不变的现有类型。闭包内写清构造方式、可读成员、可变性和合法状态组合；只有可见性会影响 Framework、Unity、序列化或程序集边界时才把它作为契约要求。不能用“包含”“至少包含”“等”“保持现有语义”让实施者猜测类型形状。辅助实现结构不进入契约闭包。
- 每个结果或事件类型都必须有当前范围内的真实消费者，并说明消费者依据其中哪项事实作出业务决定、表现更新或集成动作。若消费者已经能从稳定实时状态得到所需信息，或者返回值无人使用，删除该结果、事件或字段。
- 使用 `Kind` 或枚举区分结果形态时，构造契约必须排除无效字段组合；不要用一组可空值、默认值或互斥字段组成无法证明合法的字段袋。
- 同进程的确定性算法直接使用具体普通类型，不为单一实现创建接口、Provider、Adapter 或策略体系。直接依赖稳定语义入口是正常协作，不需要用间接层消除。
- 不因“可测试”“解耦”或“以后可能替换”扩大生产接口、注入依赖或建立接缝。JulyArch 管理的 System、Store、Procedure 和 View 使用当前 Framework 的定位与生命周期方式。

## 4. 已确认扩展

- 只为 GDD、模块设计或当前代码明确记录的变化设计局部性。MDD 应说明当前切片需要保持的已确认变化，但不为模糊未来预建接口、空角色、注册表或兼容分支。
- 对每项已确认变化，新增一种情况时应主要修改拥有该决策的唯一实现位置和对应配置。若必须同步修改多个调用方，重新检查知识是否泄漏。
- 扩展点必须隐藏真实变化，而不是把 `switch`、步骤顺序或配置判断搬到不同类。只有出现两个真实生产实现、模块设计已明确授权当前范围内的第二实现，或者 Framework 明确要求时，才建立公开抽象。

## 5. 时间推进与事件进度

- 一次玩法会话的热路径只有一个跨模块时间入口：由拥有整体推进职责的 System 在 Framework 更新边界接收 `deltaTime`。时间不跨模块接缝；其他模块不接收或返回帧时间、剩余时间、下一事件时间或模块时钟，也不建立 `TimeToNextEvent` / `Elapse(deltaTime)` / `CompleteNextEvent()`、查询最小时间后分片推进等调度握手。
- 时间所有者模块内部如何积分、累计或离散时间属于实现选择，根据 GDD 的可观察语义、当前 Framework 和真实性能需要决定；可以直接连续推进，也可以使用固定 Tick，不把任一方案无条件固化为 MDD 或跨 MDD 契约。固定步长、速度和时长等生命周期内不变的规则在创建边界解释并由状态所有者保存。
- 时间所有者必须完整处理一次更新跨越的业务位置、状态变化和待提交事实，不能用缩小时间片、任意最大迭代次数、静默丢弃事件或跨模块时间协商掩盖漏事件与不推进。
- 同一业务时刻存在多个事实时，由拥有业务优先级的唯一编排者规定稳定顺序。单次推进返回一个事实还是一批事实都可以，但返回结构必须完整表达约定的同时语义；不要用互斥枚举假装表达实际可能同时发生、且没有规定拆分顺序的多个结果。
- 只有 GDD 明确把期限、持续时间或时间戳定义为需要跨模块消费的业务事实时，才在非热路径的业务查询、开始、提交或结束边界携带该事实；每帧或每 Tick 的模块推进仍不发送时间。表现动画、异步等待和资源超时不属于玩法模块间的时间推进协议，仍由各自责任位置管理。
- 每个持久阶段都必须改变准入、推进、失败或可观察结果，并有明确进入与结束事实。若一个阶段只在同一同步调用栈内被设置后立刻离开、没有消费者能观察且没有独立待处理事实，用一次结果或阶段转换表达，不保存没有生命周期的瞬时状态。

## 6. 校验、失败与资源保护

默认采用“边界验证、内部信任、违约快速失败”。每项校验必须能够说明具体故障来源、不校验的业务后果和触发后的规定行为。

只在以下情况增加保护：

- 用户输入、网络、文件、存档、设备数据或第三方接口等不可信边界；
- GDD 允许的普通业务失败，并且调用方需要依据结果继续；
- 非法值不会自然失败而会继续产生错误结果或污染权威状态；
- 资源释放、取消、幂等性或原子提交确实要求保护。

配置经过生成不等于业务语义一定合法。对会在自然失败前继续污染运行态的非法枚举、非有限时长、重复顺序、缺失引用或跨表关系，在最接近运行态建立的唯一责任位置验证；已有表查询或类型约束会在任何状态修改前明确失败时，不重复扫描或预校验。MDD 不使用“自然失败”概括未经当前真实代码确认的行为。

为某个位置分配校验责任前，必须确认该位置通过现有或本次明确设计的依赖能够取得全部必要事实，并写明具体来源。跨表、配置与地图、配置与资源等一致性校验只有在同一责任位置能访问两侧事实时才成立；事实不可达时，只能在既定职责和依赖方向内调整责任位置或传入最小业务事实，不让调用方先解释规则。若必须改变模块依赖或决策所有权，进入设计修复；不得写下无法实施的校验承诺。

模块内部已经由类型、构造流程、上游判定、Framework 生命周期或调用契约保证的条件不重复检查。内部违约应直接访问、断言、抛出有意义的异常或自然失败；不用 `TryXxx`、`false`、默认值、空集合、静默返回或日志后继续执行来伪装恢复。

不捕获异常只为替换错误文本，不在写入后扫描完整状态，不为普通读取复制快照，不用宽泛重试或兼容分支隐藏设计错误。资源保护和候选提交失败清理不属于过度防御，但必须只存在于拥有资源或事务的责任位置。

## 7. MDD 约束

MDD 只明确：职责边界、状态所有权、公开语义、跨 MDD 契约、GDD 定义的失败、不可信输入边界、资源一致性要求和已确认变化。

MDD 不规定私有方法、辅助字段、内部集合实现、重复的不变量检查、没有恢复行为的异常包装，或只为看起来可扩展而存在的类型。验收标准验证可观察业务结果、公开契约、边界拒绝、资源行为、生成和编译，不把内部实现步骤写成固定答案。

## 8. 实施质量闭环

功能实现和首次编译完成后，重新读取磁盘上的实际 diff，并执行：

1. 沿主调用路径检查业务意图是否可以从名称与控制流直接读出；
2. 对每项业务判断、配置解释和失败判定确认唯一责任位置；
3. 对每个新增类型、结果、事件、跨 MDD 入口和间接层执行删除检查，完成契约闭包，并确认调用方只需知道完成自身职责所需的业务语义；不以访问级别替代边界判断；
4. 对每个业务模式布尔参数、重复传入的所有者配置、校验、`TryXxx`、`catch`、默认值、集合复制和生命周期守卫核对真实故障、事实可达性与处理依据；
5. 对已确认变化检查修改是否集中在拥有该决策的位置；
6. 检查受影响锥，确认调用方没有获得新的内部知识或承担不属于自己的状态修改；涉及玩法时间推进时确认时间没有跨模块接缝、同时业务事实顺序唯一且每个持久阶段都有真实生命周期；
7. 删除不能证明必要的分支、包装、复制、接口、事件和中间类型，再次编译或执行项目已有验证入口。

如果质量问题只能通过改变公开契约、业务决策所有权、模块职责或 JulyArch 角色解决，停止代码修改并进入 `design-repair.md`。纯私有实现组织问题在当前实施范围内直接修正。

本流程不创建或修改测试、Mock、Fake、Fixture、测试 asmdef 或其他测试资产，也不为测试便利改变生产设计。可以运行项目已经存在的验证入口，但不得把未执行的验证描述为通过。
