# Stage: MDD

Use [../../assets/templates/MDD_INDEX.md](../../assets/templates/MDD_INDEX.md), [../../assets/templates/MDD_MODULE.md](../../assets/templates/MDD_MODULE.md), and [../../assets/templates/PROGRESS.md](../../assets/templates/PROGRESS.md). Use [../../assets/templates/RESOURCE_MANIFEST.md](../../assets/templates/RESOURCE_MANIFEST.md) only when several resource families, import/build paths, or an independent resource Gate justify a separate manifest.

## Outcome

Translate an approved GDD into a technical contract that can be implemented in dependency-safe vertical waves.

## Work

1. Inspect the target project's installed July packages at the exact manifest pins, composition root, registration and initialization order, Luban generator, assembly definitions, current directory conventions, and adjacent project code. Record source evidence for every concrete July type, method, overload, parameter, enum member and event named in MDD. Evidence must include the exact signature, immutable pin, source path, success semantics, and the consumer-observable failure/restore channel. A package entry, type name, log line, or successful-path method alone is not interface evidence. Audit whether every GDD-required failure state can actually be distinguished through the pinned public contract; if corruption, missing data, cancellation or initialization failure collapse into the same default outcome, the capability is not sufficient. Classify a reusable deficiency with [框架能力缺口 Gate](../framework-gap-gate.md) before designing a product substitute.
2. When the user supplies a mature project, or a verified adjacent July product exists, apply [参考项目校准](../reference-project-calibration.md). State excluded scopes, inspect representative non-excluded code, and record both adopted and rejected patterns with file evidence. A reference is evidence, not authority; never copy its historical debt merely because it shipped. This shared workflow and its templates must remain project-neutral: never add a concrete reference project's name, absolute path, domain vocabulary, module list, or adopted/rejected conclusion here. Put all project-specific evidence only in the generated target project's MDD or architecture-review artifacts.
3. Classify product complexity before decomposing it. Count independent gameplay states, persistent aggregates, content families, platform seams, editor/offline tools, UI flows, and release-only capabilities. Mark the product `small`, `medium`, or `complex`, explain the evidence, and choose document depth accordingly. Complexity determines analysis depth, not module count. More modules are not evidence of a better design.
4. Build a capability tree from stable business responsibilities and real change axes. A capability module normally co-locates its Store, System, Procedures, data, events and internal helpers under one capability directory. Window code may follow an established `Views/Windows/<Window>` convention, but generic `Runtime`, `Presentation`, `State`, or `Persistence` layers must not become product modules. Composition roots, generated code, build tooling and resource folders are topology, not business modules.
5. Run three concrete change-scenario locality tests before accepting module boundaries. For each scenario, list affected module documents and directories. A normal capability change should primarily touch one module plus explicit composition/config/resource files. If one change routinely crosses three or more capability modules because state, orchestration, persistence and presentation were split by technical role, deepen or merge them.
6. For each capability, decide whether its Implementation contains a JulyArch `Store`, `System`, `Procedure`, `View`, or only ordinary classes. Apply roles by semantics: Store for authoritative mutable domain state, System for initialized/shutdown long-running capability, Procedure for one bounded business narration, and View for Unity-bound presentation/interaction. Roles live inside capability modules; do not turn Store/System/Procedure/View into horizontal module layers.
7. Give every module one cohesive external Interface: callers, operations, inputs, outputs, nullability/optional-result contracts, invariants, ordering constraints, error modes, required configuration, performance characteristics and acceptance evidence. Mark only real boundary inputs and business-optional results as nullable; required collaborators and lifecycle-established state remain required. This is a conceptual Interface, not a requirement to create a C# interface, projector, port or wrapper for every class.
8. Keep Interfaces smaller than Implementations. Avoid one interface per class and avoid adapters without a second real implementation or test stand-in. Apply the deletion test and a pass-through test: a projector/manager/coordinator that only renames fields or forwards calls stays internal or is deleted.
9. Define authoritative Store ownership by consistency boundary. Prefer capability-scoped Stores and keep Store data/events/mutators with the owning capability. Do not aggregate unrelated settings, synchronization metadata, tutorial flags and gameplay state into one root merely to reduce Store count. If cross-Store atomicity is truly required, prove the consistency boundary or invoke the framework-gap Gate; do not expose a generic full-root replacement Interface to several modules.
10. Define each System lifecycle and dependency order. Define every Procedure's trigger, ordered business steps, commit point, idempotency rule, and success/failure event. Capability-specific Procedures should narrate the use case; generic procedures such as “commit arbitrary auxiliary state” are rejected unless they hide substantial reusable behavior behind a smaller Interface. Define every View's source and allowed intents; Views never become a second Store.
11. Keep the composition root thin. It selects adapters, configures framework Systems, registers capability roles and declares persistence. Content loading, navigation policy, fonts, HTTP policy and feature behavior remain in their owners. Document composition in the index; do not count it as a product capability module. Compare the target's current launch/registration code with the proposed topology line by line. Every required reorder or responsibility move must name the existing file, current behavior, target behavior, owning output and verification; do not document a desired order as though the target already implements it.
12. Derive directory and namespace topology from the target project and accepted reference patterns. Record the baseline and every deviation. Prefer `Assets/Game/Scripts/Modules/<Capability>` for capability code and the project's established Window/Editor/Generated conventions. Do not invent a product-name/layer directory tree without a locality benefit.
13. Treat an asmdef as a compilation/dependency enforcement seam, not a module folder. Start from the target/reference assembly baseline, state an assembly budget, and justify every added asmdef with a forbidden dependency, platform compile constraint, or measured compilation boundary. For every assembly, record the physical asmdef path, the source root it owns, nested asmdef/asmref exclusions, and dependency direction. Unity assigns a source file to the nearest ancestor asmdef; two sibling asmdefs in the same directory cannot partition descendants. Reject a topology whose documented file paths would compile into a different assembly than claimed. Do not create separate Runtime/Presentation/generated assemblies solely because those labels exist in the MDD.
14. Define Luban source tables and generation evidence only where configuration is required; then read [../luban-workflow.md](../luban-workflow.md). Group tables by content ownership, record keys and cross-table references, and show which capability converts generated rows into domain contracts. Existing July UI/localization tables remain owned by their framework Providers rather than a product-wide content wrapper.
15. Define dependency order and arrange tracer-bullet waves. Each early wave must produce an observable playable slice while preserving the final module seams; do not create temporary architecture that later has to be replaced.
16. Produce `索引.md`, each module document and `进度.md`. Set the index marker `资源清单` to `none` when resources fit in the index, or to `资源清单.md` when the separate manifest is justified. The index owns cross-module/composition evidence and package adequacy; each module owns its module-specific exact calls, so signatures are not copied between both. Apply document depth by the declared complexity: `small` uses the base index contract; `medium` also defines the capability tree, JulyArch topology, current-to-target delta, directories/assemblies and interface alignment; `complex` additionally proves change locality and physical Assembly ownership. Reference calibration is present only when a real reference project is used.
17. Before completing the Stage, audit: Interface producer/consumer alignment, change locality, dependency cycles, Store mutation authority, System initialization order, Procedure narration/commit points, View intent direction, adapter ownership, composition-root thinness, assembly budget, test surface, configuration ownership, and whether every GDD subsystem is owned by exactly one capability module.

MDD documents must be self-contained for implementation. They may cite the GDD version but must not replace behavior with “see GDD section X.”

## Failure conditions

Do not complete MDD when any of the following is true:

- concrete July calls are based on memory, another product, or an unpinned working tree rather than the target pins;
- an exact call table omits an overload signature, enum member, immutable pin, source path, or consumer-observable failure/restore channel;
- a GDD-required missing/corrupt/failed state is represented only by a log or collapses into the same default value as a valid state;
- a confirmed reusable July Framework deficiency is represented as product-owned infrastructure instead of blocking for framework completion;
- a provided reference project was copied without an explicit adopted/rejected evidence table or its excluded scope leaked into the design;
- this shared workflow or a reusable template contains a concrete product/reference name, absolute repository path, domain term, module list, or project-specific architecture conclusion;
- a complex product lacks a capability tree or JulyArch topology;
- a medium or complex product omits the topology and interface sections required for its declared complexity;
- a module is named after a delivery wave instead of a stable capability;
- gameplay state, orchestration, persistence and presentation for one change axis are split into horizontal product modules without passing the change-locality test;
- one module mixes unrelated gameplay, UI, platform, tooling, and release responsibilities without a cohesion proof;
- composition root, generated code, a generic technical layer or a release checklist is counted as a product capability module;
- multiple modules can mutate the same Store subtree without one declared authority;
- a Store root combines unrelated consistency boundaries or exposes full-root replacement to several capability modules without a proved transaction contract;
- a View directly owns recoverable domain state or mutates a Store outside a Procedure/declared Store interface;
- a generic Procedure only forwards arbitrary module data into persistence instead of narrating one bounded use case;
- an adapter has no second real implementation or test stand-in;
- a product adapter duplicates a responsibility already owned by a July package, or fills a reusable missing July contract without invoking the framework-gap Gate;
- the registrar/composition root contains feature behavior beyond selection, configuration, registration and persistence declaration;
- proposed initialization/registration behavior differs from the target but no current-to-target file delta and verification is listed;
- new asmdefs mirror conceptual layers rather than enforcing evidenced compilation dependencies;
- an asmdef path and its claimed source files do not obey nearest-ancestor physical ownership, or two same-directory asmdefs are expected to partition descendants;
- output files are listed without namespace, assembly, registration, ownership, and test contracts;
- the index and module documents duplicate the same exact call signatures instead of assigning one evidence owner;
- a separate resource manifest is generated without multiple resource families, import/build paths, or an independent resource Gate;
- a required collaborator or lifecycle-established internal value is designed as optional without a real failure source and specified recovery behavior;
- `[待确认]` changes architecture, state ownership, persistence, online/offline behavior, or required platform capability.
