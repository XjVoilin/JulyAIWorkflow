# View 工作流

用于 `UI视图` 与 `2D视图` MDD。View 阶段只构建表现合同和制作接线，不拥有领域规则。

## 1. 前置条件

- 用户明确要求生成或执行某个 View MDD；
- `MDD/Modules/` 下全部模块 MDD 都是 `已确认`，且每份都记录了实际角色产物与验证证据；
- 已实际查看用户指定的参考图、Prefab、场景和参考项目；
- 已检查固定版本 July UI、事件、资源和场景能力。

参考图存在时必须打开并观察布局、信息层级和交互元素，不能只读取文件名、尺寸或旁边的文字描述。参考图缺失或无法读取且会改变设计时停止并报告。

首次进入 View 阶段时，先从 GDD、参考资料和已确认模块整理完整 View 清单，区分 UI 与 2D，并更新 `骨架.md`。这份清单是 View 阶段的完整性依据，每个条目最终都必须有对应 MDD、实际产物和确认状态；清单用于避免遗漏和控制阶段，不提前设计玩家功能串联。之后按用户指定范围生成或实现具体 View MDD。

## 2. 先区分 UI 与 2D

选择 `UI视图` 的情况：屏幕空间窗口、面板、HUD、弹层、按钮、文本和列表，走项目标准 July UI Window/Prefab 路径。

选择 `2D视图` 的情况：世界或场景空间中的棋盘、摊位、顾客、环境、灯火、动画和可交互对象，使用普通 July/Unity View 与场景资源路径，不包装成 UIWindow。

一个视觉功能同时包含 UI 和 2D 时拆成两份 MDD，以类型化事件和数据合同组合。

## 3. 按稳定视觉职责拆分

一个 Window 或 View 只承担一个稳定视觉职责。需要拆分的信号：

- 同一个 Window 同时实现主界面、选择、营业、波次小结和整夜结算；
- 包含多套互斥页面状态和大量跨阶段按钮；
- 为了刷新一部分内容必须理解完整玩家流程；
- 视觉区域具有独立生命周期、数据源或复用价值。

共享同一屏幕不代表必须属于一个类。多个 Window、Widget 和 2D View 可以共同表达一个画面；具体玩家功能联通时再决定何时显示和刷新。

## 4. UI 合同：按真实职责使用 WindowData + Events + Window

每个 UI Window 都有 `Window`。其余职责按实际需要成立：

- `WindowData`：当 Window 展示业务、输入或异步结果决定的动态事实时必需，承载打开或刷新所需的完整只读展示数据；
- `Events`：当 Window 发布玩家意图或接收异步刷新时必需，包含玩家意图事件与携带新 Data 的刷新事件；
- `Window`：渲染，并在对应职责存在时读取 Data、订阅刷新或发布意图。

不得为了满足形式创建空 `WindowData`、空 Events 文件或永远不会触发的刷新事件。完全静态、无业务输入且无交互的 Window 可以省略不适用的 Data/Events；一旦展示动态事实或参与交互，就必须使用对应合同。

合同要求：

- 存在 `WindowData` 时，Window 通过项目标准方式取得初始数据；
- 存在刷新事件时，事件携带新的 `WindowData` 或明确的局部 Data，不发送空标记让 Window 回查业务对象；
- Window 不直接获取或持有业务 Store、System、Procedure；
- Window 不计算领域规则、不推进业务状态、不保存结果；
- 玩家输入只发布类型化意图；后续玩家功能联通由发起能力的自然角色调用模块并映射新 Data；
- Data 表达可见事实，不复制可独立修改的第二份领域状态。

命名遵循目标项目先例，不强制所有类型使用相同后缀；存在的职责必须分离，不生成没有实际职责的类型。

## 5. 2D 合同：ViewData + Events + View

2D View 使用对应原则：

- `ViewData`：场景表现由业务或异步结果决定时必需，承载完整数据快照；
- `Events`：存在交互意图、播放请求或异步刷新时必需；
- `View`：绑定场景对象、渲染、播放表现和发布意图。

纯静态场景装饰可以不生成空 ViewData/Events；动态或可交互 2D View 必须使用相应合同。

2D View 可以持有动画播放进度和临时选择等表现状态，但不能把规则结果、棋盘合法性、结算或存档变成自己的事实。动画完成事件只表示表现进度，不重新计算或更改业务结果。

## 6. 框架与制作校准

读取 [项目结构与框架能力校准](project-structure-calibration.md)，确认：

- July UI 的 Window 配置、provider、资源地址、打开/关闭和 Data 获取方式；
- Prefab、场景对象、序列化引用、字体、图集和输入接线规范；
- 参考项目中的一文件一角色粒度；
- UI 与 2D 间现有事件或组合路径。

已有标准路径时不得创建运行时 UIFactory、动态 RootView 或 ApplicationSystem。框架能力仅部分匹配时复用匹配部分，不让 View 适配不相关的生命周期。

## 7. 实现与验证

View MDD 可以修改对应 Data、Events、Window/View、Prefab、场景和制作资源接线；不得新增模块业务规则或跨页面完整流程，也不得生成测试代码。

至少记录：

- 实际查看的参考图和落实的信息层级；
- UI/2D 分类和拆分理由；
- 适用的 Data 字段、意图事件、刷新事件及发布者/消费者；不适用时说明该 View 为何确实静态或无交互；
- Prefab/Inspector 序列化引用检查；
- 目标分辨率、编辑器手工交互和 Unity Console 结果；
- 尚待玩家功能联通 MDD 接入的定向 TODO。

验证通过后状态为 `待人工审查`。只有用户确认视觉结构、职责和制作结果后才能进入 `已确认`。
