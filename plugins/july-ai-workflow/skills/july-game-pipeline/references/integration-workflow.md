# 玩家功能联通工作流

用于 `类型：玩家功能联通` 的 MDD。它记录和实现一项玩家功能如何使用已经确认的模块与 View。`Integrations/` 只是后期实施文档目录，不对应运行时代码层、同名类或统一协调框架。

## 1. 前置条件

- 用户明确指定要联通的玩家功能或行为范围；
- `MDD/Modules/` 下全部模块均已实现并确认，且每份 MDD 都记录实际角色产物和验证证据；
- `骨架.md` 完整 View 清单中的每个条目都有对应 UI/2D View MDD，且均已实现并确认；
- GDD 已明确玩家触发、业务结果、可见反馈和允许的失败行为。

依赖未确认时停止并列出缺项，不创建临时模块、假数据或适配层绕过门禁。

## 2. 先确定能力归属

联通前先回答：“玩家正在完成哪项项目能力提供的行为？”

优先把编排放入该能力已有角色：

- 一次有界异步操作或用例：Procedure；
- 长期能力、入口或生命周期：System；
- 模块状态变更：Store 的受控操作；
- 简单同步规则：模块普通类型。

允许这些角色调用其他已确认模块和 July 系统。跨模块调用只要服务于发起能力，就是正常实现，不需要再包装一层 ApplicationSystem、Manager 或 Facade。

如果找不到自然归属，依次检查：

1. 是否遗漏了一个可独立命名的项目能力；
2. 是否现有模块缺少合理的 Procedure 或 System；
3. 是否只是 View 内部表现顺序；
4. 是否真的需要一个独立而有界的协调对象。

新增模块责任或角色时，先退回对应模块 MDD 调整和确认；不要在联通 MDD 中悄悄改变模块定义。

## 3. 控制联通范围

一份联通 MDD 应有清楚的玩家意图和可观察结果，但不强制等于单个相邻状态转换。

适合放在一起的内容：

- 同一项目能力的一次完整操作；
- 共享一次提交或一次 Procedure 生命周期；
- 玩家会把它理解为同一个动作；
- 中途拆开会迫使多个地方共同理解同一编排。

需要拆分的信号：

- 包含多个可独立完成和确认的玩家目的；
- 跨越多个互不相关的项目能力；
- 出现多个独立提交点或长时间页面生命周期；
- 一个 Procedure/System 为了接线开始承担无关职责。

不要把“从启动到通关”作为默认范围，也不要为了追求极小而把一次自然操作机械拆成多个空接线步骤。

## 4. MDD 内容

联通 MDD 至少记录：

| 项目 | 内容 |
| --- | --- |
| 玩家行为 | 玩家想完成什么以及从哪里触发 |
| 发起能力 | 负责这项行为的模块 |
| 承载角色 | 具体 System、Procedure、Store 操作或普通类型 |
| 参与模块 | 被调用的已确认模块及其职责 |
| 参与 View | UI/2D View 及展示责任 |
| 数据映射 | 模块事实如何形成 WindowData/ViewData |
| 意图与刷新 | View 发布的意图和接收的数据刷新 |
| 业务结果 | 成功及 GDD 已定义的失败结果 |
| 完成标准 | 玩家可观察的终点和验证路径 |

不要在文档中重新解释模块内部算法或复制 View 视觉规格。

## 5. 实现允许范围

允许：

- 在发起能力现有角色中补充本功能实际需要的行为；
- 调用其他已确认 Store、System、Procedure 或普通规则；
- 创建属于发起能力的一次有界 Procedure；
- 将模块结果映射成 WindowData/ViewData；
- 打开、关闭、组合和刷新已确认 View；
- 发布类型化玩家意图、模块事件和携带 Data 的刷新事件；
- 清除已经完成的定向 TODO。

禁止：

- 创建项目级统一协调层、ApplicationSystem、总 Manager 或转发 Facade；
- 让 Window/View 计算业务规则或直接维护第二份业务状态；
- 为页面方便改变模块事实或伪造默认结果；
- 把新的长期状态、持久化语义或独立能力藏在联通代码中；
- 生成目标项目测试代码。

Window/View 是否可以直接使用框架能力按目标项目先例校准；业务状态和行为仍由模块角色负责。优先使用类型化意图与携带 Data 的刷新，不让 View 自己重新推导领域结果。

## 6. 反馈调整

联通过程发现以下问题时停止扩展当前实现：

- 模块职责重叠或缺失；
- 需要新增 Store/System 等长期角色；
- View 拆分无法承载实际交互；
- 配置或存档所有权与原 MDD 不一致。

把对应 MDD 退回 `可实现`，完成调整和人工确认后再继续联通。已确认产物不是永久冻结的，但不得用兼容层保留错误结构。

## 7. 验证与交付

至少验证：

- 产品程序集编译和 Unity Console；
- 从声明入口手工完成玩家行为；
- 模块状态、业务结果和 ViewData 来自同一事实；
- GDD 允许的失败不会推进为伪成功；
- 编排位于自然的项目能力角色中；
- 没有新增统一协调层、无意义转发、View 业务规则或测试代码；
- 已完成的 TODO 已清除，剩余事项有明确归属。

把实际承载角色、参与模块、数据映射、差异和手工路径简洁写回 MDD。通过后更新为 `待人工审查`，等待用户确认。
