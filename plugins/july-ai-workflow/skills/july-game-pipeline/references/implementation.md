# 单个 MDD 实施规范

本规范只约束“按照用户指定的一份 MDD 实施”这一动作。当前 MDD 是本次功能范围的唯一授权来源。

## 1. 实施前检查

实施前必须：

1. 确认用户明确指定了且只指定了一份 MDD。
2. 阅读目标 MDD、MDD 索引、目标 MDD 声明的前置依赖，以及当前相关代码。
3. 按需核对当前项目实际使用的 JulyFramework、JulyArch、UI 组件和 Luban 接口。
4. 判断目标 MDD 是否足以确定本次职责、角色、接口、状态与配置改动。

不要读取其他项目的产品文档，也不要扫描项目中的说明类 Markdown 文件来补充需求。

出现以下情况时停止实施并说明原因：

- 找不到目标 MDD；
- 同时指定了多份 MDD，无法判断本次唯一目标；
- 目标 MDD 所在的前置依赖关系存在循环；
- 目标 MDD 的必要前置依赖尚未实现；
- 目标 MDD 存在会改变职责、角色或公开契约的关键歧义；
- 当前代码与 MDD 冲突，且无法在不改变 MDD 设计的前提下适配。
- 目标 MDD 要求创建项目级 `IXXSystem`、静态业务容器、成功失败 `Result` 包装或没有明确边界的数据快照；此时应先更新 MDD，不能在实施时静默改写设计。
- 目标 MDD 明确要求把产品运行时代码放入顶层 `Systems`、`Stores`、`Procedures` 或同义角色目录；此时应先更新 MDD。
- 目标 MDD 会使同一业务模块出现第二个项目业务 System 或 Store，或者要求建立项目业务 ConfigSystem、ContentSystem 或配置聚合入口；此时应先更新 MDD。
- 目标 MDD 的模块无法说明一个明确业务职责，或其 System、Store 与模块职责范围不一致；此时应先更新 MDD。
- 目标 MDD 要求新增不符合 `<中文业务名>_<英文标识>.xlsx` 的 Luban 业务作者源 Excel；此时应先更新 MDD。Luban 控制文件不适用该规则。

## 2. 唯一功能授权

只实现目标 MDD 明确描述的功能。

- 只创建或修改目标 MDD 列出的职责、类型、接口、状态、配置和文件。
- “不涉及”部分是明确边界，不得越过。
- 不得因为其他 MDD 尚未实现，就在 Store、System、Procedure、Window、WindowData、GameView 或普通类型中臆想其功能。
- 不得顺手补齐未来可能需要的按钮行为、状态、事件、流程、配置字段或兼容分支。
- 可以修改已经存在的类型，但必须是目标 MDD 明确声明的扩展；不以所谓类型所有权阻止合理扩展。

若实施过程中发现确实需要目标 MDD 未声明的新职责、跨模块契约或角色，应停止并建议先更新 MDD，不直接扩展实现范围。

## 3. 角色必须服从 MDD

MDD 生成阶段已经决定 Store、System、Procedure、Window、WindowData、GameView 与普通类型的职责。实施阶段不得删除、合并、替换或绕过这些角色。

- 当前 Procedure 即使只执行一个步骤，也应保留 MDD 指定的角色和调用关系。
- Window 通过 System 发起业务动作；System 根据 MDD 编排 Procedure。
- Store 只通过具有业务语义的方法改变状态，不向外暴露任意写入口。
- 普通类型承载不属于 JulyArch 角色的局部职责。

具体角色边界遵循 [july-architecture.md](july-architecture.md)。

### 3.1 代码形态

- System 直接实现为项目具体类型，不额外创建对应的 `IXXSystem`；当前 Framework 强制要求的框架接口除外。
- 不创建静态工具类、静态管理器或静态业务入口；静态类只用于纯常量或语言、Unity、Framework、生成器硬性要求。
- 普通可失败操作返回 `bool`，并在负责判定失败的函数内部记录日志；不创建只承载成功状态、失败原因或错误文本的 `Result`。
- 结算数据等 GDD 定义的真实业务计算产物可以使用独立类型，不改成 `bool`。
- 不创建没有明确边界需要的 `XxxSnapshot`。WindowData、存档结构，以及 MDD 明确要求的回放、跨帧冻结或提交一致性数据不在此禁令内。
- 默认信任 Framework 生命周期、Luban 生成配置、模块内部调用契约和 Store 自己完成的受控修改。
- 不添加 `EnsureInitialized`、`EnsureConfigured`、写入后的 `ValidateState`、完整集合复检、重复空值检查或只为替换错误文本的异常包装。
- 错误会在真实使用位置直接暴露时让其自然失败。只有不校验会继续产生错误业务结果或污染权威状态，或者 GDD 明确要求处理和恢复时，才在唯一责任位置增加最小校验。
- 内部违约不使用 `false`、默认值、静默返回或日志后继续执行来隐藏错误。

### 3.2 代码目录

- 产品运行时代码按业务模块放入 `Assets/Game/Scripts/Runtime/Modules/<模块名>/`。模块围绕一个权威运行时状态及其行为，或者一个能够独立存在的无状态业务能力，不按技术层次、配置来源、JulyArch 角色或宽泛概念归组。
- 每个业务模块最多一个项目业务 System、最多一个项目业务 Store；出现第二个时停止并先调整模块边界，不把无关能力或状态强行合并。
- 模块、System 和 Store 的名称与职责范围必须一致；只做少量框架调用转发的目录或类型不构成模块。
- `Views`、`Generated`、`Shared` 等模板已有专用目录保持原有职责；Window、WindowData、GameView 和生成代码继续使用对应专用目录。
- MDD 已写明且符合上述规则的路径必须遵循；旧 MDD 未写路径时，根据类型的业务职责选择对应模块目录。

## 4. 前置依赖与延后集成

### 前置依赖

前置依赖是当前 MDD 无法正确实现时必须已经存在的能力。缺失时停止，不创建临时替代品，也不伪造成功路径。

### 延后集成

延后集成只用于：当前 MDD 自身职责能够完整实现并通过编译，但与尚未实现功能之间的连接必须以后完成。

每一项延后集成都必须同时满足：

1. 目标 MDD 已明确声明该关系；
2. `M999_项目集成收敛.md` 中存在对应条目；
3. 代码中的待连接点使用统一标记 `TODO(M999:Ixxx)`；
4. TODO 只代表跨 MDD 的连接，不代表当前 MDD 自身未完成。

不得用空实现、默认返回值、静默跳过、虚假数据或无依据的兜底隐藏当前 MDD 的缺失。

如果目标 MDD 已声明延后集成，而 M999 中缺少对应条目，可以补充或完善该条目；不得借此登记 MDD 未声明的新功能。

## 5. 实施 M999

只有用户明确指定 `M999_项目集成收敛.md` 时，才执行收敛实施。

开始前必须确认 M999 涉及的各 MDD 已经完成，并逐项核对当前代码和配置。M999 应作为一次完整收敛实施：

- 只连接 M999 已登记的关系；
- 清理对应的 `TODO(M999:Ixxx)`；
- 不新增产品功能；
- 不把缺失模块替换为临时实现；
- 任一必要模块缺失或契约不一致时停止，不提交部分收敛结果。

## 6. Window 与 View 代码

只要目标 MDD 包含 Window，就必须同时实现对应 WindowData。

- WindowData 默认通过当前 July 项目的查询接口从 Store 或 System 获取显示数据。
- WindowData 的字段保持可写，以便 GM 构造测试数据验证显示。
- Window 只根据 WindowData 渲染显示，并通过 System 发起业务动作。
- Window 不直接读取 Store，不在自身内部推导或保存业务状态。
- 复杂界面按独立 UI 区域拆为 GameView；GameView 使用自己的显示数据，并服从所属 Window 的组合关系。
- Window 类型名必须以 `UI` 开头、以 `Window` 结尾。对应 ID 统一写入 `UIWindowID` 纯常量静态类，字段名与 Window 类型名完全一致。
- 创建、重命名或删除 Window 时，同步修改 `UIWindowID` 和 Luban 作者源 `TbUIWindow`；常量值与表中 ID 必须一致，不创建其他 Window ID 类或运行时注册服务。
- 只编写代码和已有配置，不创建或修改 Prefab、Scene、图片、材质、动画、音频或美术计划。

涉及 UI 时同时遵循 [july-ui-components.md](july-ui-components.md)，以项目中的实际组件 API 为准。

## 7. Luban 配置

目标 MDD 涉及配置时：

1. 修改项目现有 Luban 作者源；
2. 新增业务作者源 Excel 时使用 `<中文业务名>_<英文标识>.xlsx`，英文标识沿用当前工程已有的大小写、前缀和单词分隔约定；
3. `__tables__.xlsx`、`__beans__.xlsx`、`__enums__.xlsx` 等 Luban 控制文件保持固定名称；已有业务作者源不因本规则自动重命名；
4. 使用项目已经存在的生成入口；
5. 将生成结果视为派生产物；
6. 不手工修改生成代码或生成数据来绕过作者源。

各业务 System 直接通过框架 `IConfigSystem` 获取本模块需要的表，不创建项目业务 ConfigSystem、ContentSystem 或配置聚合入口。已进入 Luban 的数值、名单、顺序、配额、文案和当前内容不在 C# 中以字面量重复表达或逐项核对。默认信任 Luban 生成配置，不做启动巡检、完整性扫描、范围预校验或引用复检；直接在实际业务代码中读取和使用。只有 GDD 明确要求处理配置异常，或者错误配置不会自然失败而会继续污染权威状态时，才增加决定该业务行为所需的最小校验。

如果找不到项目已有的作者源或生成方式，停止并说明缺失信息。

## 8. 编译与写后验证闭环

每份普通 MDD 实施完成后都必须达到编译通过，但不要求当前功能可见、可玩或形成完整闭环。

代码、作者源和生成产物写入后，必须：

1. 从磁盘重新读取目标 MDD、实际改动和受影响的公开边界，不依赖实施过程中的记忆；
2. 对照目标 MDD 检查职责、角色、状态所有权、公开签名、文件范围、前置依赖和 `TODO(M999:Ixxx)`，确认没有实施其他 MDD 的功能；
3. 对照当前 Framework、Luban 和 UI API 检查真实调用，确认没有配置巡检、生命周期守卫、写后全状态复检、重复契约校验、假实现或默认降级；
4. 涉及作者源时运行项目已有生成入口，并检查生成结果来自作者源；
5. 使用项目已有的编译或验证入口；不为本流程额外生成测试代码；
6. 本次改动导致的问题应在当前实施范围内修正，然后重新读取改动并再次验证；若失败来自缺失前置依赖或 MDD 契约冲突，则停止并报告，不擅自修改 MDD；
7. 不把未实际执行的生成、编译或验证描述为已经通过。

只有写后检查与实际可执行验证都通过，当前实施才算完成。

## 9. 完成报告

完成后简洁说明：

- 实施的 MDD；
- 创建和修改的主要代码或配置；
- 是否新增或完成 M999 条目；
- 实际执行的编译或验证结果；
- 尚未处理且明确属于其他 MDD 的内容。

不要把未实现内容描述为已完成，也不要自动进入下一份 MDD。
