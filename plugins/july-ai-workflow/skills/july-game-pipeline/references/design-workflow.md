# 完整设计流程

本流程把策划案转成当前版本可直接审查和实施的完整设计。设计动作必须先解决结构性问题，再写正式文档；不得一边生成产品代码一边补设计。

## 1. 输入与讨论边界

读取：

- `Design/Docs/策划案.md`；
- 已有 `GDD.md`、`MDD/索引.md`、模块 MDD 与 View MDD；
- 当前工程稳定宿主的程序集、启动组合、注册、UI、场景、资源与 Luban 作者源约定；
- 当前工程固定版本 July/Luban 的公开源码、示例与实际接口。

重新生成时，旧业务代码不证明模块、角色、接口、类型或目录是正确的。只可从旧工程中识别仍然有效的稳定宿主约束，不沿用旧业务设计。

在写文档前，与用户逐项讨论会改变以下内容的问题：

- 当前版本范围、玩家目标、核心循环和完成条件；
- 业务概念的含义、规则、输入、结果和允许失败；
- 完整玩家流程、分支、回退和玩家可见反馈；
- 业务事实的唯一权威来源；
- 模块责任、依赖方向和跨模块操作归属；
- 名称相似但触发、输入或提交点不同的原子玩家动作；
- 完整 View 清单、画面责任和交互入口；
- Luban 作者数据的字段含义和归属；
- 单份 MDD 的产品符号来源、编译闭包与可独立验收范围；
- 任何会改变文件、角色、公共接口或制作范围的选择。

只有用户明确推迟、且不会改变上述结构的内容可以记录为未决。讨论期间不要写仓库内决策草稿或临时状态文件。

## 2. 建立 GDD

`GDD.md` 只记录产品事实，至少包含：

1. 产品定位、当前版本范围和排除项；
2. 玩家目标与核心循环；
3. 统一业务词汇及每个概念的含义；
4. 静态内容和可调规则；
5. 运行时事实及玩家可感知变化；
6. 每条完整玩家流程的触发、步骤、成功结果、允许失败和反馈；
7. 全局约束与不变量；
8. 用户明确推迟的非结构性内容。

GDD 禁止出现类名、JulyArch 角色、代码目录、程序集、配置表结构、注册方式或实现伪代码。

## 3. 从玩家体验推导技术设计

对每条完整玩家流程按固定顺序分析：

1. 列出玩家能看到的事实；
2. 列出玩家能执行的动作；
3. 列出动作完成后哪些事实发生改变；
4. 指定每个事实的唯一权威来源；
5. 把流程拆成原子玩家动作，为每个动作指定唯一所有者、规范签名和导航所有者；
6. 列出需要展示或交互的 View；
7. 在所有权稳定后才选择角色、类型、接口和文件。

不要从类名或预想文件结构反推业务。一个完整玩家流程可以跨多个模块，但跨模块调用必须属于发起动作的业务能力，不创建独立“联通层”。

所有原子动作先进入 `索引.md` 的动作合同表。模块流程、公共接口和 View 交互只引用该动作 ID 与规范签名，不能各自重新发明同一动作。两个步骤即使都被策划案称为“开始”，只要一个负责打开选择页、另一个负责确认选择并提交业务，就必须是两个不同动作。

## 4. 业务事实所有权

在 `索引.md` 中先建立全局事实表，再设计任何产品类型：

| 业务事实 | 权威来源 | 写入者 | 读取者 | 派生方式/更新时机 | 禁止副本 |
| --- | --- | --- | --- | --- | --- |

权威来源只能是以下之一：

- Luban 作者数据；
- 某个 Store 的受控运行时状态；
- July 或 Unity 已提供的稳定运行时事实；
- 从其他权威事实即时派生的值。

同一事实不得同时存在于配置、Store、WindowData 和自定义 Definition 中。WindowData 是可写展示快照，不是第二业务权威。可由行数、枚举项、当前时间、起始时间或其他权威数据得到的值必须计算，不配置重复常量。

框架已经提供且语义匹配的时间、资源、UI、事件或生命周期事实直接作为权威来源，不创建项目内平行表示或转换包装。

## 5. 模块划分

模块表示稳定、可独立命名和维护的产品能力。模块不是：

- 玩家流程步骤或一张页面；
- Store/System/Procedure 等技术分层；
- 表格、DTO、枚举或 Data 的集合；
- `Common`、`Core`、`Content` 等宽泛容器；
- 为未来扩展保留的空抽象。

为每个模块说明负责内容、明确排除、拥有事实、公开动作、消费者和依赖。业务模块依赖必须无环，但这还不构成可实施设计：随后必须把全部 Module MDD、View MDD、Luban 生成符号、注册和制作依赖纳入 [设计闭包审计](design-closure-audit.md) 的全产物实施图。

全产物图出现环或某份 MDD 引用后续产物时，重新分配事实、动作、导航、符号或文件所有权。不得用事件、接口、字符串路由、占位类型或协调器隐藏循环。

玩家完整流程写进发起能力的模块 MDD，包含真实跨模块调用顺序、成功/失败结果和 View 反馈。

## 6. 类型与 JulyArch 角色

先确定责任，再命名类型。

- **Store**：拥有受控运行时业务状态。公开读取，限制写入；一致变更完成后发布空业务事件。
- **System**：通过 `ArchContext` 管理或定位的稳定运行时能力。实现可以简单，当前消费者可以只有一个。
- **Procedure**：一次有界操作，尤其多步骤、异步、可取消或需要明确提交点的操作。
- **普通类型**：拥有真实算法、不变量或值语义，不需要 JulyArch 生命周期。
- **Luban 生成类型**：直接表达静态作者事实。
- **View**：拥有 Unity 表现和交互。

每个候选产品类型都回答：删除它、让消费者直接使用现有 Store/System、Luban 生成类型或框架类型后，会损失什么独立行为、不变量、运行时所有权、生命周期或错误合同？没有损失就删除候选。

禁止创建只保存静态字段的 `Definition`、生成类型镜像、手写别名枚举、查表转发器、模块级空接口、Application/Manager/Facade 总协调器。

## 7. View 完整设计

完整设计阶段必须同时列出并设计当前版本全部玩家可见屏幕和视觉功能。View 按视觉责任建档到 `MDD/Views/`，不按 UI/2D 技术类别建立子目录。

每个 UI Window 强制拥有 WindowData，并遵循 [View MDD 模板](view-mdd-template.md) 中的数据、事件、按钮与导航合同。非 Window 的 GameView 是否需要 Data、采用何种刷新方式，由实际表现责任决定，不套用 Window 规则。

View 的每个玩家交互必须引用索引中的动作 ID。View 不得给同一业务动作声明另一套参数、失败结果或导航责任。View 使用的 System、生成类型、事件和资源都必须来自自身白名单或实施顺序中更早的 MDD。

## 8. Luban 设计

任何工作簿创建前，必须在所属模块 MDD 中把每个表、Bean、枚举设计到：

- 作者源位置与表身份；
- 字段名、类型、主键/索引、约束和含义；
- 每个值的业务所有者与消费者；
- 至少一个代表性作者数据示例；
- 生成类型及直接消费方式；
- 注册或加载入口；
- 全量生成与残留检查。

派生数量、覆盖计数和其他可计算值不进入配置。杂项配置只保存确实全局、可调、非派生且没有更窄业务所有者的作者值。

## 9. 实施闭包设计

在正式写文档前按 [设计闭包审计](design-closure-audit.md) 在内存中完成：

1. 全局动作合同表；
2. 产品符号唯一提供表；
3. 包含全部 Module/View MDD 的依赖边表和无环图；
4. 有效拓扑实施顺序；
5. 每份 MDD 的可用符号集合与独立编译证明；
6. 每份 MDD 不依赖后续验收产物的证明。

Module 与 View 可以在实施顺序中交错。不得默认先实施全部模块再实施全部 View。只有全图确定后才分配 M/V 编号；低编号不得依赖同类更高编号。

当前设计不接入已有持久化系统。Store 只描述运行期事实，不写保存/读取调用、跨启动恢复、保存失败、存档校验、持久化注册或占位接口。

## 10. 完整性审计

正式设计完成前检查：

- GDD 的每项当前版本责任都映射到模块和 View；
- 每个业务事实只有一个权威来源；
- 每个玩家动作都有唯一动作 ID、所有者、规范签名和导航所有者；
- 每个产品符号都有唯一提供 MDD；
- 全部 Module/View MDD 位于同一无环实施依赖图；
- 实施顺序是有效拓扑序，每份 MDD 只引用稳定宿主、自有或更早产物；
- 每份 MDD 实施后能够独立编译并完成自身验收；
- 所有跨模块流程都写在发起模块 MDD；
- 每个类型通过必要性审查；
- 每个角色符合 JulyArch 语义；
- 所有 Luban schema 已设计完整；
- 每个 View 都有数据来源、刷新、交互和制作合同；
- 每份 MDD 有精确文件白名单和可重复验收；
- 未包含持久化接入、保存/读取失败、跨启动语义、目标项目测试代码、流程状态或设计外占位项。

审计发现结构问题时继续讨论，不将其留给实施阶段猜测。

## 11. 一次性产物

完整设计动作最终创建或更新：

```text
Design/Docs/
├── GDD.md
└── MDD/
    ├── 索引.md
    ├── Modules/M001_<业务能力>.md
    └── Views/V001_<视觉功能>.md
```

索引记录经闭包证明的精确拓扑实施顺序，每一项是一份 MDD；它不授权自动续跑。设计动作不创建产品代码、配置工作簿、Prefab 或场景改动。
