# 完整设计流程

本流程把策划案转成一套可审查、可机械验证、可逐份实施的当前版本设计。正式项目在发布前保持不变。

## 1. 讨论期：项目零写入

读取策划案、已有设计、稳定宿主约定及固定版本 July/Luban 源码。重新生成时，旧业务代码不作为模块、角色、接口或文件设计的依据。

在写任何正式或暂存设计前，讨论完所有结构性问题：

- 当前版本范围、玩家目标、核心循环和完成条件；
- 业务概念、规则、输入、结果与允许失败；
- 全部玩家流程、分支、回退和可见反馈；
- 每个业务事实的唯一权威来源；
- 稳定业务能力边界与跨模块动作所有者；
- 原子动作的触发时机、输入、提交点、失败和导航所有者；
- 当前版本完整 View 清单；
- Luban 作者事实、字段归属和派生值；
- 每份 MDD 的文件范围、依赖、编译闭包和独立验收。

只有用户明确推迟且不改变上述结构的内容可以留待以后。讨论期间不得在项目内写草稿、状态或半成品 GDD/MDD。

## 2. 建立产品 GDD

GDD 只记录产品事实，至少覆盖：

1. 产品定位、当前版本范围与排除；
2. 玩家目标和核心循环；
3. 统一业务词汇；
4. 静态内容和规则；
5. 运行时事实与玩家可感知变化；
6. 每条完整玩家流程的触发、步骤、成功、允许失败和反馈；
7. 全局约束与不变量；
8. 用户明确推迟的非结构性事项。

GDD 不出现类名、JulyArch 角色、代码目录、程序集、配置 schema、注册方式或实现伪代码。

## 3. 先建立结构化合同

结构决定确认后，才读取合同、门禁与模板，并运行 [结构化设计合同](design-contract.md) 的 `create-stage`。脚本会把暂存区绑定到当前工作区、策划案摘要和 Unity 项目版本；该绑定只证明事务来源，不表示进度。在返回的系统临时目录中先创建 `.july-design-contract.json`，暂不生成 MDD 正文。

按以下顺序推导合同：

1. 从每条玩家流程列出可见事实、原子动作和变化结果；
2. 为每个事实指定唯一权威来源；
3. 为每个动作指定唯一 ID、owner、规范 signature、允许失败与 navigation owner；
4. 以稳定业务能力划分 Module，以玩家可见屏幕/视觉功能划分 View；
5. 选择 Store、System、Procedure、普通类型、Luban 生成类型和 View；
6. 列出每份 MDD 提供的跨 MDD 产品符号；
7. 列出每份 MDD 消费的产品符号与动作；
8. 建立全部 Module/View、Luban、注册、Prefab 和运行时合同边；
9. 消除循环并完成全局拓扑排序；
10. 按拓扑序分别分配连续 M/V 编号；
11. 为每份 MDD 固定准确路径和产品文件白名单。

模块不能承担 Editor 工具、验证、发布或生成管线职责。Luban 作者事实属于实际业务能力；生成检查属于实施验收，不是业务模块。

## 4. 事实与角色判断

权威来源只能是 Luban 作者数据、某个 Store 的受控运行时状态、July/Unity 的稳定事实，或从权威事实即时派生的值。

可由表行、枚举、July 时间、全局起始时间或其他权威值计算的数据不得再次配置。WindowData 是可写展示快照，不是业务权威。

每个候选产品类型必须证明：删除后会损失真实行为、不变量、运行时所有权、生命周期或错误合同。否则直接使用已有 Store/System、生成类型或框架类型。

- Store：受控运行时业务状态；
- System：由 ArchContext 管理或定位的稳定运行时能力；
- Procedure：一次有界操作；
- 普通类型：算法、不变量和值语义；
- Luban 生成类型：静态作者事实；
- View：Unity 表现和交互。

## 5. 生成顺序与批次门禁

从同一 `.july-design-contract.json` 生成文档：

1. GDD；
2. `MDD/索引.md`，并嵌入完整合同；
3. 带同一 `--workspace` 运行 `partial --surface staging` 验证；
4. 按 `implementationOrder` 生成 MDD，每批最多两份；
5. 每份 MDD 嵌入对应 Artifact 合同；
6. 每批后带同一 `--workspace` 运行 `partial --surface staging` 验证；
7. 全部生成后带同一 `--workspace` 运行 `full --surface staging` 验证。

批次只是控制单次写入规模，不能发布、不需要用户管理，也不改变外部只有两个动作的接口。任何中断都只留下系统临时文件，不能把部分文件复制进项目。

## 6. 语义审查

机械验证通过不代替设计判断。发布前仍要逐份确认：

- GDD 每项当前版本责任都映射到 Module 与 View；
- 模块名和责任是玩家业务能力，不是流程步骤、技术层或工具；
- 动作拆分符合真实触发与提交点；
- 事实所有权和角色选择没有包装、镜像或重复；
- 伪代码足以审查输入、分支、写入、事件和导航；
- Luban schema 到字段、类型、约束、消费者和示例；
- WindowData、定向刷新、空事件和按钮调用符合 View 合同；
- 每份 MDD 的验收不需要后续产物。

发现语义问题时只修改临时合同和暂存文档，重新运行验证。

## 7. 发布

`full --surface staging` 验证退出码为 0 后，运行 `publish`。发布器：

- 再次完整验证暂存区；
- 保留现有 `策划案.md` 和其他非 GDD/MDD 文档；
- 在目标项目同卷准备完整候选 `Docs`；
- 以整套目录交换替换旧设计；
- 对正式目录再次完整验证；
- 普通失败时恢复旧目录。

发布成功后再次显式运行正式目录 `full --surface published` 验证，并用 `discard-stage` 删除本轮临时目录。只有这些步骤全部成功才可报告“完整设计已完成”。

设计动作不创建产品代码、Luban 工作簿、Prefab、场景或生成产物。
