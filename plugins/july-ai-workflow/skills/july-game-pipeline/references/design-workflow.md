# 完整设计流程

本流程把策划案转成当前版本可直接审查和实施的完整设计。设计动作必须先解决结构性问题，再写正式文档；不得一边生成产品代码一边补设计。

## 1. 输入与讨论边界

读取：

- `Design/Docs/策划案.md`；
- 已有 `GDD.md`、`MDD/索引.md`、模块 MDD 与 View MDD；
- 当前工程稳定宿主的程序集、启动组合、注册、UI、场景、资源与 Luban 作者源约定；
- 当前工程固定版本 July/Luban 的公开源码、示例与实际接口。

重新生成时，旧业务代码不证明模块、角色、接口、类型或目录是正确的。只可从旧工程中识别仍然有效的稳定宿主约束，不沿用旧业务设计。

在写文档前，与用户逐项讨论会改变以下内容的问题：

- 当前版本范围、玩家目标、核心循环和完成条件；
- 业务概念的含义、规则、输入、结果和允许失败；
- 完整玩家流程、分支、回退和玩家可见反馈；
- 业务事实的唯一权威来源；
- 模块责任、依赖方向和跨模块操作归属；
- 完整 View 清单、画面责任和交互入口；
- Luban 作者数据的字段含义和归属；
- 任何会改变文件、角色、公共接口或制作范围的选择。

只有用户明确推迟、且不会改变上述结构的内容可以记录为未决。讨论期间不要写仓库内决策草稿或临时状态文件。

## 2. 建立 GDD

`GDD.md` 只记录产品事实，至少包含：

1. 产品定位、当前版本范围和排除项；
2. 玩家目标与核心循环；
3. 统一业务词汇及每个概念的含义；
4. 静态内容和可调规则；
5. 运行时事实及玩家可感知变化；
6. 每条完整玩家流程的触发、步骤、成功结果、允许失败和反馈；
7. 全局约束与不变量；
8. 用户明确推迟的非结构性内容。

GDD 禁止出现类名、JulyArch 角色、代码目录、程序集、配置表结构、注册方式或实现伪代码。

## 3. 从玩家体验推导技术设计

对每条完整玩家流程按固定顺序分析：

1. 列出玩家能看到的事实；
2. 列出玩家能执行的动作；
3. 列出动作完成后哪些事实发生改变；
4. 指定每个事实的唯一权威来源；
5. 指定每个动作的业务能力所有者；
6. 列出需要展示或交互的 View；
7. 在所有权稳定后才选择角色、类型、接口和文件。

不要从类名或预想文件结构反推业务。一个完整玩家流程可以跨多个模块，但跨模块调用必须属于发起动作的业务能力，不创建独立“联通层”。

## 4. 业务事实所有权

在 `索引.md` 中先建立全局事实表，再设计任何产品类型：

| 业务事实 | 权威来源 | 写入者 | 读取者 | 派生方式/更新时机 | 禁止副本 |
| --- | --- | --- | --- | --- | --- |

权威来源只能是以下之一：

- Luban 作者数据；
- 某个 Store 的受控运行时状态；
- July 或 Unity 已提供的稳定运行时事实；
- 从其他权威事实即时派生的值。

同一事实不得同时存在于配置、Store、WindowData 和自定义 Definition 中。WindowData 是可写展示快照，不是第二业务权威。可由行数、枚举项、当前时间、起始时间或其他权威数据得到的值必须计算，不配置重复常量。

框架已经提供且语义匹配的时间、资源、UI、事件或生命周期事实直接作为权威来源，不创建项目内平行表示或转换包装。

## 5. 模块划分

模块表示稳定、可独立命名和维护的产品能力。模块不是：

- 玩家流程步骤或一张页面；
- Store/System/Procedure 等技术分层；
- 表格、DTO、枚举或 Data 的集合；
- `Common`、`Core`、`Content` 等宽泛容器；
- 为未来扩展保留的空抽象。

为每个模块说明负责内容、明确排除、拥有事实、公开动作、消费者和依赖。将模块依赖绘制为有向图并验证无环。出现环时重新分配事实或操作所有权；不得用事件、接口或协调器隐藏循环。

玩家完整流程写进发起能力的模块 MDD，包含真实跨模块调用顺序、成功/失败结果和 View 反馈。

## 6. 类型与 JulyArch 角色

先确定责任，再命名类型。

- **Store**：拥有受控运行时业务状态。公开读取，限制写入；一致变更完成后发布空业务事件。
- **System**：通过 `ArchContext` 管理或定位的稳定运行时能力。实现可以简单，当前消费者可以只有一个。
- **Procedure**：一次有界操作，尤其多步骤、异步、可取消或需要明确提交点的操作。
- **普通类型**：拥有真实算法、不变量或值语义，不需要 JulyArch 生命周期。
- **Luban 生成类型**：直接表达静态作者事实。
- **View**：拥有 Unity 表现和交互。

每个候选产品类型都回答：删除它、让消费者直接使用现有 Store/System、Luban 生成类型或框架类型后，会损失什么独立行为、不变量、运行时所有权、生命周期或错误合同？没有损失就删除候选。

禁止创建只保存静态字段的 `Definition`、生成类型镜像、手写别名枚举、查表转发器、模块级空接口、Application/Manager/Facade 总协调器。

## 7. View 完整设计

完整设计阶段必须同时列出并设计当前版本全部玩家可见屏幕和视觉功能。View 按视觉责任建档到 `MDD/Views/`，不按 UI/2D 技术类别建立子目录。

每个 UI Window 强制拥有 WindowData，并遵循 [View MDD 模板](view-mdd-template.md) 中的数据、事件、按钮与导航合同。非 Window 的 GameView 是否需要 Data、采用何种刷新方式，由实际表现责任决定，不套用 Window 规则。

## 8. Luban 设计

任何工作簿创建前，必须在所属模块 MDD 中把每个表、Bean、枚举设计到：

- 作者源位置与表身份；
- 字段名、类型、主键/索引、约束和含义；
- 每个值的业务所有者与消费者；
- 至少一个代表性作者数据示例；
- 生成类型及直接消费方式；
- 注册或加载入口；
- 全量生成与残留检查。

派生数量、覆盖计数和其他可计算值不进入配置。杂项配置只保存确实全局、可调、非派生且没有更窄业务所有者的作者值。

## 9. 完整性审计

正式设计完成前检查：

- GDD 的每项当前版本责任都映射到模块和 View；
- 每个业务事实只有一个权威来源；
- 每个玩家动作都有明确发起模块；
- 模块依赖图无环；
- 所有跨模块流程都写在发起模块 MDD；
- 每个类型通过必要性审查；
- 每个角色符合 JulyArch 语义；
- 所有 Luban schema 已设计完整；
- 每个 View 都有数据来源、刷新、交互和制作合同；
- 每份 MDD 有精确文件白名单和可重复验收；
- 未包含持久化设计、目标项目测试代码、流程状态或设计外占位项。

审计发现结构问题时继续讨论，不将其留给实施阶段猜测。

## 10. 一次性产物

完整设计动作最终创建或更新：

```text
Design/Docs/
├── GDD.md
└── MDD/
    ├── 索引.md
    ├── Modules/M001_<业务能力>.md
    └── Views/V001_<视觉功能>.md
```

实施波次只记录推荐依赖顺序。设计动作不创建产品代码、配置工作簿、Prefab 或场景改动。
