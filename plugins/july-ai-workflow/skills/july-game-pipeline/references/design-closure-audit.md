# 设计闭包审计

完整设计只有同时满足“业务合同唯一”和“单份 MDD 可实施闭包”才可以写入正式文档。模块依赖无环只是其中一项，不能代替本审计。

## 1. 原子玩家动作与唯一合同

先把完整玩家流程拆成原子动作。两个按钮或步骤即使都叫“开始”，只要触发时机、输入、提交点或结果不同，就是两个动作。

在 `索引.md` 建立全局动作合同表。每个动作分配稳定 ID：

| 动作 ID | 玩家意图 | 类型 | 唯一所有者 | 规范签名/调用 | 前置 | 成功/允许失败 | 导航所有者与目标 | GDD |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A001 |  | 业务操作 / 纯导航 / View 本地表现 | 具体模块、View 或 UISystem | 完整签名；无公开调用时写 `无` |  |  |  |  |

约束：

- 每个玩家动作只能有一行、一个所有者和一个规范签名；
- 模块流程、公共接口和 View 交互必须引用动作 ID；
- 同一动作在所有 MDD 中的名称、参数、返回、失败合同和导航所有者必须逐字一致；
- 一个 MDD 不得先调用无参数或半成品操作，另一个 MDD 再用不同参数“正式开始”同一业务；
- 纯展示选择可以由 WindowData 本地维护；真正提交由一个业务 System 方法拥有；
- 纯导航由 Window 调用 UISystem；依赖业务成功的导航属于该业务操作的 System/Procedure，并在动作表中只登记一次。

发现重复动作、签名不一致或导航所有者冲突时，先重新划分原子动作与责任，不写正式设计。

## 2. 产品符号唯一提供者

“产品符号”包括：

- 手写 C# 类型、公开成员和事件；
- Luban 表、Bean、枚举及其生成类型；
- Window、WindowData、GameView；
- Prefab、场景对象、资源地址和本地化键；
- Store/System 注册项及启动接入点。

在 `索引.md` 建立提供表：

| 产品符号/产物 | 唯一提供 MDD | 定义文件/作者源 | 可用时点 | 消费 MDD |
| --- | --- | --- | --- | --- |
|  |  |  | 该 MDD 实施完成后 |  |

一个符号只能由一份 MDD 创建。共享注册文件可以被多份 MDD 分别修改，但每次新增的注册项仍由对应角色所属 MDD 唯一提供。

不得写“复用后续 MDD 的 Bean/枚举/WindowData”。消费者必须排在提供者之后；若一个作者表使用另一模块的 Bean/枚举，定义这些生成符号的 MDD 必须先完成。

## 3. 全产物实施依赖图

依赖图节点是全部 Module MDD 和 View MDD，不只是业务模块。每条边必须记录具体依赖：

| 消费 MDD | 提供 MDD | 依赖符号/文件/动作 ID | 依赖类型 | 原因 |
| --- | --- | --- | --- | --- |
|  |  |  | 编译 / Luban 作者 / 注册 / Prefab制作 / 运行时合同 |  |

稳定宿主和固定 July/Luban 公共 API 不是 MDD 节点，但必须有当前工程证据。尚未实施的产品代码、生成类型、View 或资源都是 MDD 依赖。

图必须无环。出现环时按责任解决：

1. 检查动作是否被错误地拆成两个所有者；
2. 检查数据或生成类型是否属于错误模块；
3. 检查纯导航是否错误进入业务 System；
4. 检查文件是否应由同一稳定能力拥有；
5. 检查 MDD 边界是否本身不能作为一次实施单位。

不得为了消除图上的环而创建空接口、占位类型、携带数据的事件、反射调用、字符串式业务路由、Facade、Manager 或临时兼容层。若在既定规则下无法形成无环图，停止并与用户讨论 MDD 边界或交互责任。

## 4. 单份 MDD 编译闭包

按全产物依赖图做拓扑排序。对排序中的每一份 MDD，模拟“此前只实施了更早 MDD”：

```text
available = 稳定宿主 + 固定 July/Luban API + 所有更早 MDD 的产物 + 当前 MDD 自有白名单产物

for each 当前 MDD 引用的产品类型、成员、生成类型、Window、WindowData、事件、Prefab 脚本、注册项:
    require 引用存在于 available

require 当前 MDD 实施后 Unity 可编译
require 当前 MDD 自己的验收不需要后续 MDD
```

当前 MDD 内多个新文件可以相互引用，因为它们在同一实施任务中一起产生。以下情况不闭包：

- MDD 的 System 直接构造后续 View 的 Data；
- View 调用后续模块尚未提供的 System；
- 作者表使用后续 MDD 才定义的 Bean 或枚举；
- 注册当前角色需要后续类型；
- 验收要求打开后续 Prefab 或完成后续玩家流程；
- 文件白名单没有包含实现规范签名所需的文件。

不闭包时必须重新分配动作、导航、符号所有权或 MDD 白名单。不能把缺失内容留到实施时暂停。

## 5. 拓扑实施顺序与编号

只有闭包审计通过后才编号并写实施顺序：

- Module 编号按它们在全局拓扑顺序中首次出现的先后递增；低编号模块不得依赖更高编号模块；
- View 编号按它们在全局拓扑顺序中首次出现的先后递增；低编号 View 不得依赖更高编号 View；
- 全局实施顺序允许 Module 与 View 交错；不得默认“全部模块后再全部 View”；
- 每一行只列一份 MDD、精确前置 MDD、此前可用符号和独立验收结果；
- 编号是身份，索引中的全局顺序是实施依据。一次仍只实施用户指定的一份 MDD。

第一行必须是真正无产品 MDD 前置依赖且可以独立编译验收的 MDD。

## 6. 持久化禁入

当前流程只设计运行时 Store 和操作。除非用户明确修改本工作流边界，否则正式 GDD 技术映射、索引、模块 MDD、View MDD 和白名单中不得出现：

- Store 接入持久化系统或注册为可存储对象；
- 保存/读取调用、保存失败、重试或回滚合同；
- 本地/服务器选择、Repository、实体、版本、迁移；
- 新存档/旧存档、跨启动恢复或破损存档校验；
- 为未来存档预留的接口、字段、TODO 或占位类型。

产品概念可能需要长期保存，不代表本轮可以设计保存。只描述当前运行期权威事实与行为；具体存读时机由用户后续手动加入。

## 7. 交付前逐项对照

在写入正式文档前先在内存中完成表格和拓扑排序。写入后再次逐项对照：

1. 每个 GDD 玩家动作都有唯一动作 ID；
2. 每个动作在所有 MDD/View 中只有一个规范签名和导航所有者；
3. 每个产品符号有唯一提供 MDD；
4. 全部 Module/View MDD 都在同一依赖图中；
5. 图无环，实施顺序是有效拓扑序；
6. 每份 MDD 只引用稳定宿主、自有或更早产物；
7. 每份 MDD 实施后可以独立编译并完成自身验收；
8. 文件白名单覆盖其提供的全部产物；
9. 没有持久化设计、目标项目测试代码或设计外占位；
10. 任一项失败时继续修订设计，不向用户交付“完整设计”。
