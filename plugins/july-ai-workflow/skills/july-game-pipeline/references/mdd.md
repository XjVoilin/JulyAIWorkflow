# 模块设计到全部 MDD

本流程只根据一份已确认的模块设计生成或更新全部 MDD、简洁索引和 `M999_项目集成收敛.md`，不修改 GDD 或模块设计，不实施代码。

开始前必须已经读取 `july-architecture.md` 和 `code-quality.md`。某份 MDD 涉及 View 时，再读取 `july-ui-components.md`。

## 1. 确定输入与目标

使用用户 `@` 指定的模块设计。目标 MDD 目录由统一入口按默认位置确定。

- 找不到模块设计：报告未执行；
- 模块设计没有记录唯一来源 GDD，或者来源路径无法从模块设计所在位置解析：报告未执行，建议先更新模块设计；
- 目标 MDD 目录不存在：创建完整 MDD 集合；
- 目标 MDD 目录已存在但用户尚未确认更新：停止，不覆盖；
- 用户已对统一入口的本次询问作出肯定确认：读取现有索引、全部 MDD、模块设计、来源 GDD 和当前代码并整体更新。

未指定目标时，在模块设计同级使用 `MDD` 目录。来源 GDD 提供产品规则，模块设计提供模块职责、状态所有权、协作方向和 JulyArch 角色规划；两者都必须读取，但用户不需要再次显式指定 GDD。

## 2. 检查当前技术工程

直接检查当前项目实际存在的：

- JulyFramework 包、版本、基类、生命周期和 API；
- 当前代码目录、命名空间、asmdef 和注册方式；
- Luban 作者源、生成配置和已有生成命令；
- 已经实现的产品代码和公开接口。

不要读取其他产品项目，不建立项目画像，不要求项目提供额外说明 Markdown，不执行独立的模板完整性检查。

来源 GDD 或模块设计需要但当前工程未安装的 July 能力必须报告，不能自动安装或设计替代框架。

## 3. 先解决歧义

如果来源 GDD 没有明确会影响状态、规则、功能边界或玩家结果的产品语义，报告一个具体缺口并停止，建议用户先更新 GDD。若模块设计与来源 GDD、当前状态所有权或已有模块职责冲突，停止并建议先更新模块设计。当前动作不修改任何上游文档，也不生成部分 MDD。

普通技术选择根据当前工程、JulyArch 正向职责和最小必要改动自行决定。只有技术选择会明显改变公共接口、长期扩展或多个功能边界时才询问用户，每次只问一个问题并给出推荐。

## 4. 目标产物

一次生成：

```text
MDD/
├─ 索引.md
├─ M001_功能名称.md
├─ M002_功能名称.md
└─ M999_项目集成收敛.md
```

不建立 `Modules`、`Views` 或其他技术分类目录。View 是统一 MDD 可以包含的一种代码职责。

## 5. 锁定上游设计

生成 MDD 前先验证模块设计能够作为稳定输入：

- 来源 GDD 路径唯一、可解析，产品规则没有被模块设计复制或改写；
- GDD 中的业务决策、权威状态和不变量在模块设计中都有唯一归属；
- 模块职责、明确排除、稳定语义接口、事务编排和依赖方向完整；
- JulyArch 角色规划与当前工程实际能力可以落实；
- 现有 MDD 更新时，其所属模块和角色仍与最新模块设计一致。

当前动作不得重新拆分、合并或重命名模块，不得改变业务决策、状态、不变量、事务编排的归属，也不得重新分配模块设计已经确定的 JulyArch 角色。发现上游设计不完整或不合理时停止并建议更新模块设计；发现产品规则缺失时停止并建议更新 GDD。

## 6. 根据模块设计拆分 MDD 并落实角色

一份 MDD 围绕一个清晰的功能责任或一次适合人工审查的职责变化。MDD 是实施与审查切片，不决定模块边界：

- 不要求独立运行、独立可见或形成可玩闭环；
- 不要求没有其他 MDD 依赖；
- 不按每个类机械拆分；
- 不把完整纵向闭环的所有业务、View 和配置强行塞进一份文档；
- 一份 MDD 可以创建多个为同一责任服务的角色，也可以只修改一个已有角色；
- View 可以单独成一份 MDD，也可以与少量强相关代码位于同一 MDD；
- 多份 MDD 可以按各自明确范围逐步扩展同一个已有角色或模块。

拆分结果必须便于用户逐份检查业务决策、状态生命周期、所有权、角色和职责。

严格按照模块设计的职责、状态所有权、依赖和角色规划确定具体类型、公开或跨 MDD 签名与文件路径。System 和 Store 没有固定数量目标，每个角色都必须具有模块设计记录的成立依据；模块也可以没有其中任一角色。普通类型只分解同一模块的实现，不能掩盖第二项长期业务能力。MDD 将角色规划细化为实施契约后，实施阶段必须忠实落地。

每份 MDD 明确：

- 本次创建的 JulyArch 角色、公开或跨 MDD 使用的普通类型，以及 Luban 配置；
- 本次允许增量修改的已有类型和具体新增行为；
- 本次创建或修改的主要产品类型的准确文件路径；
- 本次明确不涉及的功能；
- 每项运行时状态及其队列、计数器、游标、随机、推进和恢复机制由哪个 System、Store 或普通运行对象拥有，以及独立共享、替换、持久化或能力生命周期依据；
- 每个编排者拥有的阶段、跨所有者顺序、事务提交和结果处理，以及它明确不拥有的领域机制；
- 类型的真实职责；
- 被其他 MDD 使用的类型及其完整契约闭包：准确 C# 构造函数、方法、属性、事件载荷、可变性和合法状态组合；只有 Framework、Unity、序列化或程序集边界真正要求时才把访问级别写成设计约束。

不使用“类型 Owner”概念。辅助方法、字段、局部集合和具体代码结构留给实施阶段，不在 MDD 中预写完整类代码。实施可以在目标职责与模块范围内创建普通类型来集中已授权的规则、算法、转换和局部运行态；MDD 不逐个预授权这类实现类型，但也不允许它们新增业务职责、跨 MDD 契约、JulyArch 角色或跨模块依赖。

设计公开或跨 MDD 契约时同时遵守：

- 项目业务 System 使用具体类型，不设计配套的 `IXXSystem`；
- 不设计项目业务 `ConfigSystem`、`ContentSystem` 或其他配置聚合入口；实际承担配置读取的业务代码使用框架 `IConfigSystem`，不因读取配置额外创建 System；
- 不设计静态工具类、静态管理器或静态业务入口，纯常量及语言、Unity、Framework、生成器硬性要求除外；
- 对每个公开或跨 MDD 签名执行 `code-quality.md` 的契约闭包；签名引用的项目自定义值、状态、结果和事件类型必须递归展开，不能用“包含”“至少包含”“等”代替准确声明，也不展开私有辅助实现；
- 访问级别与调用方知识统一遵循 `code-quality.md`；同一程序集内不把访问级别写成解耦目标，跨 MDD 契约只描述调用方完成职责所需的业务语义；
- 不用布尔参数让调用方切换不同业务模式；拥有阶段、恢复、保护或流程状态的类型从自身状态决定行为，确有不同调用意图时使用不同语义入口；
- 生命周期内不变的配置由状态所有者在创建边界解释并保存，后续方法不重复接收这些规则参数；
- 普通可失败操作在调用方只需区分接受或拒绝时使用 `bool`；调用方必须区分多个合法结果时设计能排除无效组合的语义结果，不设计只包装成功状态、错误文本或技术异常的通用 `Result`；
- 真实业务计算、推进或阶段转换产物可以定义独立数据类型，不把它误判为成功包装；
- 每个结果或事件类型都写明真实消费者及其使用的业务事实；当前没有消费者、只重复可查询状态或只为假想表现与扩展存在时删除，不把无消费者的包装列为跨 MDD 契约；
- 时间驱动契约遵循 `code-quality.md`：只允许一个 Framework 原始时间入口，并写明从 `deltaTime` 到业务推进信号的转换责任、同一业务步的跨模块优先级、各状态所有者拥有的速度／时长／队列／到期机制和可观察结果；不把原始帧时间、全局下一事件查询或通用剩余时间调度设计为跨 MDD 契约。采用固定 Tick 时，普通运行对象可以接收确定性 Tick 并自行推进领域机制；
- 每个持久阶段写明与其他阶段不同的准入或推进语义、进入事实和结束事实；同一同步调用栈内立即离开且不可观察的状态不设计为阶段；
- 不为普通读取和解耦设计数据快照；按复制行为而不是类型名判断，`ViewState`、`ReadModel`、`DTO` 等只要用于复制全部或大部分可变业务状态供下游读取，同样属于快照。保留 WindowData、存档边界、真实业务结果和 GDD 明确要求的冻结数据；
- 不设计只转发 Store 查询或语义修改的 System；System 公开入口必须隐藏真实业务决策、生命周期或协作步骤；
- 不用 Procedure 包装纯同步调用；只有真实需要等待、跨帧、取消或嵌套的流程才设计 Procedure；
- 公开接口、失败边界、内部实现自由度和已确认变化遵循 `code-quality.md`；配置或文件输入只有在不会于状态修改前自然失败时才设计最小校验，并明确唯一责任位置、该位置实际可取得的全部事实来源和失败行为。无法取得一侧事实的跨表、地图或资源一致性检查不得写成校验承诺；只在模块设计既定职责和依赖方向内调整责任位置或传入最小业务事实，不让调用方解释规则；若必须改变依赖或决策所有权，停止并建议更新模块设计。MDD 不用未经当前代码确认的“自然失败”代替契约，也不把内部不变量逐项改写为验收分支。
- 涉及 WindowData 时遵循 `july-architecture.md` 的两种来源路径；MDD 明确正常入口选择“注入已填充 Data”还是“未注入并创建、填充默认 Data”，不能混用。

产品运行时代码按已确定的业务模块放入 `Assets/Game/Scripts/Runtime/Modules/<模块名>/`，不按 Store、System、Procedure 等角色创建顶层目录。`Views`、`Generated`、`Shared` 等模板已有专用目录保持原有职责。已进入 Luban 的具体配置事实不在 C# 中重复设计。

新增 Luban 业务作者源 Excel 文件在实施范围中写出准确路径，并使用 `<中文业务名>_<英文标识>.xlsx`。英文标识沿用当前工程已有风格；Luban 控制文件和已有作者源文件名不受新增命名规则影响。

## 7. 依赖

每份 MDD 只区分：

### 前置依赖

当前 MDD 无法在不臆造类型或接口的情况下正确实现和编译。记录提供方 MDD、所需跨 MDD 契约或能力，以及为什么必须先实施。

写入前置依赖前必须在当前代码中查找所需类型与准确签名。当前能力已经存在且目标外部签名保持不变时，不把内部实现将由另一份 MDD 迁移、两份 MDD 修改相邻文件、建议实施顺序或最终设计一致性写成前置依赖；这些情况不妨碍当前 MDD 独立正确实现和编译。

### 延迟集成

当前 MDD 自己的职责可以完整实现并编译，但尚不能接入后续流程。记录来源 MDD、目标 MDD、业务连接事实和对应的 M999 集成项。

不要为了消除依赖而创建假接口、占位 System、Common/Core 容器、字符串路由或默认实现。

全部普通 MDD 必须存在可执行顺序。前置依赖不能直接或间接形成循环；出现循环时，调整职责边界，或把只影响最终连接的关系改为延迟集成，不得保留一组无法开始实施的 MDD。

## 8. 普通 MDD 模板

标题可以按内容扩展，但语义至少覆盖：

```markdown
# Mxxx 功能名称

- 文档类型：MDD
- 来源模块设计：`<相对于本文件的准确路径>`
- 来源 GDD：`<相对于本文件的准确路径>`

## 目标与边界
<本 MDD 负责什么，以及明确不负责什么>

## 对应模块设计
<引用模块设计中的所属模块、业务决策、状态生命周期与所有权和角色规划>

## 对应 GDD 内容
<引用 GDD 中的产品规则和功能，不重新发明需求>

## 实施范围

### 创建
- <准确文件路径：类型、配置或文件职责>

### 修改
- <准确文件路径：已有类型只增加什么行为>

### 不涉及
- <相邻但不属于本 MDD 的功能>

## 前置依赖
- 无 / <MDD、准确能力、原因>

## 延迟集成
- 无 / <目标 MDD、业务连接、M999:Ixxx>

## 角色、职责与编排
| 类型 | 所属模块 | JulyArch 角色 | 拥有的状态与机制 | 编排责任与明确排除 | 必要协作 |
|---|---|---|---|---|---|

## 状态与数据
<权威状态、能力运行态、流程态、派生值、配置事实，各自生命周期与所有者及修改入口>

## 行为与跨 MDD 契约
| 类型 | 准确签名 | 语义 | 返回与失败处理 |
|---|---|---|---|

<对表中所有签名引用的项目自定义类型完成契约闭包；结果和事件同时写明合法状态组合与真实消费者。不要列出私有辅助方法和字段。>

## View 代码
<仅在涉及 Window、WindowData 或 GameView 时填写；每个 Window 同时明确规范类型名、UIWindowID 常量和 TbUIWindow 作者源记录>

## Luban 配置
<仅在涉及作者源时填写；新增业务 Excel 使用“中文业务名_英文标识.xlsx”，并写明表、Bean、枚举和生成入口>

## 验收标准
<可观察业务结果、公开契约、边界拒绝、确定性、事务顺序、资源行为、TODO、生成和编译检查；不固定私有实现步骤>

## 验证方案
<通过真实业务接口验证哪些行为，使用哪些自动化测试或项目验证入口；无法自动化时写明替代步骤和具体原因。测试不得要求生产代码增加测试专用接缝。>
```

不涉及 View 或 Luban 时省略对应章节。没有依赖时明确写“无”。模板是推荐输出结构，不是机械标题校验规则。

## 9. 索引

索引只保留人可读的完整地图：

```markdown
# MDD 索引

- 文档类型：MDD索引
- 来源模块设计：`<相对于本文件的准确路径>`
- 来源 GDD：`<相对于本文件的准确路径>`

| ID | 名称 | 所属模块 | 核心职责 | 前置依赖 | 延迟集成 | 建议顺序 |
|---|---|---|---|---|---|---|
```

索引只维护上表所需的人可读信息，不承担额外的机器契约或流程状态。

ID 规则：

- 普通 MDD 使用稳定的 `M001`、`M002`……；
- `M999` 固定用于项目集成收敛；
- 更新时保留已有 ID；
- 新功能使用下一个未使用 ID；
- 不自动复用或重新编号；
- 来源 GDD 或模块设计删除职责时报告可能失效的 MDD，不自动删除文档。

## 10. M999 项目集成收敛

M999 是一份特殊 MDD，不是新的插件动作。它只记录普通 MDD 已经声明、但因实施顺序延迟的连接。

只有连接确实不能在来源普通 MDD 中完成、并且后续仍需要实际修改文件时才进入 M999。当前工程已经存在且目标保持不变的注册、持久化、页面打开、配置加载或事件订阅，不因需要“保持、确认、核对”而建立集成项；更新时这类旧集成项应删除并保留 ID 空缺，不改号、不复用。

允许记录：

- 跨 MDD 调用；
- 事件连接；
- 页面导航；
- 注册与装配；
- Luban 配置接入；
- 其他已经在普通 MDD 中声明的集成点。

禁止记录新业务规则、新状态、新 System 能力、新页面功能或角色重新设计。

使用稳定集成项 ID：

```markdown
# M999 项目集成收敛

- 文档类型：MDD
- 来源模块设计：`<相对于本文件的准确路径>`
- 来源 GDD：`<相对于本文件的准确路径>`

## I001 集成项名称

- 来源 MDD：Mxxx
- 目标 MDD：Mxxx
- 业务连接：<已由普通 MDD 定义的关系>
- 实施条件：<必须已经实施的 MDD>
- 允许修改：<连接所需类型或配置>
- 预期结果：<完成后的调用、事件、导航或注册>
```

更新时保留已有 `Ixxx`，不重新编号。

## 11. 写后验证闭环

生成或更新索引、全部普通 MDD 和 M999 后，产出尚未完成。必须执行以下闭环：

1. 从磁盘重新读取索引、全部普通 MDD 和 M999，不依赖写作过程中的记忆；
2. 建立只用于当前执行的临时一致性矩阵，至少记录每项 GDD 功能和模块设计业务决策的承担 MDD、所属模块、状态生命周期与所有者、领域推进机制所有者、JulyArch 角色、跨模块事务编排者及其明确排除、每份 MDD 的前置依赖与延迟集成、持久状态边界、View/Luban 范围、跨 MDD 契约闭包及调用方所需知识、结果或事件消费者、校验所需事实来源、原始时间入口、确定性推进信号、验证路径和文件创建/修改事实；不把矩阵写入项目；
3. 对照来源 GDD、模块设计、当前代码、实际 JulyFramework/Luban/UI API、`july-architecture.md`、`code-quality.md` 和按需加载的 `july-ui-components.md` 逐项验证；
4. 能在 MDD 动作范围内修正的问题立即修正，然后从磁盘重新读取受影响文档并再次验证；
