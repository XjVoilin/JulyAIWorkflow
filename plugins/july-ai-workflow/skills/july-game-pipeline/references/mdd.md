# GDD 到全部 MDD

本流程只生成或更新全部 MDD、简洁索引和 `M999_项目集成收敛.md`，不实施代码。

开始前必须已经读取 `july-architecture.md`。某份 MDD 涉及 View 时，再读取 `july-ui-components.md`。

## 1. 确定输入与目标

优先使用用户 `@` 指定的 GDD。未指定时，只使用当前项目中名称明确且唯一的 GDD。

- 找不到 GDD：报告未执行；
- 候选不唯一：询问用户；
- 目标 MDD 目录已存在而用户只说“生成”：停止，不覆盖；
- 用户说“更新”：读取现有索引、全部 MDD、当前代码和最新 GDD；
- 用户说“重新生成 MDD”：报告第一版不支持，建议改为更新全部 MDD。

未指定目标时，在 GDD 同级使用 `MDD` 目录。

## 2. 检查当前技术工程

直接检查当前项目实际存在的：

- JulyFramework 包、版本、基类、生命周期和 API；
- 当前代码目录、命名空间、asmdef 和注册方式；
- Luban 作者源、生成配置和已有生成命令；
- 已经实现的产品代码和公开接口。

不要读取其他产品项目，不建立项目画像，不要求项目提供额外说明 Markdown，不执行独立的模板完整性检查。

GDD 需要但当前工程未安装的 July 能力必须报告，不能自动安装或设计替代框架。

## 3. 先解决歧义

如果 GDD 没有明确会影响状态、规则、功能边界或玩家结果的产品语义，报告一个具体缺口并停止。建议用户单独执行 GDD 更新；当前动作不修改 GDD，也不生成部分 MDD。

普通技术选择根据当前工程、JulyArch 正向职责和最小必要改动自行决定。只有技术选择会明显改变公共接口、长期扩展或多个功能边界时才询问用户，每次只问一个问题并给出推荐。

## 4. 一次生成完整 MDD 集合

一次生成：

```text
MDD/
├─ 索引.md
├─ M001_功能名称.md
├─ M002_功能名称.md
└─ M999_项目集成收敛.md
```

不建立 `Modules`、`Views` 或其他技术分类目录。View 是统一 MDD 可以包含的一种代码职责。

## 5. 拆分原则

一份 MDD 围绕一个清晰的功能责任或一次适合人工审查的职责变化。

- 不要求独立运行、独立可见或形成可玩闭环；
- 不要求没有其他 MDD 依赖；
- 不按每个类机械拆分；
- 不把完整纵向闭环的所有业务、View 和配置强行塞进一份文档；
- 一份 MDD 可以创建多个为同一责任服务的角色；
- 一份 MDD 可以只修改一个已有角色；
- View 可以单独成一份 MDD，也可以与少量强相关代码位于同一 MDD；
- 多份 MDD 可以按各自明确范围逐步扩展同一个已有角色。

拆分结果必须便于用户逐份检查角色、状态所有权和职责。

## 6. 角色与公开边界

根据完整 GDD 和全部 MDD 关系统一分配 JulyArch 角色。角色由职责与协作关系决定；MDD 确定角色后，实施阶段必须忠实落地。

在确定类型和路径前，先按 `july-architecture.md` 统一划分业务模块：围绕权威运行时状态及其行为，或能够独立存在的无状态业务能力归组。MDD 拆分不决定模块边界；多份 MDD 可以按明确范围扩展同一个模块。

每个候选模块必须能够说明一个核心业务职责及明确不负责的相邻职责，并同时通过以下检查：

- 模块内最多一个项目业务 System、最多一个项目业务 Store；
- System、Store 与模块的职责范围一致；
- 不按技术层次、JulyArch 角色、配置来源或覆盖大部分产品的宽泛概念命名；
- 删除模块后不会只剩少量框架调用转发；
- 不为满足角色数量限制而合并无关状态或能力。

每份 MDD 明确：

- 本次创建的类型或 Luban 配置；
- 本次允许增量修改的已有类型和具体新增行为；
- 本次创建或修改的主要产品类型的准确文件路径；
- 本次明确不涉及的功能；
- 业务状态由哪个 Store 拥有；
- 类型的真实职责；
- 被其他 MDD 使用的公开类型与准确 C# 签名。

不使用“类型 Owner”概念。私有方法、辅助字段和具体代码结构留给实施阶段，不在 MDD 中预写完整类代码。

设计公开类型时同时遵守：

- 项目业务 System 使用具体类型，不设计配套的 `IXXSystem`；
- 不设计项目业务 `ConfigSystem`、`ContentSystem` 或其他配置聚合入口；各业务 System 直接读取本模块需要的 Luban 表；
- 不设计静态工具类、静态管理器或静态业务入口，纯常量及语言、Unity、Framework、生成器硬性要求除外；
- 普通可失败操作使用 `bool` 并由责任函数记录失败日志，不设计只包装成功状态和失败原因的 `Result`；
- 真实业务计算产物可以定义独立数据类型，不把它误判为成功包装；
- 不为普通读取和解耦设计数据快照；保留 WindowData、存档边界和 GDD 明确要求的冻结数据。

产品运行时代码按已确定的业务模块放入 `Assets/Game/Scripts/Runtime/Modules/<模块名>/`，不按 Store、System、Procedure 等角色创建顶层目录。`Views`、`Generated`、`Shared` 等模板已有专用目录保持原有职责。已进入 Luban 的具体配置事实不在 C# 中重复设计。

## 7. 依赖

每份 MDD 只区分：

### 前置依赖

当前 MDD 无法在不臆造类型或接口的情况下正确实现和编译。记录提供方 MDD、所需公开类型或能力，以及为什么必须先实施。

### 延迟集成

当前 MDD 自己的职责可以完整实现并编译，但尚不能接入后续流程。记录来源 MDD、目标 MDD、业务连接事实和对应的 M999 集成项。

不要为了消除依赖而创建假接口、占位 System、Common/Core 容器、字符串路由或默认实现。

全部普通 MDD 必须存在可执行顺序。前置依赖不能直接或间接形成循环；出现循环时，调整职责边界，或把只影响最终连接的关系改为延迟集成，不得保留一组无法开始实施的 MDD。

## 8. 普通 MDD 模板

标题可以按内容扩展，但语义至少覆盖：

```markdown
# Mxxx 功能名称

## 目标与边界
<本 MDD 负责什么，以及明确不负责什么>

## 对应 GDD 内容
<引用 GDD 中的产品规则和功能，不重新发明需求>

## 实施范围

### 创建
- <准确文件路径：类型、配置或文件职责>

### 修改
- <准确文件路径：已有类型只增加什么行为>

### 不涉及
- <相邻但不属于本 MDD 的功能>

## 前置依赖
- 无 / <MDD、准确能力、原因>

## 延迟集成
- 无 / <目标 MDD、业务连接、M999:Ixxx>

## 角色与职责
| 类型 | 所属模块 | JulyArch 角色 | 职责 | 必要协作 |
|---|---|---|---|---|

## 状态与数据
<权威状态、派生值、配置事实及修改入口>

## 行为与公开能力
| 类型 | 准确公开签名 | 语义 | 返回与失败处理 |
|---|---|---|---|

## View 代码
<仅在涉及 Window、WindowData 或 GameView 时填写；每个 Window 同时明确规范类型名、UIWindowID 常量和 TbUIWindow 作者源记录>

## Luban 配置
<仅在涉及作者源时填写>

## 验收标准
<职责、范围、TODO、生成和编译检查>
```

不涉及 View 或 Luban 时省略对应章节。没有依赖时明确写“无”。模板是推荐输出结构，不是机械标题校验规则。

## 9. 索引

索引只保留人可读的完整地图：

```markdown
# MDD 索引

| ID | 名称 | 所属模块 | 核心职责 | 前置依赖 | 延迟集成 | 建议顺序 |
|---|---|---|---|---|---|---|
```

索引只维护上表所需的人可读信息，不承担额外的机器契约或流程状态。

ID 规则：

- 普通 MDD 使用稳定的 `M001`、`M002`……；
- `M999` 固定用于项目集成收敛；
- 更新时保留已有 ID；
- 新功能使用下一个未使用 ID；
- 不自动复用或重新编号；
- GDD 删除功能时报告可能失效的 MDD，不自动删除。

## 10. M999 项目集成收敛

M999 是一份特殊 MDD，不是新的插件动作。它只记录普通 MDD 已经声明、但因实施顺序延迟的连接。

允许记录：

- 跨 MDD 调用；
- 事件连接；
- 页面导航；
- 注册与装配；
- Luban 配置接入；
- 其他已经在普通 MDD 中声明的集成点。

禁止记录新业务规则、新状态、新 System 能力、新页面功能或角色重新设计。

使用稳定集成项 ID：

```markdown
# M999 项目集成收敛

## I001 集成项名称

- 来源 MDD：Mxxx
- 目标 MDD：Mxxx
- 业务连接：<已由普通 MDD 定义的关系>
- 实施条件：<必须已经实施的 MDD>
- 允许修改：<连接所需类型或配置>
- 预期结果：<完成后的调用、事件、导航或注册>
```

更新时保留已有 `Ixxx`，不重新编号。

## 11. 完成检查

写入前确认：

- GDD 的每项真实功能都有明确 MDD 承担；
- 每份 MDD 适合单独人工检查，不追求单份闭环；
- 业务状态所有权和 JulyArch 角色清楚；
- 跨 MDD 公开签名准确且一致；
- 前置依赖与延迟集成没有混淆；
- 普通 MDD 的前置依赖不存在循环，并且存在明确的可执行顺序；
- 全部延迟关系进入 M999；
- View 与普通功能使用统一 MDD；
- 每个 Window 类型名以 `UI` 开头、以 `Window` 结尾，`UIWindowID` 同名常量与 `TbUIWindow` ID 一致；
- 没有项目级 `IXXSystem`、静态业务容器、成功失败 `Result` 包装或无明确边界的数据快照；
- 每个业务模块最多一个项目业务 System、最多一个项目业务 Store，且名称和职责范围一致；
- 没有项目业务 ConfigSystem、ContentSystem 或配置聚合入口，没有在 C# 中重复 Luban 的具体配置事实；
- 每个模块都能说明单一业务职责及明确不负责的相邻职责，没有宽泛收纳模块或纯转发模块；
- 产品运行时代码按业务模块位于 `Runtime/Modules/<模块名>`，没有按 JulyArch 角色创建顶层 `Systems`、`Stores` 或 `Procedures` 目录；
- 没有生成本流程范围之外的产物；
- 只修改了目标 GDD 对应的 MDD 集合。

完成后报告索引、普通 MDD 和 M999 的路径，然后停止，不实施任何 MDD。
