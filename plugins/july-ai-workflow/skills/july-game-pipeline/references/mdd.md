# GDD 到全部 MDD

本流程只生成或更新全部 MDD、简洁索引和 `M999_项目集成收敛.md`，不实施代码。

开始前必须已经读取 `july-architecture.md`。某份 MDD 涉及 View 时，再读取 `july-ui-components.md`。

## 1. 确定输入与目标

优先使用用户 `@` 指定的 GDD。未指定时，只使用当前项目中名称明确且唯一的 GDD。

- 找不到 GDD：报告未执行；
- 候选不唯一：询问用户；
- 目标 MDD 目录已存在而用户只说“生成”：停止，不覆盖；
- 用户说“更新”：读取现有索引、全部 MDD、当前代码和最新 GDD；
- 用户说“重新生成 MDD”：报告第一版不支持，建议改为更新全部 MDD。

未指定目标时，在 GDD 同级使用 `MDD` 目录。

## 2. 检查当前技术工程

直接检查当前项目实际存在的：

- JulyFramework 包、版本、基类、生命周期和 API；
- 当前代码目录、命名空间、asmdef 和注册方式；
- Luban 作者源、生成配置和已有生成命令；
- 已经实现的产品代码和公开接口。

不要读取其他产品项目，不建立项目画像，不要求项目提供额外说明 Markdown，不执行独立的模板完整性检查。

GDD 需要但当前工程未安装的 July 能力必须报告，不能自动安装或设计替代框架。

## 3. 先解决歧义

如果 GDD 没有明确会影响状态、规则、功能边界或玩家结果的产品语义，报告一个具体缺口并停止。建议用户单独执行 GDD 更新；当前动作不修改 GDD，也不生成部分 MDD。

普通技术选择根据当前工程、JulyArch 正向职责和最小必要改动自行决定。只有技术选择会明显改变公共接口、长期扩展或多个功能边界时才询问用户，每次只问一个问题并给出推荐。

## 4. 一次生成完整 MDD 集合

一次生成：

```text
MDD/
├─ 索引.md
├─ M001_功能名称.md
├─ M002_功能名称.md
└─ M999_项目集成收敛.md
```

不建立 `Modules`、`Views` 或其他技术分类目录。View 是统一 MDD 可以包含的一种代码职责。

## 5. 拆分原则

一份 MDD 围绕一个清晰的功能责任或一次适合人工审查的职责变化。

- 不要求独立运行、独立可见或形成可玩闭环；
- 不要求没有其他 MDD 依赖；
- 不按每个类机械拆分；
- 不把完整纵向闭环的所有业务、View 和配置强行塞进一份文档；
- 一份 MDD 可以创建多个为同一责任服务的角色；
- 一份 MDD 可以只修改一个已有角色；
- View 可以单独成一份 MDD，也可以与少量强相关代码位于同一 MDD；
- 多份 MDD 可以按各自明确范围逐步扩展同一个已有角色。

拆分结果必须便于用户逐份检查角色、状态所有权和职责。

## 6. 角色与公开边界

在确定类型、路径和 JulyArch 角色前，先按 `july-architecture.md` 的模块规则建立只用于当前执行的全局模块图，不写入项目。模块图至少记录：

- 每个模块封装的共同变化知识、稳定接口和明确不负责的相邻职责；
- 权威状态、不变量和必须原子提交的变化；
- 当前项目范围内已确认的扩展及其 GDD、已有 MDD、已接受需求或现有代码来源；
- 模块依赖，以及计划分配的 System、Store、Procedure 和普通类型。

候选模块只有在具有独立变化方向，并能通过稳定接口隐藏当前或已确认扩展的实质复杂度时才成立。共享 Store、相同数据、业务动词、调用方数量、MDD 和代码规模不作为单独依据。拆分若破坏原子提交、形成循环依赖或暴露内部知识，必须重新调整接缝。

扩展既有模块或 System 时，必须在模块图中说明新增能力为何仍与原职责共同变化。无法说明时重新判断模块，不用普通类型抽取掩盖 System 已经承担第二项业务能力。删除后只剩少量转发且没有明确扩展价值的候选不创建。

模块图稳定后再根据职责与协作关系统一分配 JulyArch 角色。模块可以没有 System 或 Store；每个模块最多一个项目业务 System、最多一个项目业务 Store，不为满足数量限制合并无关状态或能力。MDD 确定角色后，实施阶段必须忠实落地。

每份 MDD 明确：

- 本次创建的类型或 Luban 配置；
- 本次允许增量修改的已有类型和具体新增行为；
- 本次创建或修改的主要产品类型的准确文件路径；
- 本次明确不涉及的功能；
- 业务状态由哪个 Store 拥有；
- 类型的真实职责；
- 被其他 MDD 使用的公开类型与准确 C# 签名。

不使用“类型 Owner”概念。私有方法、辅助字段和具体代码结构留给实施阶段，不在 MDD 中预写完整类代码。

设计公开类型时同时遵守：

- 项目业务 System 使用具体类型，不设计配套的 `IXXSystem`；
- 不设计项目业务 `ConfigSystem`、`ContentSystem` 或其他配置聚合入口；各业务 System 直接读取本模块需要的 Luban 表；
- 不设计静态工具类、静态管理器或静态业务入口，纯常量及语言、Unity、Framework、生成器硬性要求除外；
- 普通可失败操作使用 `bool` 并由责任函数记录失败日志，不设计只包装成功状态和失败原因的 `Result`；
- 真实业务计算产物可以定义独立数据类型，不把它误判为成功包装；
- 不为普通读取和解耦设计数据快照；保留 WindowData、存档边界和 GDD 明确要求的冻结数据；
- 默认信任 Framework 生命周期、Luban 生成配置和模块内部契约，不设计启动巡检、完整状态复检、`EnsureInitialized`、`EnsureConfigured` 或只为更友好报错存在的预校验；
- 只有 GDD 定义了失败处理，或者缺少校验会让错误继续运行并污染权威状态时，才在 MDD 中明确最小校验及其具体业务行为。

产品运行时代码按已确定的业务模块放入 `Assets/Game/Scripts/Runtime/Modules/<模块名>/`，不按 Store、System、Procedure 等角色创建顶层目录。`Views`、`Generated`、`Shared` 等模板已有专用目录保持原有职责。已进入 Luban 的具体配置事实不在 C# 中重复设计。

新增 Luban 业务作者源 Excel 文件在实施范围中写出准确路径，并使用 `<中文业务名>_<英文标识>.xlsx`。英文标识沿用当前工程已有风格；Luban 控制文件和已有作者源文件名不受新增命名规则影响。

## 7. 依赖

每份 MDD 只区分：

### 前置依赖

当前 MDD 无法在不臆造类型或接口的情况下正确实现和编译。记录提供方 MDD、所需公开类型或能力，以及为什么必须先实施。

### 延迟集成

当前 MDD 自己的职责可以完整实现并编译，但尚不能接入后续流程。记录来源 MDD、目标 MDD、业务连接事实和对应的 M999 集成项。

不要为了消除依赖而创建假接口、占位 System、Common/Core 容器、字符串路由或默认实现。

全部普通 MDD 必须存在可执行顺序。前置依赖不能直接或间接形成循环；出现循环时，调整职责边界，或把只影响最终连接的关系改为延迟集成，不得保留一组无法开始实施的 MDD。

## 8. 普通 MDD 模板

标题可以按内容扩展，但语义至少覆盖：

```markdown
# Mxxx 功能名称

## 目标与边界
<本 MDD 负责什么，以及明确不负责什么>

## 对应 GDD 内容
<引用 GDD 中的产品规则和功能，不重新发明需求>

## 实施范围

### 创建
- <准确文件路径：类型、配置或文件职责>

### 修改
- <准确文件路径：已有类型只增加什么行为>

### 不涉及
- <相邻但不属于本 MDD 的功能>

## 前置依赖
- 无 / <MDD、准确能力、原因>

## 延迟集成
- 无 / <目标 MDD、业务连接、M999:Ixxx>

## 角色与职责
| 类型 | 所属模块 | JulyArch 角色 | 职责 | 必要协作 |
|---|---|---|---|---|

## 状态与数据
<权威状态、派生值、配置事实及修改入口>

## 行为与公开能力
| 类型 | 准确公开签名 | 语义 | 返回与失败处理 |
|---|---|---|---|

## View 代码
<仅在涉及 Window、WindowData 或 GameView 时填写；每个 Window 同时明确规范类型名、UIWindowID 常量和 TbUIWindow 作者源记录>

## Luban 配置
<仅在涉及作者源时填写；新增业务 Excel 使用“中文业务名_英文标识.xlsx”，并写明表、Bean、枚举和生成入口>

## 验收标准
<职责、范围、TODO、生成和编译检查>
```

不涉及 View 或 Luban 时省略对应章节。没有依赖时明确写“无”。模板是推荐输出结构，不是机械标题校验规则。

## 9. 索引

索引只保留人可读的完整地图：

```markdown
# MDD 索引

| ID | 名称 | 所属模块 | 核心职责 | 前置依赖 | 延迟集成 | 建议顺序 |
|---|---|---|---|---|---|---|
```

索引只维护上表所需的人可读信息，不承担额外的机器契约或流程状态。

ID 规则：

- 普通 MDD 使用稳定的 `M001`、`M002`……；
- `M999` 固定用于项目集成收敛；
- 更新时保留已有 ID；
- 新功能使用下一个未使用 ID；
- 不自动复用或重新编号；
- GDD 删除功能时报告可能失效的 MDD，不自动删除。

## 10. M999 项目集成收敛

M999 是一份特殊 MDD，不是新的插件动作。它只记录普通 MDD 已经声明、但因实施顺序延迟的连接。

允许记录：

- 跨 MDD 调用；
- 事件连接；
- 页面导航；
- 注册与装配；
- Luban 配置接入；
- 其他已经在普通 MDD 中声明的集成点。

禁止记录新业务规则、新状态、新 System 能力、新页面功能或角色重新设计。

使用稳定集成项 ID：

```markdown
# M999 项目集成收敛

## I001 集成项名称

- 来源 MDD：Mxxx
- 目标 MDD：Mxxx
- 业务连接：<已由普通 MDD 定义的关系>
- 实施条件：<必须已经实施的 MDD>
- 允许修改：<连接所需类型或配置>
- 预期结果：<完成后的调用、事件、导航或注册>
```

更新时保留已有 `Ixxx`，不重新编号。

## 11. 写后验证闭环

生成或更新索引、全部普通 MDD 和 M999 后，产出尚未完成。必须执行以下闭环：

1. 从磁盘重新读取索引、全部普通 MDD 和 M999，不依赖写作过程中的记忆；
2. 建立只用于当前执行的临时一致性矩阵，至少记录每项 GDD 功能的承担 MDD、每个模块封装的共同变化知识、稳定接口、明确排除、已确认扩展及来源、状态与角色、每份 MDD 的前置依赖与延迟集成、持久状态边界、View/Luban 范围、主要公开签名和文件创建/修改事实；不把矩阵写入项目；
3. 对照完整 GDD、当前代码、实际 JulyFramework/Luban/UI API、`july-architecture.md` 和按需加载的 `july-ui-components.md` 逐项验证；
4. 能在 MDD 动作范围内修正的问题立即修正，然后从磁盘重新读取受影响文档并再次验证；
5. 只有全部检查通过才能报告完成。若问题需要改变产品语义、角色、状态所有权或公共接口，停止并询问用户，不生成部分完成结论。

首次生成和更新都必须确认：

- GDD 的每项真实功能都有明确 MDD 承担；
- 每份 MDD 适合单独人工检查，不追求单份闭环；
- 业务状态所有权和 JulyArch 角色清楚；
- 跨 MDD 公开签名准确且一致；
- MDD 声明的公开签名、Framework 生命周期和组件能力与当前工程实际 API 一致；
- 前置依赖与延迟集成没有混淆；
- 前置依赖只记录当前工程尚不存在、且不先实施提供方就无法正确实现和编译的能力；现有类型或仅由某 MDD 维护的配置事实不自动构成前置依赖；
- 普通 MDD 的前置依赖不存在循环，并且存在明确的可执行顺序；
- 全部延迟关系进入 M999；
- View 与普通功能使用统一 MDD；
- 每个 Window 类型名以 `UI` 开头、以 `Window` 结尾，`UIWindowID` 同名常量与 `TbUIWindow` ID 一致；
- 每个 Window 都有 WindowData，未注入时创建默认 WindowData，正常运行和 GM 显示均只根据该 Data 渲染；
- 没有项目级 `IXXSystem`、静态业务容器、成功失败 `Result` 包装或无明确边界的数据快照；
- 每个业务模块最多一个项目业务 System、最多一个项目业务 Store；System 的公开能力属于同一长期业务能力，角色在模块确定后分配；
- 没有项目业务 ConfigSystem、ContentSystem 或配置聚合入口，没有在 C# 中重复 Luban 的具体配置事实；
- 没有无真实故障和业务处理依据的配置巡检、生命周期守卫、完整状态复检或异常包装；
- 没有把 Luban 配置缺失、模块内部违约或上游已保证的条件改写成普通业务状态；来自文件、设备时间等真实外部边界且会产生错误业务结果或污染权威状态的输入，只在唯一责任位置设计一次最小校验和明确处理；
- 新增 Luban 业务作者源 Excel 使用“中文业务名_英文标识.xlsx”，控制文件和已有作者源未被无依据重命名；
- 每个模块都能说明共同变化的业务知识、稳定接口及明确不负责的相邻职责；没有宽泛收纳模块、纯转发模块或按 JulyArch 角色划分的模块；
- 小模块的保留能够由当前实质复杂度或当前项目范围内有明确来源的已确认扩展解释；模糊未来没有产生空角色或抽象；
- 共享 Store、相同数据、MDD、调用方数量和代码规模没有被单独用作合并或拆分依据，模块拆分没有破坏原子提交、产生循环依赖或暴露内部知识；
- 新增到既有 System 的公开入口仍属于同一长期业务能力；普通类型只分解该能力的内部实现，没有掩盖第二项业务职责；
- 产品运行时代码按业务模块位于 `Runtime/Modules/<模块名>`，没有按 JulyArch 角色创建顶层 `Systems`、`Stores` 或 `Procedures` 目录；
- 没有生成本流程范围之外的产物；
- 只修改了目标 GDD 对应的 MDD 集合。

更新已有 MDD 时还必须确认：

- 保留已有 `Mxxx` 与 `Ixxx`，新内容没有复用历史空缺或无依据重编号；
- 当前已存在的代码、作者源和公开能力在实施范围中被识别为修改或复用，没有重新描述为待创建能力；
- 旧规则被删除或改变后，索引、其他普通 MDD 和 M999 没有遗留引用；
- 新增或改变持久字段时，同一状态所有者的存档边界与恢复行为已同步检查；
- 更新覆盖完整 MDD 集合，没有只修正用户最近提到或文本上最显眼的问题。

全部通过后报告索引、普通 MDD、M999 的路径和实际验证结果，然后停止，不实施任何 MDD。
